# 기본 프로필 프리셋

사용자에게 "이 프리셋 그대로 쓸지, 새로 구성할지" 물을 때 보여주는 세트다. 사용자가 직접
설계를 요청했거나 이 세트를 거절하면 쓰지 않는다.

**프리셋에는 모델 ID도 provider도 없다.** 프리셋이 정의하는 것은 역할, 요구 성능 등급,
권한 등급, `notes` 네 가지뿐이다. 모델과 provider는 아래 해석 절차가 **등록할 때마다
실조회로** 정한다. 정적 후보 목록을 두면 연결도 안 된 provider의 모델을 권하게 되고,
사용자가 나중에 provider를 추가하면 그 목록이 낡기 때문이다.

## 해석 절차

순서대로 실행한다. 각 단계는 앞 단계의 조회 결과만 쓴다.

### 1단계 — 활성 provider 확인

MCP `list_providers`로 활성 provider 목록을 받는다.

**활성 provider가 하나도 없으면 프리셋을 제안하지 않고 중단한다.** 프로필은 `provider`가
필수 필드라 만들 수 없다. 이때 사용자에게 아래 취지로 안내한다.

> Paseo에 활성화된 provider가 없습니다. 프로필은 provider와 model이 있어야 만들 수 있어
> 지금은 프리셋을 제안할 수 없습니다. Paseo 설정에서 모델을 연결한 뒤 다시 요청해 주세요.

활성 provider가 하나라도 있으면 **그 provider들만** 이후 단계의 대상이다. 비활성 provider는
후보에서 제외한다. 특정 provider를 이름으로 우대하거나 배제하지 않는다.

### 2단계 — 모델과 thinking 옵션 조회

MCP `list_models`로 1단계 provider들의 모델 ID와 `thinkingOptions`를 받는다. 표시명이 아니라
**ID**를 쓴다.

**모델이 0개인 provider는 후보에서 뺀다.** provider가 활성이라는 것과 그 provider로 쓸 모델이
있다는 것은 다르다. 프로필은 `model` 없이는 아무 에이전트도 띄우지 못하므로, 여기서 갈래가
둘로 나뉜다.

- **일부 provider만 0개다** — 그 provider만 빼고 남은 provider로 계속 진행한다. 중단하지
  않는다. 3단계 이후의 「활성 provider」는 **모델이 하나 이상 있는 provider**만 가리킨다.
  빠진 provider가 있다는 사실은 4단계에서 후보를 보여줄 때 한 줄로 알린다.
- **모든 provider가 0개다 — 쓸 수 있는 모델이 하나도 없다** — 활성 provider가 있어도
  **프리셋을 제안하지 않고 중단한다.** 이때 사용자에게 아래 취지로 안내한다.

> Paseo에 연결된 모델이 없습니다. provider는 활성이지만 쓸 수 있는 모델이 조회되지 않아
> 지금은 프리셋을 제안할 수 없습니다. Paseo 설정에서 모델을 연결한 뒤 다시 요청해 주세요.

### 3단계 — 등급 판정

조회 결과만으로 판정한다. 모델 ID를 아는 것에 의존하지 않는다.

**3-1. provider 안에서 사고 상한으로 정렬한다.** 상한은 그 모델의 `thinkingOptions` 중 가장
높은 값이고, 높낮이는 이 순서다.

```text
(빈 배열) < off < low < medium < high < xhigh < max < ultra = ultracode
```

`ultra`(codex)와 `ultracode`(claude)는 이름만 다른 같은 자리다. 상한이 같으면 `list_models`가
돌려준 순서를 유지한다.

**3-2. 정렬 결과의 자리로 등급을 준다.**

| provider의 모델 수 | 고성능 | 중급 | 저성능 |
| --- | --- | --- | --- |
| 3개 이상 | 1위 | 2위 | 최하위 |
| 2개 | 1위 | 1위 | 2위 |
| 1개 | 그 모델 | 그 모델 | 그 모델 |

등급은 **provider 안에서의 상대 순위**다. provider마다 따로 매긴다. 모델 수가 적은
provider도 이 표로 세 등급이 모두 채워지므로, 모델이 적다는 이유로 제외되지 않는다.

**3-3. 갈리지 않으면 묻는다.** 상한이 같고 반환 순서로도 우열을 정할 수 없으면 추측하지
말고 사용자에게 어느 것을 위에 둘지 묻는다.

### 4단계 — 등급별 모델 확정

활성 provider가 하나면 3단계 결과를 그대로 쓴다.

**여럿이면 등급마다 provider별 후보가 생긴다.** 어느 provider를 쓸지 임의로 고르지 말고,
등급별 후보를 사용자에게 보여주고 고르게 한다. 프리셋별로 일곱 번 묻지 않는다 — 고성능,
중급, 저성능 세 등급에 대해 한 번만 묻는다. 사용자가 선호 provider를 이미 말했으면 그것을
기본으로 두고 확인만 받는다.

### 5단계 — 프리셋에 채워 제시

7종에 확정된 모델을 채우고, `thinkingOptionId`와 `modeId`를 아래 규칙으로 계산해 표로
보여준 뒤 확정받는다. 확정 전에는 `--apply`를 실행하지 않는다.

provider별 mode 값과 모델별 thinking 옵션의 생김새는 [`provider-modes.md`](provider-modes.md)에
예시가 있다. 그 문서는 스냅샷이므로 **판정은 이 절차의 실조회 결과로 한다.**

### `thinkingOptionId` 규칙

프리셋은 모두 **최고 등급**을 쓴다. 모델마다 유효 값이 다르므로 값이 아니라 규칙으로 적는다.

| 고른 모델의 `thinkingOptions` | `thinkingOptionId` |
| --- | --- |
| `max`가 있다 | `max` |
| `max`는 없고 `xhigh`가 있다 | `xhigh` |
| 둘 다 없다 | 목록의 마지막 값 |
| **빈 배열이다** | **필드를 넣지 않는다** |

- `ultra`(codex)와 `ultracode`(claude)는 목록에 있어도 기본으로 쓰지 않는다. 사용자가
  명시적으로 요청할 때만 넣는다.
- 비용을 낮추고 싶다는 요청이 있으면 해당 프로필만 한 단계 내린다. 세트 전체를 내리지 않는다.

### 권한 등급 → `modeId`

| 권한 등급 | claude | codex |
| --- | --- | --- |
| 읽기·확인 | `auto` | `auto` |
| 파일 작성 | `auto` | `auto-review` |
| 명령 전권 | `bypassPermissions` | `full-access` |

- 표에 없는 provider는 `inspect_provider`의 `modes[].id`를 받아 제약이 큰 쪽부터 세 등급에
  대응시킨다. 자세한 방법은 [`provider-modes.md`](provider-modes.md)에 있다.
- **명령 전권은 `run-command` 하나에만 붙인다.** codex `full-access`는 네트워크 접근과
  무제한 실행을 준다.
- claude `plan`은 어느 프리셋에도 쓰지 않는다. 문서 산출까지 막는다.

## 세트

| id | name | 요구 성능 등급 | 권한 등급 | icon / color |
| --- | --- | --- | --- | --- |
| `team-lead` | 팀장 | 고성능 | 읽기·확인 | compass / violet |
| `design` | 설계 | 고성능 | 파일 작성 | fileText / emerald |
| `analyze` | 분석 | 고성능 | 파일 작성 | microscope / red |
| `review` | 검토 | 고성능 | 읽기·확인 | eye / amber |
| `work` | 작업 | 중급 | 파일 작성 | code / orange |
| `search` | 검색·조사 | 저성능 | 읽기·확인 | search / sky |
| `run-command` | 명령어 실행 | 저성능 | 명령 전권 | terminal / sky |

`notes`는 전부 64~75자다. `scripts/manage_profiles.py`의 `MAX_NOTES_UNICODE_CHARS`
(160자를 넘으면 경고) 안에 있다. 사용자가 문구를 고칠 때도 이 한도를 넘기지 않는다.

### `team-lead` — 팀장

- `notes`: `여러 단계에 걸친 요청과 배분 판단에 사용 — 라우팅, 순서 결정, 결과 취합, 사용자 확인. 실제 작업은 워커 프로필.`
- 권한 근거: 위임 판단과 취합만 하므로 파일을 직접 고칠 이유가 없다.
- 라우팅이 틀리면 그 아래 작업이 전부 어긋난다. 등급을 고성능 아래로 내리지 않는다.

**팀장 모델 우선 추천 — 이 프리셋에만 적용한다.** 3단계의 상대 순위로 고른 고성능 모델을
그대로 쓰기 전에, 확정된 provider의 `list_models` 결과에서 아래를 **먼저 찾아본다.**

| 확정된 provider | 조회 결과에서 찾을 것 |
| --- | --- |
| codex | id에 `sol`이 들어간 모델. 여럿이면 3단계 정렬에서 위인 것. |
| claude | id에 `opus`가 들어가고 **버전이 5 이상**인 모델. 여럿이면 3단계 정렬에서 위인 것. |

**claude의 버전 하한 판정.** `claude`에는 Opus 5와 Opus 4.x가 함께 조회된다. `opus`만으로
찾으면 4.x가 잡혀 「Opus 5 이상」이 깨지므로, id에서 버전을 읽어 걸러낸다.

1. id에서 `opus` **뒤에** 오는 첫 숫자 묶음을 major 버전으로 읽는다(`-`나 `.`로 이어지는
   minor는 무시한다).
2. **major가 5 이상인 것만 후보로 남긴다.** 그 아래는 후보에서 뺀다.
3. **버전 숫자를 읽을 수 없는 id는 후보에서 뺀다.** 5 이상이라고 추정하지 않는다 — 하한을
   보장하는 것이 이 판정의 목적이고, 못 읽은 것을 통과시키면 목적이 사라진다.
4. 남은 후보가 없으면 아래 폴백으로 내려간다.

이것은 버전 비교 규칙이지 특정 모델 id를 값으로 박는 것이 아니다. **판정에 쓸 id를 열거하지
않는다** — 새 Opus가 나오면 문서를 고치지 않아도 규칙이 그대로 통과시킨다.

- **표의 문자열은 프로필에 적을 값이 아니라 조회 결과에서 찾을 검색 키다.** 찾은 모델의
  id를 그대로 쓴다. 이 표에 이름을 적어 두고 그것을 프로필 값으로 옮기지 않는다 — 없는
  모델 id를 적으면 스크립트가 오류로 막는다.
- **찾지 못하면 폴백한다.** 검색 키에 걸리는 모델이(claude는 버전 하한까지 통과한 모델이) 조회
  결과에 하나도 없으면 우선 추천을 포기하고 **3단계 상대 순위의 고성능 1위를 그대로 쓴다.**
  이 폴백이 기본 동작이고, 우선
  추천은 그 위에 얹는 선호일 뿐이다. 상대 순위 규칙 자체는 이 추천 때문에 바뀌지 않는다.
- 이 추천은 4단계에서 확정된 provider 안에서만 적용된다. **provider 선택을 대신하지 않는다.**
  두 provider가 모두 활성이어도 고성능 provider를 고르는 것은 4단계의 사용자 선택이다.
- 이 문서를 쓴 시점에 각 검색 키가 가리키는 것은 codex `gpt-5.6-sol`, claude
  `claude-opus-5`다. **스냅샷이므로 판정은 조회 결과로 한다.** 더 새 모델이 정렬 위에
  들어오면 그것이 추천값이 된다.
- **다른 여섯 프리셋은 이 우선 추천을 쓰지 않는다.** 3단계 상대 순위 결과를 그대로 쓴다.

**팀장 표시 규칙 — 팀장으로 추천하는 프로필은 `id`와 `name` 양쪽에 팀장임을 드러낸다.**
팀장이 `list_profiles`로 자기 자리를 찾을 때 근거가 그 둘뿐이기 때문이다.

- `id`: `team-lead`. 여러 개면 `team-lead-<구분>`으로 접두를 유지한다.
- `name`: `팀장`을 포함한다. 여러 개면 `팀장 · <구분>` 형태로 쓴다.
- 워커 프로필의 `id`와 `name`에는 `team-lead` / `팀장`을 넣지 않는다.

### `design` — 설계

- `notes`: `무엇을 만들지 정하는 작업에 사용 — 요구사항, 범위와 비범위, 수용 기준, 아키텍처 선택. 코드를 쓰는 것은 작업.`
- 권한 근거: 스펙과 계획을 **파일로** 남긴다. claude `plan`은 그 산출까지 막으므로 쓰지 않는다.

### `analyze` — 분석

- `notes`: `원인과 영향 범위를 파고드는 작업에 사용 — 재현, 로그 대조, 가설 배제, 원인 특정, 파급 범위 산정. 위치만 찾으면 검색·조사.`
- 권한 근거: 재현 코드와 임시 로그를 넣었다 빼야 하므로 파일 작성이 필요하다. 원인을 찾은
  뒤의 본 수정은 `work`가 맡는다.

### `review` — 검토

- `notes`: `작성된 변경 검토에 사용 — 수용 기준 충족, 회귀 위험, 예외 처리 누락, 테스트 보장 범위, 진행 가부. 수정은 하지 않음.`
- 권한 근거: 판정만 한다. 파일 작성 권한을 주면 지적과 수정이 섞여 판정 근거가 흐려진다.

### `work` — 작업

- `notes`: `본 코드 작업에 사용 — 기능 추가, 다중 파일 수정, 구조 변경, 원인이 특정된 결함 수정, 테스트, 빌드 검증. 원인 추적은 분석.`
- 권한 근거: 본 코드를 고치는 프로필이다.

### `search` — 검색·조사

- `notes`: `찾아서 알려주는 작업에 사용 — 파일 경로, 코드 위치, 설정 값, 문서와 웹 자료. 왜 그런지 따지는 것은 분석.`
- 권한 근거: 읽기만 한다. 쓰기 권한을 기본으로 주지 않는다.

### `run-command` — 명령어 실행

- `notes`: `실행할 명령이 정해진 작업에 사용 — 빌드, 테스트, 린트, 설치, 로그 수집, 환경 점검. 실패 원인 추적은 분석.`
- 권한 근거: 명령 실행이 목적이라 전권 등급이 필요한 **유일한** 프리셋이다.
- **등록 전에 사용자에게 알리고 확인받는다** — codex `full-access`와 claude
  `bypassPermissions`는 승인 프롬프트 없이 네트워크 접근과 명령 실행을 허용한다. 확인이
  없으면 읽기·확인 등급으로 낮춰 등록하고, 명령마다 승인 프롬프트가 뜬다는 점을 알린다.

## 해석 예시

활성 provider가 `claude` 하나이고, 3단계 정렬의 1위가 `claude-opus-5`(상한 `ultracode`)로
나왔을 때 `team-lead`의 결과는 이렇다. **이 값들은 예시이며 조회 결과에 따라 달라진다.**

```json
{
  "id": "team-lead",
  "name": "팀장",
  "provider": "claude",
  "model": "claude-opus-5",
  "thinkingOptionId": "max",
  "modeId": "auto",
  "icon": "compass",
  "color": "violet",
  "notes": "여러 단계에 걸친 요청과 배분 판단에 사용 — 라우팅, 순서 결정, 결과 취합, 사용자 확인. 실제 작업은 워커 프로필."
}
```

`thinkingOptionId`가 `ultracode`가 아니라 `max`인 것은 규칙대로다 — 최상위 값은 사용자가
요청할 때만 쓴다.

`featureValues`는 어느 프리셋에도 넣지 않는다. 전부 기본값 `false`로 두는 것이 기본이고,
`fast_mode` 같은 토글은 사용자가 요청할 때만 `inspect_provider`로 존재를 확인하고 추가한다.

## 세트 조정 근거

- 출발점 6종(팀장 / 작업 / 분석 / 설계 / 검색·조사 / 명령어 실행)에 `review`(검토)를 하나 더했다.
  산출물을 만든 에이전트가 스스로 수용 판정을 하면 같은 전제를 물려받아 같은 오류를
  통과시키므로, 검토는 별도 `notes`를 가진 프로필이어야 팀장이 다른 워커로 보낼 수 있다.
- 줄인 것은 없다.
