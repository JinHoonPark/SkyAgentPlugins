# 위임 절차

SKILL.md 「수행자 선택」에서 위임으로 판정됐거나 「독립 검토 판단」으로 검토 노드를 열 때 이 문서를 따른다. 승인·권한·성공 판정의 게이트는 SKILL.md 「위임 경로의 승인·판정 게이트」에 있고, 이 문서는 조회·브리핑·기록·호출 방법을 담는다.

순서는 「전제 점검」 → 「레벨 판정 게이트」 → 레벨 1이면 [references/level1.md](level1.md)의 「레벨 1 — 팬아웃」, 레벨 2면 [references/level2.md](level2.md)다. 프로필·브리핑·결과 파일·개입·취합은 두 레벨이 이 문서의 절을 함께 쓴다.

이 스킬과 참조의 `GRAPH.md` 생성·행 추가·열 변경은 스킬 디렉터리에서 `python3 scripts/graph_update.py`의 `create`·`add-row`·`set`으로 수행한다. `python3`가 없으면 `python`으로 실행한다. 스크립트 오류가 나면 [references/failure-handling.md](failure-handling.md)의 「그래프 갱신 오류」를 읽는다.

## 전제 점검

### 도구를 부를 수 있는 상태로 만든다

claude에서 Paseo 도구는 호출 전에 스키마를 로드한다.

```text
ToolSearch select:mcp__paseo__list_profiles,mcp__paseo__create_agent,mcp__paseo__list_workspaces,mcp__paseo__send_agent_prompt,mcp__paseo__get_agent_status,mcp__paseo__list_agents,mcp__paseo__cancel_agent
```

필요한 도구가 늘면 같은 형식으로 이어 붙인다. 이 호스트에 `ToolSearch`가 있으면 먼저 쓰고, 없으면 노출된 도구와 현재 검색 수단으로 확인한다. Codex에서 `ToolSearch` 부재를 단정하거나 특정 모드를 강제하지 않는다. 이후 도구 이름은 접두어 없이 쓴다.

Paseo 도구가 세션에 없으면 연결 불충족을 보고하고 사용자 전역 config를 스스로 고치지 않는다. 프로필 조회는 `list_profiles`로만 한다. provider를 추측하지 않는다. 새 세션에 도구를 주입하려면 `daemon.mcp.injectIntoAgents`가 활성이어야 하며 없으면 기본은 false다. 승인된 범위에서만 복구하고, 불가능하면 설정 변경을 제시해 사용자 판단을 받는다. 그 뒤에만 `paseo run`의 `--provider`·`--mode`·`--thinking`으로 기동하고, 응답·`inspect`의 `thinking`·`currentModeId`를 요청값과 대조해 확인 여부를 SKILL.md 「기동 보고」로 보고한다.

### 프로필 목록을 읽는다

`list_profiles`로 모든 프로필의 `notes`를 읽고 `notes`가 맞는 프로필을 고른다. 추측하지 않는다. 같은 세션에서 이미 읽었으면 다시 호출하지 않는다.
**예외 — 사용자가 그 세션에서 프로필을 바꿨거나 갱신이 확인되면 `list_profiles`를 다시
호출한다.**

| 상태 | 판별 | 처리 |
| --- | --- | --- |
| **A. 목록이 비었다** | `list_profiles`가 빈 목록 | 프로필이 없다고 알리고 진행 여부를 묻는다. 진행하겠다고 답하면 `list_providers`·`list_models`로 고른 뒤 그 사실을 완료 보고에 남긴다 |
| **B. 맞는 것이 없다** | 어느 `notes`도 이 작업 유형을 포함하지 않는다 | 어느 프로필도 억지로 고르지 않는다. 어떤 유형을 찾았고 어느 `notes`도 걸리지 않았는지 한 줄로 알리지 않고, 아래 「역할↔프로필 해석」 4단계로 이번 실행용 값을 구성해 그 사실을 완료 보고에 남긴다 |
| **C. 부분적으로만 맞는다** | `notes`가 인접하지만 경계 문구가 이 작업을 배제한다 | 허용되는 부분만 분리해 배정하고, 나머지는 적합 프로필 없음으로 처리한다(B). 통지로 경계를 넓히지 않는다. 벗어나는 부분이 작업의 본체이면 B로 취급한다. 분리 배정한 사실은 완료 보고에 남긴다 |

### 워크스페이스를 고른다

`list_workspaces`로 조회해 `cwd`가 대상 저장소인 워크스페이스를 고르고, 그 `workspaceId`를
`create_agent`에 **명시한다.** 생략하면 새 워크스페이스가 만들어진다. 워크스페이스 ID를
하드코딩하지 않고 매번 조회한다.

결과 파일을 서로 읽어야 하는 작업들은 같은 워크스페이스에 둔다. 같은 파일을 여럿이 써야 하는 요청은 「레벨 판정 게이트」 Step 3에서 레벨 2로
떨어지므로 격리로 우회하지 않는다. worktree 격리는 사용자가
명시할 때만 쓰고, 그때는 각 worktree 경로를 받아 그 경로를 읽어야 하는 워커의 브리핑에 넣는다.

이 호스트에서 쓸 수 있는 완료 알림·대기 수단을 확인하고, 없으면 종료 확인에
`get_agent_status`·`list_agents`의 제한된 상태 조회를 허용한다.

## 레벨 판정 게이트

대상·역할·공통 입력을 기준으로 작업을 서로 겹치지 않는 단위로 먼저 쪼갠다. 단위 하나 =
워커 노드 하나. 맥락이 다른 일은 나눈다 — 한 세션에 여러 맥락을 몰지 않는다. 워커를 하나라도
띄우기 전에, 그 단위들 사이의 의존을 이 절의 트리로 판정한다.

개발 요청의 단계 전이는 [references/level2.md](level2.md)의 「개발 워크플로우 단계」를 따른다.

여러 작업에 같은 내용이 필요하면, 그것이 이미 확정된 공통 입력인지 먼저 확인한다.
확정됐으면 리더가 같은 내용을 각 워커에 넘겨 독립 노드로 둔다. 확정되지 않았으면 작성
노드 → 사용 노드의 다단이다. 리더가 독립성을 만들려고 그 내용을 직접 창작하면 SKILL.md 「리더가
직접 하는 일」의 제한과 충돌한다. 그 경우는 다단으로 간다.

대상 파일이 다르다는 사실만으로 무조건 분리하지는 않되, 공통 입력이 있다는 이유로 한
워커에 합치지도 않는다.

### 같은 목적의 작업 묶음

동일한 목적·역할·확정 입력을 공유하는 정확 검색과 미리 지정된 명령은 **횟수와 무관하게 한 작업 단위로 묶는다.** 같은 조회를 여러 단위로 나눠 여러 워커에 맡기지 않는다.

묶기 전에 각 항목에 Step 1~5의 의존·역할 분리·공동 쓰기·판정 의존·불명확성이 없는지 확인하고, **하나라도 있으면 묶지 않는다.** 출력에 따라 다음 명령을 고르는 작업은 이 묶음에서 제외하고 「프로필 선택과 값 이관」의 역할 해석으로 보낸다.

묶음 전체에도 SKILL.md 「행동 전 승인 점검」과 「실행 중 개입과 실패」의 실패·권한 규칙을 적용한다. 묶음으로 승인 점검, Step 1~5 레벨 판정, 작성자와 검토자 분리를 우회하지 않는다.

**순서가 있는 판정 트리다. 위에서부터 내려가 처음 걸리는 곳에서 멈춘다.**

```text
Step 0 (레벨과 직교, 항상 수행 — SKILL.md 「행동 전 승인 점검」)

Step 1  어떤 작업의 입력이 다른 작업의 출력인가?            예 → 레벨 2 (멈춤)
Step 2  같은 대상에 서로 다른 역할이 배정되는가?            예 → 레벨 2 (멈춤)
          (구현과 검토, 토론자와 사회자, 작성과 감수)
Step 3  둘 이상의 작업이 같은 파일을 쓰는가?                예 → 레벨 2 (멈춤)
Step 4  어떤 작업의 합격 기준 판정이 다른 작업의 결과에      예 → 레벨 2 (멈춤)
        걸려 있는가?
Step 5  Step 1~4 중 하나라도 "모르겠다"인가?                예 → 레벨 2 (멈춤)
Step 6  그 밖의 전부                                       → 레벨 1
```

쪼갠 결과 다른 작업이 없어도 트리를 건너뛰지 않는다.

### 레벨 2로 떨어지면 level2.md로 간다

Step 1~5 중 하나에 걸리면 레벨 1 팬아웃으로 내려가지 않고 [references/level2.md](level2.md)로 간다. 승인 화면의 mermaid가 해당 의존을 드러낸다.
실행 순서를 바꿔 순차로 돌린다는 이유만으로 레벨 1로 바꾸지 않는다.

## 프로필 선택과 값 이관

### 역할↔프로필 해석

워크플로우 단계와 그래프 패턴은 **역할 이름**으로 기술한다 — 스펙 작성, 스파이크 설계,
구현, 독립 검토처럼 일의 종류다. **프로필 id는 실제 선택 결과와 프리셋 예시에만 쓴다.**

역할 프로필은 앞 단계에서 확정되지 않을 때만 다음 단계로 해석한다.

1. **`notes`가 핵심 작업을 명시 허용하는 프로필을 쓴다.** 스펙 작성에는 요구사항 분석과 사용자 확인 질문 생성이 포함된다. 이름·id가 `spec`이어도 허용 근거가 되지 않는다.
2. **이름·id가 달라도 작업 범위를 허용하는 넓은 프로필을 쓴다.**
3. **담당 부분을 안전하게 분리할 수 있으면 분리 배정한다.** 나머지나 분리 불가능한 작업은 4단계로 간다.
4. **없으면 [../../../references/presets.md](../../../references/presets.md)의 역할 정의와 실조회 모델·thinking으로 이번 실행용 값을 구성한다.** 이때 필요한 「역할 정의」·「역할별 thinking 등급」·「등급 해석 — 표 밖 후보 만들기」 절이 현재 컨텍스트에 없으면 읽는다. 전역 `agentProfiles`는 자동으로 바꾸지 않고 값의 출처를 보고한다.

`notes`가 배제한 일의 처리는 SKILL.md 「위임 경로의 승인·판정 게이트」를 따른다. 적합한 `notes`가 없으면 보고한다.

### 값 이관

`create_agent`에는 `profile` 인수가 없다. **프로필의 값은 자동으로 적용되지 않으므로 네가
옮겨 담는다.** 아래 대응을 그대로 따른다.

| 프로필의 값 | `create_agent`의 자리 |
| --- | --- |
| `provider` + `model` | `provider` — 두 값을 `provider/model` 한 문자열로 합쳐 넣는다 |
| `modeId` | `settings.modeId` |
| `thinkingOptionId` | `settings.thinkingOptionId` |
| `featureValues` | `settings.features` — **프로필에 이 키가 있을 때만** 옮긴다. 없으면 `settings.features`를 넣지 않는다 |

- `workspaceId`를 명시한다(「전제 점검」). `title`은 `프로필이름: 한 줄 요약`이며 60자 이내다. 프로필 이름 때문에 요약 여유가 10자 미만이면 요약만 쓰고 프로필은 `labels.profile`에 둔다. `labels`는 `{"profile": 프로필id, "task": 한 마디, "run": 실행 식별자, "node": 노드 ID}`이며 `run`은 `{YYYY-MM-DD}-{슬러그}` 실행 디렉터리 이름이다.
- 선택 필드인 `settings.modeId`도 기본으로 채우고 프로필 값을 그대로 옮긴다. 결과 파일을 쓸 단위에는 claude `plan` 모드를 고르지 않는다.
- 요청값이 아니라 기동 결과로 모드·모델·thinking을 확인한다. `currentModeId`와 `snapshot.model`·`snapshot.effectiveThinkingOptionId`를 대조하고 `runtimeInfo`는 쓰지 않는다. 노드 1~2개면 `create_agent` 직후 `get_agent_status` 1회, 팬아웃이면 전체 기동 후 `list_agents` 1회로 묶어 확인한다. 보고의 모드·모델에는 확인값과 요청값이 다를 때 출처를 적는다(SKILL.md 「기동 보고」).

### 자문 역할의 폴백

자문 역할의 승인과 대체 금지는 SKILL.md 「위임 경로의 승인·판정 게이트」를 따른다. 적합 프로필이 없으면 이번 실행용 값을 구성할 때 [../../../references/presets.md](../../../references/presets.md)의 「역할 정의」·「등급 해석 — 표 밖 후보 만들기」 중 자문에 필요한 절만 읽는다. 구성할 수도 없으면 자문 노드를 생략하고 보고한다.

## 워커 브리핑

브리핑은 이 작업의 수행·권한·판정에 필요한 정보만 한 번씩 싣는다.

[assets/worker-briefing.md](../assets/worker-briefing.md)가 그 템플릿이다. 워커를 띄우기 직전에 필요한 내용이 현재 컨텍스트에 없으면 읽는다. 중괄호 자리를 채워 `initialPrompt`로 넘긴다.

반드시 싣는 것: 워커 신분과 세션 내 재위임 금지; 실제 프로필 이름과 `notes` 원문(첫 줄은 `너는 워커다. 프로필: {이름} — {notes 원문}`); 노드 목표·수정 가능 대상·사용자 확정 제약; **요약하지 않은 원본 합격 기준**; 필수 입력 경로; 지정한 결과·실패 보고 경로; 도구·권한 예외(셸은 기본 도구, 새 터미널 금지); 출력 크기 제한; 보고 형식.

싣지 않는 것: 프로필 선택 이유·모델 비교; 큐·계획 승인 절차; 다른 노드 작업·참고 배경; 같은 제약의 반복; 미승인 제안; 경로로 제공한 앞 산출물 본문; 검토 노드에 주는 작성자 보고·해결 방향.

사용자 대화에만 있는 제약은 브리핑에 싣는다. 스펙 질문과 그 사용자 답변은 제외 목록의 좁은 예외로서 조건과 예외까지 원문으로 전달한다. 미확정 요청과 질문 대안은 미확정 입력으로 표시하고 실행 지시나 확정 제약으로 취급하지 않는다.

전체 대화와 산출물 본문은 다시 보내지 않는다. 글자 수 때문에 포함 목록 항목을 빼지 않는다. 추가 맥락은 빠지면 실행이나 판정이 달라지는 경우에만 싣는다. 새 브리핑 문서는 만들지 않는다.

### 검토 노드

검토를 여는 조건과 검토 워커의 독립성 요건은 SKILL.md 「독립 검토 판단」에 있다.

검토 라운드는 같은 단계·같은 수용 기준에 대해 총 3회(최초 1회, 재검토 최대 2회)다. 상세한 예산·라운드별 결과/실패 경로는 검토를 열 때 [references/level2.md](level2.md)의 「두 예산 — 사용자 왕복과 검토 라운드」를 읽는다.

**전용 검토 프로필이 있으면 우선한다.** 없으면 「프로필 선택과 값 이관」의 역할↔프로필 해석으로 고른다. 검토 노드 기동 직전에 필요한 내용이 현재 컨텍스트에 없으면 [assets/review-briefing.md](../assets/review-briefing.md)를 읽어 `initialPrompt`로 넘긴다.
팀장 직접 수정 검토는 작업을 마친 뒤 검토를 열 때 [references/level2.md](level2.md)의 「팀장 직접 수정 검토」를 읽는다.

### 결과 파일로 받는다

결과는 완료 알림 본문이 아니라 파일로 받는다. 알림은 결론·수행 범위·핵심 실행 증빙·근거·제약·결과 경로를 짧게 적고 해당하지 않는 항목은 생략하되 **출력 제한 때문에 사용자 요구 데이터나 합격 근거를 빼지 않는다.** 긴 텍스트는 결과 파일에 부분과 위치를 보존한다. 파일 수정 자체가 결과면 별도 성공 보고 파일은 만들지 않는다.

실행 디렉터리는 `.skywork/paseo-orchestration/{날짜}-{슬러그}/`다. 날짜는 실행일의 `YYYY-MM-DD`, 슬러그는 실행 전용이며 경로가 이미 있으면 바꾼다. 조사·분석·판정·검토 결과는 노드별 `nodes/{노드 ID}.md`, 실패 보고는 **서로 다른** `nodes/{노드 ID}.failure.md`다. 앞 라운드 파일은 보존하고, 2라운드 이후 경로는 [references/level2.md](level2.md)의 「두 예산 — 사용자 왕복과 검토 라운드」를 따른다. 단계 산출물 `SPEC.md`·`SPIKE.md`·`MILESTONES.md`·`MILESTONE{NN}-Tasks.md`는 실행 디렉터리 바로 아래에 두며 `{NN}`은 마일스톤 번호다. 단계의 실패 보고도 노드 실패 경로에 둔다. 상세는 레벨 2 참조의 「설계」를 따른다.

경로는 네가 정해 브리핑에 명시하고 스킬 소스에 사용자 고정 경로를 넣지 않는다. 실행 중에는 선택한 workspace 기준 상대 경로를 쓰고 worktree 간 전달이나 호스트가 요구할 때는 조회로 확인한 실제 절대 경로를 전달한다. 이 디렉터리의 `GRAPH.md`가 레벨 1·2 공용 실행 기록이다.

파일 수정 작업에도 **실패 보고 경로를 지정한다.** 성공하면 실패 파일이 생기지 않고, 파일이 있으면 그것이 실패다. 실패 보고를 결과 파일보다 앞세운다. **수정 대상 파일에 실패 사유를 쓰게 하지 않는다.** 기록 불가·쓰기 금지면 워커의 짧은 실패·미검증 응답을 실패 보고로 본다. **결과 파일 본문을 네 컨텍스트로 옮기지 않는다.** 필요하면 알림 요약 뒤 해당 범위만 읽는다.

## 실행 중 개입과 실패

실패 분류·재시도·셸 실패·프로바이더 장애·재개가 발생하면 [references/failure-handling.md](failure-handling.md)의 필요한 절을 읽는다.

### 주입 — 승인이 필요한 것과 아닌 것

실행 중 지시는 `send_agent_prompt`, 워커 폐기는 `cancel_agent`를 쓴다. 호스트가 메시지·모드 변경을 막으면 우회하지 않고 보고한다.

| 종류 | 예 | 승인 |
| --- | --- | --- |
| **조회형** | 진행 질의, 결과 파일 경로 확인 | 불필요 |
| **범위 내 명확화** | 결과 경로·출력 형식 재지시, 기존 결과 파일 덮어쓰기/이어 쓰기/버리기 | 불필요 |
| **범위 변경** | 합격 기준 변경·추가, 대상 파일 추가, 역할 변경, 되돌리기 어려운 행동 추가, 권한을 올리는 모드 변경 | **보내기 전에 필수** |

애매하면 범위 변경으로 본다. 사후 통지는 승인이 아니다. 이미 받은 계획·되돌리기·권한 승인은 같은 범위에서 재사용한다. 범위 변경 승인 뒤 지시를 보냈으면 `python3 scripts/graph_update.py set`으로 해당 `GRAPH.md` 행을 갱신한다.

### 실패

워커 실패는 참조의 재시도 분류를 따른다. 브리핑 결함·명시 거부는 재시도하지 않고 원인을 보고하며 모드를 올려 우회하지 않는다. 권한 대기는 승인 범위 안이면 재사용하고, 아니면 요청 원문을 보여주고 사용자 판단을 받는다. 사용자 중단이면 실행 중 전원을 중단하고 상태·남은 경로를 보고한다. 부분 실패는 작업별 완료/실패/미기동, 완료 결과 경로와 미완료 범위를 보고한다.

자동 재시도는 부수효과 없음·멱등 두 조건을 모두 만족할 때 1회만 한다. 재기동 **전에** 사용 횟수를 기록하고 생성 결과가 불명이면 조회부터 한다. 재시도 셀에는 한도·사용 횟수를 적는다. 셸 실패를 `full-access`로 자동 승격하지 않는다. 호스트가 허용하고 기존 또는 새 승인이 있을 때만 모드를 바꾸며, 프로바이더 장애도 자동 대체하지 않는다.

## 취합과 보고

기동 시점 출력은 SKILL.md 「기동 보고」를 따른다.

전원 판정 뒤 팀장이 최종 취합한다. 여러 결과 파일의 새 비교·분석 파일은 워커에 맡길 수 있다. 완료 보고 직전에 필요한 내용이 현재 컨텍스트에 없으면 [references/FORM.md](FORM.md)의 `## 완료 보고`를 읽는다. `paseo run`으로 기동한 노드는 확인값과 요청값의 차이·확인 실패를 완료 보고에도 밝힌다.

### 결과 인수

팀장은 종료 요약의 수행 범위·핵심 근거·종료 코드·누락·미검증을 **원본 합격 기준과 대조**해 인수한다. 근거 없이 완료로 인정하지 않는다. 원문 전체 재독·검색·명령 전면 재수행을 기본으로 하지 않고, 근거 불일치·필수 데이터 누락·중요 결함 의심 때만 범위를 특정해 확인한다. **이미 낸 증빙의 필요한 부분을 확인하는 것은 결과 인수다.**

후속은 팀장의 결과 인수(새 워커 없음), 원래 역할 워커의 범위 내 보완(같은 노드 재작업과 순차 후속 노드 구분), 역할 변경(「프로필 선택과 값 이관」의 프로필 해석, 실제 `notes`가 허용하는 스펙 판정은 같은 워커), 별도 워커의 독립 검토(원본 요구·개발 워크플로우·승인 그래프·팀장 직접 수정이 요구할 때)를 구분한다. 순차 후속 재사용은 [references/level2.md](level2.md)의 「순차 후속 노드의 워커 재사용」을 따르고 서로 다른 검토 노드에는 적용하지 않는다. 재사용은 기동 보고 없이 완료 보고에 노드와 `agentId`를 남긴다. SKILL.md 「독립 검토 판단」의 세 요건을 지킨다.
