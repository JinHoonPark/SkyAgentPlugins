# 레벨 2 — 그래프 실행

2절에서 레벨 2로 떨어진 요청만 이 문서로 온다. 새 스케줄러나 실행 엔진을 만들지 않는다.
기동은 `create_agent`, 순서는 완료 알림과 아래 절차다. 값 이관은 4절, 브리핑은 5절,
주입·실패 게이트는 6절이다.

그래프 형태(팬아웃·팬인·순차·토론)를 고를 때는
[references/graph-patterns.md](graph-patterns.md)를 읽는다.
실패·재시도·재개·프로바이더 장애의 동작은 그때
[references/failure-handling.md](failure-handling.md)를 읽는다.

여기서 링크 표시에 적은 `references/graph-patterns.md`, `references/failure-handling.md`,
`references/FORM.md`는 모두 **스킬 디렉터리 기준** 경로다. 아래 본문의 링크 표시도 같다.

같은 요청의 중단·압축 복구면 아래 「재개」로 간다. 새 요청이면 앞선 그래프를 재사용하지
않고 다시 설계한다.

## 설계

노드 ID는 `N1`, `N2`, `N3`처럼 쓴다. `노드1`은 쓰지 않는다.

그래프 모양은 `flowchart TD` mermaid다. 방향은 위에서 아래다. 같은 스테이지의 병렬
노드는 같은 앞 노드에서 갈라 나오게 그린다. `subgraph`로 뎁스를 묶지 않는다 — 의존은
노드끼리 화살표로 그린다. 라벨은 `N1["..."]`로 따옴표로 감싼다. 노드 도형은 이 직사각형
하나만 쓴다 — 새 도형이나 `style`·`click`을 추가하지 않는다.

라벨은 노드 종류에 따라 줄 수가 다르다. **워커 노드**는 세 줄이다 — 첫 줄
`[ 노드ID · 역할 ]`, 둘째 줄 모델명, 셋째 줄 작업 한 마디. **공동 판정·사용자 게이트 같은
제어 노드**는 두 줄이다 — 첫 줄 `[ 노드ID · 종류 ]`, 둘째 줄 판단 대상 또는 확정 대상.
어느 쪽이든 첫 줄은 대괄호로 감싸고 안쪽에 공백을 한 칸씩 둔다. 제어 노드는 워커가
아니므로 모델명과 `agentId`를 만들지 않는다 — 가짜 모델명이나 가짜 `agentId`를 넣지 않는다.
줄 구분은 `<br/>`다. mermaid 코드펜스 맨 위에 아래 프론트매터를 **필수**로 넣는다 —
없으면 긴 프로필 이름이 재줄바꿈돼 행 구성이 깨진다.

```text
---
config:
  flowchart:
    wrappingWidth: 500
---
```

모델명은 `provider`를 뺀 값이고 thinking은 넣지 않는다. 나머지 속성은 아래 노드 표에만
둔다. 상태를 라벨에 넣지 않는다 — 표 갱신이 다이어그램 문자열 수정이 되어 문법이 깨진다.
계획 승인과 `GRAPH.md` 기록 모두 이 형식이다.

관계선은 한 줄에 하나씩 쓴다. 전달물·조건·반복 한도는 노드 설명이 아니라 관계선 라벨에
둔다. 되돌아가는 엣지는 `피드백:`으로 시작한다.

```text
N1 -->|통과| N2
N2 -->|확정| N3
N3 -->|필요| N4
N3 -->|생략| N5
N6 -->|피드백: 수정 필요, 잔여 2회| N1
```

라벨 엣지와 제어 노드 표기는 그래프 패널 렌더가 확인된 뒤에 실제 `GRAPH.md`와 승인 화면에
쓴다. 확인 전에는 규칙과 견본만 저장소에 둔다.

승인 대상은 mermaid와 되돌리기 경고다 — 이 승인 화면은 레벨 2 한정이고 레벨 1에는 없다
(`references/level1.md`의 「레벨 1의 `GRAPH.md` 기록」). 노드 표는 `GRAPH.md`에만 쓴다.

| 필드 | 내용 |
| --- | --- |
| 노드 ID | `N1`, `N2`, `N3` … |
| 종류 | `워커` / `공동 판정` / `사용자 게이트` 중 하나. mermaid 라벨의 줄 수도 이 종류를 따른다 |
| 프로필 | 역할과 그 역할에 실제 선택된 프로필 이름, 선택 근거 한 마디 |
| 입력 | 앞 노드 결과 파일 **경로** (스테이지 1은 리더 브리핑) |
| 결과 파일 | 성공 결과 경로 + 실패 보고 경로 — 워커 브리핑(5절)에 준 경로와 같아야 한다. **단계 산출물은 예외**로 실행 디렉터리 바로 아래 `SPEC.md`, `MILESTONES.md`, `MILESTONE{NN}-Tasks.md`에 쓰고, `{NN}`은 마일스톤 번호이지 노드 번호가 아니다 — 브리핑·이 표·뒤 노드 입력·재개 대조가 모두 이 실제 경로를 쓴다. 게이트 행에는 확정 대상 산출물 경로를 쓴다 |
| 합격 기준 | 팀장이 워커의 보고가 아니라 결과물을 직접 확인해 판정할 수 있는 한 줄이며, 결과 파일·실패 보고 파일의 존재·부재만으로 끝내지 않고 요청된 결과가 실제로 만들어졌는지를 담는다 |
| 진행 조건 | 다음 단계로 넘어가는 근거 — 선택된 분기, 검토 판정, 확정 근거 |
| 워크스페이스 | 공유(local) 또는 격리(worktree) |
| 되돌리기 | 예/아니오. 예면 그 노드 기동 직전 추가 승인(2절 Step 0) |
| 재시도 | `불가` 또는 `가능 · 한도 1 · 사용 0`. 열을 늘리지 않는다. 한도와 사용 횟수는 이 셀에 적는다. 기동 재시도도 이 셀에 쓴다 |
| 검토 라운드 | `상한 3 · 사용 N` — 검토를 시작하기 전에 상한과 사용 횟수를 적는다. 총 3라운드는 최초 검토 1회와 재검토 최대 2회다 |
| 게이트 | 그 단계의 사용자 확정을 기록한다 — **확정 대상 경로**, **검토 노드 ID**, **검토 시점 내용 해시**. 확정은 그 경로의 검토된 내용에만 유효하다 |
| 상태 | `대기` / `실행 중` / `완료` / `실패` / `생략`. 이 다섯 개만 쓴다. `생략`은 판정이 생략인 단계로, 워커를 만들지 않고 `create_agent` 대상이 아니다. 사용자 응답 대기는 게이트 행의 `대기` 상태와 `진행 조건`으로 나타내고, 확정되면 `완료`로 바꾼다 |
| agentId | 각 `create_agent` 호출 결과를 받는 즉시 그 노드 행에 채운다 |

- 같은 파일을 쓰는 노드는 격리하지 말고 그래프를 고쳐 순차로 둔다.
- 기본 워크스페이스는 1절에서 고른 공유 workspace다. worktree는 사용자가 명시할 때만.
- 토론 라운드는 기본 총 3라운드다. 연장은 횟수와 대상을 지정한 **사용자 결정**으로만 한다.
  설계 때 라운드를 스테이지로 드러나게 지정한다.
- 한 스테이지 노드 수가 10을 넘으면 3절 큐를 그 스테이지 안에서 그대로 쓴다. 다만 `GRAPH.md`
  기록 갱신은 3절이 아니라 아래 「기록 시점」을 따른다.
- 게이트 행의 해시는 확정 시점에 검토된 내용을 가리킨다. 그 경로의 파일 내용이 바뀌면 그 확정과
  이를 전제로 한 **미기동** 단계만 보류한다. 이미 기동한 단계는 되돌리지 않는다.
- 확정과 해시 이력은 `GRAPH.md`의 게이트 행에만 남긴다. 별도 버전 이력 문서를 만들지 않는다.

### 공동 판정과 판정안

스파이크 필요성과 마일스톤 필요성은 **공동 판정**이다. 담당 전문 역할 워커가 판정안을 내고,
팀장이 세션 맥락·사용자 확정 사항과 대조해 공동 결론을 낸다. `팀장 단독` 판정은 금지한다.
「생략」도 정상 산출물이며 실패가 아니다.

- 스파이크 설계 역할의 판정안은 실패하면 무엇이 성립하지 않는지, 현재 근거, 확인할 질문,
  필요·생략·정보 부족을 담는다.
- 마일스톤 역할의 판정안은 독립적으로 확인 가능한 중간 결과, 실제 순서 의존,
  필요·생략·정보 부족을 담는다. 파일 수·워커 수만으로 판정하지 않는다.

팀장은 판정안의 결론 한 줄과 핵심 쟁점만 읽고 대조한다. 불일치하면 그 차이만 전문 역할에
되묻는다. 합의가 서기 전에는 분기를 고르지 않고, 사업·제품 선택이 남으면 사용자에게 올린다.

전문 역할 워커는 종료 요약에 판정(필요·생략·정보 부족)과 핵심 쟁점 한 줄만 남기고, 상세
근거는 결과 파일에 둔다. 팀장은 그 본문을 옮기지 않는다.

### 스펙 문답

스펙 작성 워커가 결정이 필요한 질문을 만들고 팀장이 의미를 바꾸지 않고 사용자에게 중계하며,
사용자 답변은 그 질문과 묶어 원문으로 같은 작성 워커에게 전달한다.

- 한 번에 서로 독립된 결정 하나만 묻고, 답에 따라 결과·범위·수용 판정이 달라지는 미결정
  지점만 대상으로 한다. 주어진 근거로 답할 수 있는 것은 묻지 않는다.
- 중계하는 것은 질문과 답변뿐이고, 스펙 본문과 작성자의 분석 과정은 옮기지 않는다.
- 사용자가 확정할 때까지 왕복 횟수에 상한을 두지 않는다. 검토 라운드 예산과는 별개다.

### 마일스톤 생략과 스펙 변경

마일스톤을 생략하면 마일스톤 역할과 팀장이 단일 마일스톤 번호를 확정하고 `MILESTONES.md` 작성만
생략한다. 태스크 파일은 `MILESTONE{NN}-Tasks.md`의 `{NN}`에 그 확정 번호를 쓴다. 태스크 분해
역할은 확정된 스펙을 직접 입력으로 받을 수 있다.

사용자 피드백으로 스펙이 바뀌면 승인된 내용만 반영하고, 영향을 받는 하위 단계만 다시 검토한다.

## 계획 승인

워커를 하나라도 띄우기 **전에** 계획 승인을 **1회** 받는다. 읽기·조사만인 다단 그래프도
같다. 개별 노드 기동에 추가 계획 승인은 없다.

현재 대화에서 작업 범위·역할·실행 순서가 명시적으로 승인됐고 실행안이 그 내용과 같으면,
진행한다. 승인되지 않은 결정이나 승인 내용과 달라진 부분만
확인한다. 앞선 제안을 특정하는 "작업 시작해"는 그 제안의 승인이다. 다만 모호한 지시를
전체 계획 승인으로 확대하지 않는다.

그 승인이 아직 없으면 목적 → mermaid → 되돌리기 경고 → 기록 경로 순으로 **일반
응답으로 출력하고 턴을 마쳐** 사용자 답변을 기다린다. 이 순서는 고정이다. 승인 화면을
출력하기 직전에 [references/FORM.md](FORM.md)의 `## 승인 화면`을 읽는다. mermaid
전체 검토가 필요하므로 이 승인 요청은 질문 도구의 짧은 선택지로 대체하지 않는다.
무응답·주제 전환은 승인이 아니다. 승인 전에 `create_agent`를 호출하지 않는다.

목적 줄은 mermaid 밖에 `### 목적 — {한 문장}`으로 둔다. mermaid 안에 넣으면 스타일을
못 준다. 되돌리기 어려운 노드가 있으면
`⚠️ [ **노드ID** ] 되돌리기 어려움 — 기동 전 별도 승인`을 올리고, 없으면 경고 줄을
출력하지 않는다. 재시도·워크스페이스 등 다른 예외는 올리지 않는다.
`입력`·`결과 파일`·`합격 기준`·`재시도`는 승인 화면에 출력하지 않는다. 기록 경로는
`기록 : ` 뒤에 `GRAPH.md` 경로다.

형태가 바뀌는 재설계·범위 변경 주입·프로바이더 대체는 다시 승인받는다.

## GRAPH.md

레벨 2는 항상 만든다 — 레벨 1도 같다(`references/level1.md`의 「레벨 1의 `GRAPH.md` 기록」). 생성 자체는 승인
대상이 아니고, 레벨 2는 승인 요청에 **기록 파일을 쓸 것과 그 경로를** 알린다. 레벨 1은
승인 요청이 없으므로 기동 보고(7절)에서 그 경로를 알린다.

경로: 5절에서 정한 실행 디렉터리의 `GRAPH.md`
결과 파일 규칙은 5절과 같다.

`GRAPH.md`는 mermaid 1개와 노드 표 1개만 둔다 — 갱신은 그 블록을 고치는 것이고 새 갱신본을
뒤에 덧붙이는 것이 아니다. 노드 추가·승인된 구조 변경은 mermaid와 표에 함께 반영한다.

실행 기록을 쓰기 직전에 [references/FORM.md](FORM.md)의 `## 실행 기록`을 읽는다.

기록 시점:

1. 계획이 확정된 실행은 **`create_agent` 호출 전에** mermaid 블록과 노드 행을 먼저 쓴다.
   합격 기준·결과 파일·실패 보고 경로·재시도 한도·검토 라운드 상한과 사용 횟수는 표에
   그대로 둔다. 각 호출 결과를 받는 **즉시** 그 노드 행의 `agentId`를 채운다.
2. 공동 판정·사용자 게이트·분기 결정 때에도 표를 갱신한다. 변하는 상태 문자열은 표에만
   두고 mermaid에는 넣지 않는다.
3. 노드 판정은 확인 즉시 그 행의 상태에 반영한다. 스테이지 경계는 다음 단계를 기동할지
   판단하는 시점이다. 사용자가 실행을 중단할 때 그 시점 상태로 즉시 갱신한다.
4. 재시도 잔여 횟수는 재시도가 실제로 발생할 때 기록한다.
5. 승인된 주입이 노드 행을 바꾸면 그때도 갱신한다.

## 실행

### 단계 전이

한 단계는 아래 순서대로 간다.

1. 작성 워커가 그 단계의 대상 산출물을 **작성 완료**한다.
2. **독립 검토** 노드를 기동해 그 산출물을 검토한다.
3. 수정이 필요하면 검토가 지적한 **경로를 그대로** 작성 워커에게 전달한다.
4. 작성 워커가 수정하고 **같은 절차로 재검토**한다.
5. 검토를 **통과**하면 사용자 확정을 기다린다. 검토 통과만으로 사용자 게이트는 완료되지
   않는다.
6. 사용자가 **명시적으로 확정한 뒤에** 다음 단계를 **기동**한다.

검토 예산은 총 3회다. 검토 라운드의 기본값과 검토 실패의 세 갈래는
[references/failure-handling.md](failure-handling.md)에 있으므로 이 파일에 반복하지 않는다.

- 사용자 피드백은 같은 단계의 수정이며, 사용자가 확정할 때까지 왕복 횟수 상한을 두지 않는다.
  총 3회는 작업 워커와 검토 워커 사이의 검토 라운드에만 적용한다. 검토 뒤의 사용자 수정 왕복과
  답변을 기다리는 시간은 이 예산을 소비하지 않는다. 새 요구사항이 생겨도 예산을 자동으로
  초기화하지 않고, 범위와 추가 횟수는 사용자가 정한다.
- 검토 라운드마다 별도 노드 ID와 별도의 결과·실패 보고 경로를 쓴다. 앞 라운드의 파일을
  덮어쓰거나 지우지 않으며, 다음 검토가 앞 검토의 결과 경로를 참조할 수 있다.
- 계획 승인 1회는 실행 구조의 승인일 뿐 미작성 산출물 내용의 확정이 아니다. 승인된 분기와
  라운드 범위 안의 전이는 재설계가 아니다. 새 단계·새 범위·상한 연장만 새 승인 대상이다.

### 기동과 판정

1. **기동 전에** 5절의 결과 파일·실패 보고 경로 분리를 확인한다 — 같으면 분리하기 전까지
   기동하지 않는다. 승인된 한 스테이지의 `대기` 노드를 기동한다. 상한 10 + FIFO는 3절과
   같다.
2. 완료 알림 대기는 3절과 같다.
3. **종료와 합격 기준 통과를 나누어 판정한다.** 실패 보고 경로에 내용이 있으면 `실패`다.
   그다음에야 결과 파일과 합격 기준을 대조한다. 에이전트가 멈춘 것만으로 `완료`가 아니다.
4. **선택된 경로의 활성 노드가 통과하고 필요한 사용자 게이트가 확정되면 진행한다.**
   `생략`은 차단 원인이 아니다. 하나라도 `실패`면 그 노드에 의존하는 노드는 기동하지 않는다.
5. 뒤 노드 브리핑에는 앞 노드 결과 파일의 **경로만** 넣는다. 본문을 붙이지 않는다. 단계
   산출물이면 `SPEC.md`·`MILESTONES.md`·`MILESTONE{NN}-Tasks.md`의 실제 경로를 넣는다.
6. 검토 노드는 5절이다.
7. 실행 중 `agentId`가 있으면 그 ID로 상태를 조회한다. 살아 있거나 이미 끝난 노드를
   완료 재기동하지 않는다. 생성 결과가 불명이면 조회부터 하고 중복 기동하지 않는다.
8. 주입과 실패 게이트는 6절이다. 범위 변경·재설계는 보내기 전에 승인을 받는다. 호스트가
   실행 중 메시지를 막으면 보내지 않고 보고한다.

### patch 왕복

**최초 작성 라운드는 예외**다 — 기준 파일이 없으므로 작성 워커가 산출물을 직접 쓴다.
2라운드부터 작성 워커는 대상 산출물을 직접 고치지 않고, 같은 실행 디렉터리에
`{산출물 이름}.round{N}.patch` **하나**를 낸다. `N`은 라운드 번호다.

- 팀장은 `git apply`로 그 patch를 **본문을 읽지 않고** 기계적으로 적용한다. 실행 디렉터리가
  git 추적 대상이 아니어도 `git apply`는 작업 트리 파일에 동작하므로, 추적 여부를 이 규칙의
  우회로 쓰지 않는다.
- 깨끗하게 적용되지 않으면 그 라운드는 실패한다. 이 실패는 검토 라운드가 아니라
  **기동 재시도 예산**을 소비한다.
- 이전 판본 사본을 만들지 않는다 — 라운드마다 남는 파일이 곧 그 라운드의 판본이다.

## 재개

중단·압축 복구는 레벨 1·2가 **같은 절차**를 쓴다 — 레벨 1의 서술은 `references/level1.md`의 「레벨 1 재개」이고
동작이 이 문서와 같다. 다른 점은 레벨 1에 재사용할 계획 승인이 없다는 것뿐이다.

`list_agents`로 자식 에이전트를 조회하고(`labels`의 `paseo.parent-agent-id`), `GRAPH.md`가
있으면 읽는다. 절차와 재시도·재수행의 상세는
[references/failure-handling.md](failure-handling.md)의 「재개」에 있으므로 이 파일에
반복하지 않는다.

앞 그래프를 이어 가려면 **선택된 분기·잔여 검토 라운드·확정 대상**이 모두 앞 시도와 같아야
한다. 셋 중 하나라도 다르면 앞 그래프를 이어 가지 않고 다시 설계한다.

판정은 **현재 시도만** 본다. `GRAPH.md` 결과 칸이 가리키는 **현재 시도의 결과 파일과 실패 보고
경로** 두 개가 유일한 근거다. 현재 결과가 합격 기준을 충족하고 현재 실패 보고가 비어 있으면
`완료`다. **앞 시도에 남은 실패 보고 파일은 판정 근거가 아니며**, 그것을 이유로 그 노드를 다시
띄우지 않는다.

실행 중인 노드는 다시 띄우지 않고, `대기`는 기동한다. 그래프 형태가 그대로면 이미 받은 계획
승인을 재사용한다.
