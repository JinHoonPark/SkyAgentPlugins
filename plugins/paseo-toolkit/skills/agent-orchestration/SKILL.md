# Agent Orchestration

작업 지시를 받으면 리더인 너는 직접 착수하지 않는다. 작업을 워커에 맡기고, 결과를 취합해
사용자에게 보고하는 것이 이 스킬의 절차다. 작은 일도 그에 맞는 싼 모델로 내리는 것이 이
라우팅의 목적이므로 크기로 예외를 두지 않는다.

절차는 순서대로 1절부터 7절까지다. 레벨 2로 떨어지면 9절로 간다. 8절은 사용자가
상시 라우팅을 요청했을 때만 읽는다.

## 리더가 직접 하는 일

워커가 원리적으로 못 하는 셋만 직접 한다.

1. 이 세션의 대화 맥락 자체를 근거로 삼아야 하는 일
2. 사용자와의 확인 문답
3. 워커 결과 취합과 사용자 보고

파일과 설정은 대상이 이 세션 것이어도 워커가 다룰 수 있다. 워커에 맡긴다. 예외로 사용자가
"이 세션에서 직접 하라"고 지시하면 그 요청은 직접 한다.

`Agent` 도구·`Workflow`·deep-research는 쓰지 않는다 — 프로필을 실을 수 없기 때문이다.
단 스킬이 그 도구들을 쓰라고 지시하면 그 스킬을 따른다.

## 1. 전제 점검

### 도구를 부를 수 있는 상태로 만든다

claude에서 Paseo 도구는 deferred다. 스키마를 먼저 로드해야 호출할 수 있다.

```text
ToolSearch select:mcp__paseo__list_profiles,mcp__paseo__create_agent,mcp__paseo__list_workspaces,mcp__paseo__send_agent_prompt,mcp__paseo__get_agent_status,mcp__paseo__list_agents,mcp__paseo__cancel_agent
```

필요한 도구가 늘면 같은 형식으로 이어 붙인다. **이 호스트에 `ToolSearch`가 있으면** 그
줄로 스키마를 먼저 로드한다. 없으면 이미 노출된 도구 목록과 현재 검색 수단으로 같은
이름을 확인한다. Codex라고 해서 `ToolSearch`가 없다고 단정하거나 특정 모드를 강제하지
않는다. 이후 절차의 도구 이름(`list_profiles`, `create_agent`, `list_workspaces`,
`send_agent_prompt`, `get_agent_status`, `list_agents`, `cancel_agent`)은 접두어 없이 쓴다.

Paseo 도구가 이 세션에 붙어 있지 않으면 연결이 불충족이다. 그 사실을 명확히 보고하고
사용자 전역 config를 스스로 고치지 않는다. 프로필 조회는 `list_profiles` 하나뿐이고
대응하는 CLI 명령이 없다. provider를 추측하지 않는다. (`daemon.mcp.injectIntoAgents`가
활성이어야 새 세션에 Paseo 도구가 주입된다. 없으면 기본은 false다. 연결이 실패하면 이미
승인된 범위 안에서 복구하고, 복구할 수 없으면 필요한 설정 변경을 구체적으로 제시해 사용자
판단을 받는다.) 사용자 판단을 받은 뒤에만 `paseo run`의 `--provider`·`--mode`·`--thinking`으로
기동한다. 기동 후 응답·`inspect`의 `thinking`/`currentModeId` 값을 요청값과 대조해 적용
여부를 확인하고, 확인됐는지 못 했는지를 기동 보고(7절)에 적는다.

### 프로필 목록을 읽는다

`list_profiles`로 모든 프로필의 `notes`를 읽고 `notes`가 맞는 프로필을 고른다. 선택 기준은
`notes`에 있으므로 추측하지 않는다. 같은 세션에서 이미 읽었으면 다시 호출하지 않는다.

| 상태 | 판별 | 처리 |
| --- | --- | --- |
| **A. 목록이 비었다** | `list_profiles`가 빈 목록 | provider를 추측하지 않는다. 프로필이 없다고 알리고, 진행을 원하면 `list_providers`·`list_models`로 고른 뒤 그 사실을 보고에 남긴다 |
| **B. 맞는 것이 없다** | 어느 `notes`도 이 작업 유형을 포함하지 않는다 | 어느 프로필도 억지로 고르지 않는다. provider를 추측하지 않는다. 어떤 유형을 찾았고 어느 `notes`도 걸리지 않았는지 한 줄로 알린 뒤 `list_providers`·`list_models`로 고르고 그 사실을 보고에 남긴다 |
| **C. 부분적으로만 맞는다** | `notes`가 인접하지만 경계 문구가 이 작업을 배제한다 | 허용되는 부분만 분리해 배정하고, 나머지는 적합 프로필 없음으로 처리한다(B). 통지로 경계를 넓히지 않는다. provider를 추측하지 않는다. 벗어나는 부분이 작업의 본체이면 B로 취급한다 |

### 워크스페이스를 고른다

`list_workspaces`로 조회해 `cwd`가 대상 저장소인 워크스페이스를 고르고, 그 `workspaceId`를
`create_agent`에 **명시한다.** 생략하면 새 워크스페이스가 만들어진다. 워크스페이스 ID를
하드코딩하지 않고 매번 조회한다.

결과 파일을 서로 읽어야 하는 작업들은 같은 워크스페이스에 둔다. 격리하면 뒤 작업이 앞
작업의 파일을 볼 수 없다. 같은 파일을 여럿이 써야 하는 요청은 2절 Step 3에서 레벨 2로
떨어지므로 격리로 우회하지 않는다 — 격리는 병합 문제를 새로 만든다. worktree 격리는 사용자가
명시할 때만 쓰고, 그때는 각 worktree 경로를 받아 그 경로를 읽어야 하는 워커의 브리핑에 넣는다.

이 호스트에서 쓸 수 있는 완료 알림·대기 수단을 확인하고, 없으면 종료 확인에
`get_agent_status`·`list_agents`의 제한된 상태 조회를 허용한다.

## 2. 레벨 판정 게이트

대상·역할·공통 입력을 기준으로 작업을 서로 겹치지 않는 단위로 먼저 쪼갠다. 단위 하나 =
워커 하나. 맥락이 다른 일은 나눈다 — 한 세션에 여러 맥락을 몰지 않는다. 워커를 하나라도
띄우기 전에, 그 단위들 사이의 의존을 이 절의 트리로 판정한다.

여러 작업에 같은 내용이 필요하면, 그것이 이미 확정된 공통 입력인지 먼저 확인한다.
확정됐으면 리더가 같은 내용을 각 워커에 넘겨 독립 노드로 둔다. 확정되지 않았으면 작성
노드 → 사용 노드의 다단이다. 리더가 독립성을 만들려고 그 내용을 직접 창작하면 「리더가
직접 하는 일」의 제한과 충돌한다. 그 경우는 다단으로 간다.

대상 파일이 다르다는 사실만으로 무조건 분리하지는 않되, 공통 입력이 있다는 이유로 한
워커에 합치지도 않는다.

**순서가 있는 판정 트리다. 위에서부터 내려가 처음 걸리는 곳에서 멈춘다.** **워커 수는 어느
단계에도 나오지 않는다.**

```text
Step 0 (레벨과 직교, 항상 수행)
  되돌리기 점검 → 걸리면 그 작업에 별도 게이트를 단다. 레벨은 바꾸지 않는다.

Step 1  어떤 작업의 입력이 다른 작업의 출력인가?            예 → 레벨 2 (멈춤)
Step 2  같은 대상에 서로 다른 역할이 배정되는가?            예 → 레벨 2 (멈춤)
          (구현과 검토, 토론자와 사회자, 작성과 감수)
Step 3  둘 이상의 작업이 같은 파일을 쓰는가?                예 → 레벨 2 (멈춤)
Step 4  어떤 작업의 합격 기준 판정이 다른 작업의 결과에      예 → 레벨 2 (멈춤)
        걸려 있는가?
Step 5  Step 1~4 중 하나라도 "모르겠다"인가?                예 → 레벨 2 (멈춤)
Step 6  그 밖의 전부                                       → 레벨 1
```

쪼갠 결과 다른 작업이 없어도 트리를 건너뛰지 않는다. Step 6에서 레벨 1이 된다.

### 레벨 2로 떨어지면 9절로 간다

Step 1~5 중 하나에 걸리면 **레벨 1로 처리하지 않는다.** 프로필 선택·기동 어느 것도
3절로 내려가지 않는다. 어느 Step에 무엇 때문에 걸렸는지 한 줄로 알리고 9절로 간다.
순서를 바꿔 순차로 돌리는 것으로 레벨 2가 레벨 1이 되지는 않는다.

### Step 0 — 되돌리기 어려운 작업

레벨과 직교하므로 **레벨 1 경로에서도, 워커가 하나뿐인 요청에서도 건너뛰지 않는다.**

범위는 넷이다 — git 커밋·푸시·태그·브랜치 삭제, 외부 전송, 파일·디렉터리 삭제, 저장소 밖
설정 변경.

- 걸리는 단위가 있으면 그 단위의 기동 **직전에** 승인을 받는다. 걸리지 않는 나머지 단위는
  승인을 기다리지 않고 기동한다.
- 사용자가 그 되돌리기 어려운 작업을 이미 명시적으로 지시했으면 그 지시가 곧 승인이다. 리더가 스스로
  추가한 되돌리기 어려운 행동은 언제나 승인 대상이다.
- git 커밋·스테이징·푸시·태그·브랜치 삭제는 사용자 명시 승인 없이 워커에 맡기지 않는다.
- 무응답·답변 누락·주제 전환·다른 작업 지시는 승인이 아니다.

## 3. 레벨 1 — 팬아웃

2절에서 레벨 1로 판정된 요청만 이 절로 온다. 레벨 1은 작업 사이에 의존이 없다는 전제 위에 선다.

1. 단위마다 프로필을 고른다(4절). 단위 성격이 같으면 같은 프로필을 써도 된다.
2. 되돌리기 어려운 단위를 점검한다(2절 Step 0).
3. 활성 큐를 채워 기동한다. 승인 문답은 하지 않는다(되돌리기 어려운 단위 제외).
4. 완료 대기는 1절에서 확인한 수단을 쓴다. 알림이 있으면 폴링하지 않는다. 종료마다 아래
   투입 절차를 돈다.
5. 전원 완료 후 취합해 7절 형식으로 보고한다.

작업 개수가 많다는 것 자체는 승인 사유가 아니다. 개수는 큐가 처리한다.

### 활성 큐와 대기 큐

| 개념 | 값·정의 |
| --- | --- |
| **활성 큐** | 지금 실행 중인 워커. 동시 실행 상한 10 |
| **대기 큐** | 아직 기동하지 않은 작업. 상한 없음. 순서는 네가 쪼갠 순서(FIFO) |

작업마다 이만큼을 들고 있는다 — 노드 ID(쪼갠 순서) / 상태(`대기`·`실행 중`·`완료`·`실패`) /
프로필 / 대상 / 결과 파일 경로 / agentId(기동 후) / 되돌리기(예·아니오) / 재시도 가능 여부(6절).

**큐 상태 파일을 만들지 않는다.** 큐는 네 컨텍스트에만 둔다.

투입 절차 — 1절에서 확인한 수단으로 종료를 기다린다. 종료 1건을 확인하면:

1. 종료를 확인한 뒤 실패 보고와 합격 기준을 대조해 판정한다 — 파일이 없다는 사실만으로
   성공을 판정하지 않는다(9절 실행 3). 활성 슬롯 1개가 빈다.
2. 대기 큐가 비어 있지 않으면 선두 1개를 기동하고 `실행 중`으로 바꾼다.
3. 알림이 여러 건 몰려 오면 **해제된 슬롯 수만큼** 투입한다. 상한을 넘겨 기동하지 않는다.
4. 대기 큐가 비고 활성 큐도 비면 취합·보고로 넘어간다.
5. 기동이 실패하면 그 작업은 활성 슬롯을 잡지 않은 것으로 보고 6절의 재시도 분류를 따른다.

### 의존을 뒤늦게 발견하면

대기 중 작업이 실패한 앞 작업의 결과 파일을 필요로 한다는 것이 드러나면, 그것은 실패 처리가
아니라 **레벨 판정이 틀렸다는 신호**다.

1. 남은 대기 큐의 투입을 멈춘다. 실행 중인 워커는 중단하지 않고 결과를 받는다.
2. 발견한 의존 관계를 명시해 알린다. "레벨 1로 판정했는데 작업 N이 작업 M의 결과 파일을 필요로
   한다"까지 적는다.
3. 남은 작업은 2절 Step 1에 걸린다 — 레벨 2로 재판정해 9절로 간다. 순차로 다시 배열해
   레벨 1로 이어 가지 않는다.
4. 이미 완료된 작업은 다시 기동하지 않는다. 그 결과 파일 경로를 새 그래프의 스테이지 1
   입력으로 재사용한다.

## 4. 프로필 선택과 값 이관

`create_agent`에는 `profile` 인수가 없다. **프로필의 값은 자동으로 적용되지 않으므로 네가
옮겨 담는다.** 이름이 서로 다르니 아래 대응을 그대로 따른다.

| 프로필의 값 | `create_agent`의 자리 |
| --- | --- |
| `provider` + `model` | `provider` — 두 값을 `provider/model` 한 문자열로 합쳐 넣는다 |
| `modeId` | `settings.modeId` |
| `thinkingOptionId` | `settings.thinkingOptionId` |
| `featureValues` | `settings.features` — **프로필에 이 키가 있을 때만** 옮긴다. 없으면 `settings.features`를 넣지 않는다 |

- `workspaceId`를 명시한다(1절).
- `title`은 `프로필이름: 한 줄 요약`, `labels`는 `{"profile": 프로필id, "task": 한 마디}`.
  `title`은 60자 상한이므로 그 안에서 만든다. 프로필 이름이 길어 요약 여유가 10자 미만이면
  `title`에 요약만 쓰고 프로필은 `labels.profile`로만 남긴다.
- `settings.modeId`는 스키마상 선택 필드지만 **채우는 것을 기본으로 둔다.** 프로필의 값을
  그대로 옮기는 것이 원칙이고, 채워서 나쁠 이유가 없다.
- 실제 모드·모델·thinking은 요청값이 아니라 기동 결과로 확인한다. 모드는 `create_agent`
  응답의 `currentModeId`를 요청값과 대조한다. 모델과 thinking은 `snapshot.model`·
  `snapshot.effectiveThinkingOptionId`로 확인한다. `runtimeInfo`는 쓰지 않는다 — claude
  워커는 기동 직후 그 안의 `model`이 null이다. 노드 1~2개면 `create_agent` 직후
  `get_agent_status` 1회, 팬아웃이면 전체 기동 후 `list_agents` 1회로 한꺼번에 대조한다.
  호출 수가 노드 수에 비례하지 않게 한다. 보고의 "모드"·"모델" 줄에는 확인한 값을 쓰고,
  요청값과 다르면 출처를 적는다(7절).
- claude의 `plan` 모드는 파일 산출을 막는다. 결과 파일을 써야 하는 단위에 고르지 않는다.

## 5. 워커 브리핑

워커 제약을 매 단위마다 실을 수 있는 자리는 `initialPrompt` 하나다. 그래서 워커 규칙 전부가
여기 들어간다.

`assets/worker-briefing.md`가 그 템플릿이다. **워커를 띄우기 직전에 읽고** 중괄호 자리를 채워
`initialPrompt`로 넘긴다.

반드시 실어야 하는 것:

- **첫 줄 고정** — `너는 워커다. 프로필: {이름} — {그 프로필의 notes 원문}`. Paseo는 워커에게
  자기 프로필을 알려주지 않으므로 프롬프트에 써야 한다. `notes`의 경계 문구가 워커의 작업
  범위다.
- 작업 지시와 **원본 합격 기준**. 네가 요약한 것이 아니라 원본을 옮긴다.
- 결과 파일 경로와 실패 보고 경로(둘 다 네가 지정한다), 쓸 도구, 출력 크기 제한.
- 다시 위임하지 않는다. 셸은 기본 도구로 실행하고 터미널을 새로 만들지 않는다.
- 보고 형식(결론 / 근거 위치 `파일:줄` / 미검증 항목).
- 실패했으면 **실패 보고 경로**에 실패 사유를 쓰고 수정 대상 파일에는 쓰지 않는다. 네가 파일만
  보고 실패를 판정할 수 있어야 한다.

리더 절차(전제 점검, 큐 운영, 승인 게이트, 보고 형식)는 브리핑에 넣지 않는다. 워커가 쓸 일이
없는 맥락이고, 실으면 워커가 다시 위임하려 든다.

### 검토는 만든 워커에게 맡기지 않는다

결과 파일이 합격 기준을 충족하는지 판정하는 일을 그것을 만든 에이전트에게 맡기지 않는다. 구현자가 브리핑한 검토는
구현자의 전제를 물려받아 같은 오류를 통과시킨다.

- 검토는 **검토용 `notes`를 가진 프로필의 별도 워커**에 맡긴다. 구현 워커와 다른 프로필이다.
- 넘기는 것은 **원본 합격 기준과 대상 경로**다. 구현자의 보고서는 넘기지 않는다.
- 구현과 검토를 함께 요청받은 것은 2절 Step 2에 걸린다. 레벨 2이므로 9절로 간다. 검토
  노드를 띄우기 직전에 [assets/review-briefing.md](assets/review-briefing.md)를 읽고
  중괄호를 채워 `initialPrompt`로 넘긴다.

### 결과 파일로 받는다

완료 알림에 실리는 응답은 잘릴 수 있다. 그래서 결과는 알림 본문이 아니라 파일로 받는다.

- 조사·분석처럼 결과가 텍스트라면 실행 디렉터리를 정한다:
  `.skywork/paseo-orchestration/{날짜}-{슬러그}/`. 날짜는 실행일의 `YYYY-MM-DD`이고
  슬러그는 이번 실행 전용 값이다. 같은 경로가 이미 있으면 슬러그를 바꿔 새 디렉터리를
  고른다. 작업마다 결과 파일은 `nodes/{노드 ID}.md`, 실패 보고는
  `nodes/{노드 ID}.failure.md`에 쓰게 한다 — 반드시 서로 다른 파일이다. 경로는 네가
  정해 브리핑에 명시한다. 스킬 소스에 사용자의 고정 경로를 하드코딩하지 않는다 —
  실행 중에는 선택한 workspace 기준 상대 경로로 해석한다. worktree 간 전달이나 호스트가
  절대 경로를 요구할 때는 조회로 확인한 실제 절대 경로를 그대로 전달한다.
- 결과가 파일 수정 그 자체라면 성공했을 때 쓸 별도 결과 파일을 만들지 않는다. 그래도
  **실패 보고 경로는 지정한다** — 같은 실행 디렉터리의 `nodes/{노드 ID}.failure.md`다. 성공하면 그
  파일이 생기지 않고, 파일이 있으면 그것이 실패다.
- **수정 대상 파일에 실패 사유를 쓰게 하지 않는다.** 그 파일이 곧 결과 파일이므로 실패 기록을
  섞으면 결과 파일이 망가진다. 실패 사유는 언제나 실패 보고 경로로 간다.
- 파일 기록이 불가능하거나 사용자가 쓰기를 금지한 경우, 워커는 파일을 쓰지 않고 짧은
  응답으로 실패와 미검증을 보고한다. 그 응답을 실패 보고로 본다.
- **결과 파일 본문을 네 컨텍스트로 옮기지 않는다.** 리더 컨텍스트를 아끼는 것이 위임의 나머지
  절반이다. 판단이 필요할 때만 알림 요약을 읽고, 부족하면 결과 파일을 범위를 제한해 읽는다.

## 6. 실행 중 개입과 실패 처리

실패 분류·재시도 한도·셸 실패·프로바이더 장애·재개의 동작은 그때
[references/failure-handling.md](references/failure-handling.md)를 읽는다. 아래는 그 자리에서
빠지면 행동이 바뀌는 게이트다.

### 주입 — 승인이 필요한 것과 아닌 것

실행 중인 워커에 지시를 보내는 수단은 `send_agent_prompt`다. 그 워커를 폐기할 때만
`cancel_agent`를 쓴다. **이 호스트가 실행 중 메시지·모드 변경을 막으면 그 정책을 이 표보다
앞세운다.** 막히면 우회하지 않고 보고한다.

| 종류 | 예 | 승인 |
| --- | --- | --- |
| **조회형** | 진행 상황 질의, 지금까지 쓴 결과 파일 경로 확인 | 불필요 |
| **범위 내 명확화** | 결과 파일 경로 재지시, 출력 형식 지정, 이미 쓴 결과 파일의 처리 지시(덮어쓰기/이어 쓰기/버리기) | 불필요 |
| **범위 변경** | 합격 기준의 변경·추가, 대상 파일 추가, 역할 변경, 되돌리기 어려운 행동 추가, 권한을 올리는 모드 변경 | **필수 — 보내기 전에** |

승인 없이 보낸 뒤 사후에 알리면 게이트를 우회한 것이다. 애매하면 범위 변경으로 본다.
이미 받은 계획·되돌리기·권한 승인은 같은 범위에서 다시 묻지 않고 재사용한다. 레벨 2에서
범위 변경을 승인받으면 보낸 뒤 `GRAPH.md`의 해당 노드 행을 갱신한다(9절).

### 실패

| 상황 | 처리 |
| --- | --- |
| 워커 실패 | 참조의 재시도 분류를 따른다. 무조건 자동 재시도는 하지 않는다 |
| 브리핑 결함으로 실패 | 재시도하지 않고 원인과 함께 보고한다 |
| 권한 대기 | 기존 승인 범위 안이면 재사용해 응답한다. 없거나 범위를 넘으면 요청 원문을 그대로 보여주고 사용자 판단을 받는다 — 임의로 자동 승인하지 않는다 |
| 명시 거부 | 재시도하지 않는다. 모드를 올려 우회하지 않는다 |
| 사용자 중단 | 실행 중 전원을 중단하고 작업별 상태와 남은 결과 파일 경로를 보고한다 |
| 부분 실패 | 작업별 상태(완료/실패/미기동) + 완료된 결과 파일 경로 + 무엇을 못 했는지 |

자동 재시도는 참조의 두 조건(부수효과 없음 + 멱등)을 모두 만족할 때만, 1회만 한다. 호출
**전에** 사용 횟수를 기록한다. 생성 결과가 불명이면 재기동하지 않고 조회부터 한다. 실패
보고 경로에 내용이 있으면 그것을 완료보다 앞세운다. 레벨 2는 재시도 셀에 한도와 사용
횟수를 적는다(9절).

### codex 셸 · 프로바이더 장애

셸 실패를 `full-access`로 자동 승격하지 않는다. 호스트 정책이 허용하고, 그 권한이 이미
승인됐거나 새로 승인된 뒤에만 모드를 바꾼다. 프로바이더 장애는 자동 대체하지 않는다.
동작은 참조를 따른다.

## 7. 취합과 보고

워커를 띄웠으면 반드시 안내한다. 작업 크기로 생략하지 않는다. 워커 하나당 코드블록
하나다. 여러 개를 띄웠으면 블록을 연달아 놓는다. 한 블록에 여러 건을 넣지 않고, 블록
사이에 구분자를 넣지 않는다. 표로 바꾸지 않는다.

기동 보고를 출력하기 직전에 [references/FORM.md](references/FORM.md)의 `## 기동 보고`를 읽는다.

네 줄이고 라벨은 `이름` / `모델` / `모드` / `작업`이다. 라벨 뒤는 ` : `(공백-콜론-공백)다.
`이름`은 프로필 이름, `작업`은 맡은 일 한 줄이다. `모델`은 `provider/model [ thinkingOptionId ]`
이고 확인값(`snapshot.model`·`snapshot.effectiveThinkingOptionId`)을 쓴다. `모드`는
확인값(`currentModeId`)이고, 모드가 없는 프로바이더는 `없음`으로 쓴다. mermaid 라벨은
「어떤 그래프로 작업되는가」가 목적이라 모델명만 담고, 이 안내는
「어떤 에이전트가 무엇을 맡았는가」가 목적이라 두 형식을 같게 맞추지 않는다.

- 요청값과 다르면 출처를 적는다.
- `paseo run` CLI로 기동했으면 `thinkingOptionId`가 유실될 수 있다는 사실을 함께 적는다(1절).
- 대기 큐가 있으면 `활성 N / 대기 M`을 함께 낸다.
- **쪼개기와 프로필 선택의 과정은 출력하지 않는다.** 결과만 낸다.
- 레벨 2는 승인 시점에 그래프를, 완료 시점에 노드별 상태와 취합 결과를 낸다. 설계 과정은
  출력하지 않는다.

전원 완료 후 사용자에게 결과를 정리해 보고하는 최종 취합은 리더가 한다. 워커에 맡기지
않는다. 여러 워커의 결과 파일을 입력으로 새로운 비교·분석 결과 파일을 만드는 작업은 워커에
맡길 수 있다.

- 작업별 상태(완료/실패/미기동)와 완료된 결과 파일 경로를 낸다.

## 8. 세션이 이 스킬을 참조하지 않고 지나갈 때

사용자가 상시 프롬프트 추가를 요청한 경우에만 `scripts/append_system_prompt.py`를 실행한다.
요청이 없으면 이 절을 실행하지 않는다. **이 절차를 실행할 때 스크립트를 읽는다.**

대상 필드는 `daemon.appendSystemPrompt` 하나다. 파일 경로는 스크립트가 정한다. 다른 후보를
두지 않는다. 값은 덧붙이기만 하며 제거 경로는 없다. 기본이 dry-run이라 승인 전에 제시할 수
있다.

1. **점검·제시** — `--value`에 추가할 한 줄만 주고 실행한다. 그 줄이 이미 있으면
   `alreadyPresent`가 참으로 오고 아무것도 하지 않는다. 그 사실을 알리고 끝낸다.
   ```text
   python scripts/append_system_prompt.py --value "추가할 한 줄"
   ```
2. **승인** — dry-run이 낸 넷을 그대로 보여주고 명시 승인을 받는다: 고칠 파일 경로 / 추가할
   한 줄 원문 / 바뀌는 부분만의 diff / 되돌리는 방법. 저장소 밖 설정 변경이므로 승인 없이
   진행하지 않는다. 무응답·주제 전환은 승인이 아니다.
3. **적용** — 승인 뒤에만 같은 명령에 `--apply`를 붙인다. 백업·반영·reload·로그 재적재
   확인과 실패 시 롤백은 스크립트가 한다.
4. **보고** — 무엇을 고쳤는지와, 시스템 프롬프트는 세션 시작 시 고정되므로 **새 세션부터**
   적용된다고 보는 것을 함께 알린다.

되돌릴 때는 `--rollback`에 백업 경로를 준다. `--apply`가 없으면 이것도 dry-run이다.

```text
python scripts/append_system_prompt.py --rollback "백업 경로" --apply
```

## 9. 레벨 2 — 그래프 실행

2절에서 레벨 2로 떨어진 요청만 이 절로 온다. 새 스케줄러나 실행 엔진을 만들지 않는다.
기동은 `create_agent`, 순서는 완료 알림과 아래 절차다. 값 이관은 4절, 브리핑은 5절,
주입·실패 게이트는 6절이다.

그래프 형태(팬아웃·팬인·순차·토론)를 고를 때는
[references/graph-patterns.md](references/graph-patterns.md)를 읽는다.
실패·재시도·재개·프로바이더 장애의 동작은 그때
[references/failure-handling.md](references/failure-handling.md)를 읽는다.

같은 요청의 중단·압축 복구면 아래 「재개」로 간다. 새 요청이면 앞선 그래프를 재사용하지
않고 다시 설계한다.

### 설계

노드 ID는 `N1`, `N2`, `N3`처럼 쓴다. `노드1`은 쓰지 않는다.

그래프 모양은 `flowchart TD` mermaid다. 방향은 위에서 아래다. 같은 스테이지의 병렬
노드는 같은 앞 노드에서 갈라 나오게 그린다. `subgraph`로 뎁스를 묶지 않는다 — 의존은
노드끼리 화살표로 그린다. 라벨은 `N1["..."]`로 따옴표로 감싼다. 라벨은 세 줄이다 —
첫 줄 `[ 노드ID · 프로필 이름 ]`, 둘째 줄 모델명, 셋째 줄 한 마디. 줄 구분은 `<br/>`다.
첫 줄은 대괄호로 감싸고 안쪽에 공백을 한 칸씩 둔다. mermaid 코드펜스 맨 위에 아래
프론트매터를 **필수**로 넣는다 — 없으면 긴 프로필 이름이 재줄바꿈돼 행 구성이 깨진다.

```text
---
config:
  flowchart:
    wrappingWidth: 500
---
```

모델명은 `provider`를 뺀 값이고 thinking은 넣지 않는다. 나머지 속성은 아래 노드 표에만
둔다. 상태를 라벨에 넣지 않는다 — 표 갱신이 다이어그램 문자열 수정이 되어 문법이 깨진다.
계획 승인과 `GRAPH.md` 기록 모두 이 형식이다.

승인 대상은 mermaid와 되돌리기 경고다. 노드 표는 `GRAPH.md`에만 쓴다.

| 필드 | 내용 |
| --- | --- |
| 노드 ID | `N1`, `N2`, `N3` … |
| 프로필 | 이름과 선택 근거 한 마디 |
| 입력 | 앞 노드 결과 파일 **경로** (스테이지 1은 리더 브리핑) |
| 결과 파일 | 성공 결과 경로 + 실패 보고 경로 — 워커 브리핑(5절)에 준 경로와 같아야 한다 |
| 합격 기준 | 결과 파일·실패 보고 파일만 보고 판정할 수 있는 한 줄 |
| 워크스페이스 | 공유(local) 또는 격리(worktree) |
| 되돌리기 | 예/아니오. 예면 그 노드 기동 직전 추가 승인(2절 Step 0) |
| 재시도 | `불가` 또는 `가능 · 한도 1 · 사용 0`. 열을 늘리지 않는다. 한도와 사용 횟수는 이 셀에 적는다 |
| 상태 | `대기` / `실행 중` / `완료` / `실패` |
| agentId | 그 스테이지 기동을 마친 뒤 채운다 |

- 같은 파일을 쓰는 노드는 격리하지 말고 그래프를 고쳐 순차로 둔다.
- 기본 워크스페이스는 1절에서 고른 공유 workspace다. worktree는 사용자가 명시할 때만.
- 토론 라운드 전역 상한은 없다. 설계 때 스테이지로 드러나게 지정한다.
- 한 스테이지 노드 수가 10을 넘으면 3절 큐를 그 스테이지 안에서 그대로 쓴다.

### 계획 승인

워커를 하나라도 띄우기 **전에** 계획 승인을 **1회** 받는다. 읽기·조사만인 다단 그래프도
같다. 개별 노드 기동에 추가 계획 승인은 없다.

현재 대화에서 작업 범위·역할·실행 순서가 명시적으로 승인됐고 실행안이 그 내용과 같으면,
진행한다. 승인되지 않은 결정이나 승인 내용과 달라진 부분만
확인한다. 앞선 제안을 특정하는 "작업 시작해"는 그 제안의 승인이다. 다만 모호한 지시를
전체 계획 승인으로 확대하지 않는다.

그 승인이 아직 없으면 목적 → mermaid → 되돌리기 경고 → 기록 경로 순으로 **일반
응답으로 출력하고 턴을 마쳐** 사용자 답변을 기다린다. 이 순서는 고정이다. 승인 화면을
출력하기 직전에 [references/FORM.md](references/FORM.md)의 `## 승인 화면`을 읽는다. mermaid
전체 검토가 필요하므로 이 승인 요청은 질문 도구의 짧은 선택지로 대체하지 않는다.
무응답·주제 전환은 승인이 아니다. 승인 전에 `create_agent`를 호출하지 않는다.

목적 줄은 mermaid 밖에 `### 목적 — {한 문장}`으로 둔다. mermaid 안에 넣으면 스타일을
못 준다. 되돌리기 어려운 노드가 있으면
`⚠️ [ **노드ID** ] 되돌리기 어려움 — 기동 전 별도 승인`을 올리고, 없으면 경고 줄을
출력하지 않는다. 재시도·워크스페이스 등 다른 예외는 올리지 않는다.
`입력`·`결과 파일`·`합격 기준`·`재시도`는 승인 화면에 출력하지 않는다. 기록 경로는
`기록 : ` 뒤에 `GRAPH.md` 경로다.

형태가 바뀌는 재설계·범위 변경 주입·프로바이더 대체는 다시 승인받는다.

### GRAPH.md

레벨 2는 항상 만든다. 생성 자체는 승인 대상이 아니고, 승인 요청에 **기록 파일을 쓸 것과
그 경로를** 알린다.

경로: 5절에서 정한 실행 디렉터리의 `GRAPH.md`
결과 파일 규칙은 5절과 같다.

실행 기록을 쓰기 직전에 [references/FORM.md](references/FORM.md)의 `## 실행 기록`을 읽는다.

기록 시점:

1. 그 스테이지 기동을 마친 뒤 mermaid와 노드 표와 `agentId`를 한 번에 쓴다. 합격 기준·
   결과 파일·실패 보고 경로·재시도 한도는 표에 그대로 둔다.
2. 상태 갱신은 스테이지 경계에서만 한다. 노드 하나마다 갱신하지 않는다.
   사용자가 실행을 중단할 때 그 시점 상태로 즉시 갱신한다.
3. 재시도 잔여 횟수는 재시도가 실제로 발생할 때 기록한다.
4. 승인된 주입이 노드 행을 바꾸면 그때도 갱신한다.

### 실행

1. **기동 전에** 5절의 결과 파일·실패 보고 경로 분리를 확인한다 — 같으면 분리하기 전까지
   기동하지 않는다. 승인된 한 스테이지의 `대기` 노드를 기동한다. 상한 10 + FIFO는 3절과
   같다.
2. 완료 알림 대기는 3절과 같다.
3. **종료와 합격 기준 통과를 나누어 판정한다.** 실패 보고 경로에 내용이 있으면 `실패`다.
   그다음에야 결과 파일과 합격 기준을 대조한다. 에이전트가 멈춘 것만으로 `완료`가 아니다.
4. 그 스테이지의 `대기`가 없어지고 전원이 `완료`여야 다음 스테이지로 간다. 하나라도
   `실패`면 그 노드에 의존하는 노드는 기동하지 않는다.
5. 뒤 노드 브리핑에는 앞 노드 결과 파일의 **경로만** 넣는다. 본문을 붙이지 않는다.
6. 검토 노드는 5절이다.
7. 실행 중 `agentId`가 있으면 그 ID로 상태를 조회한다. 살아 있거나 이미 끝난 노드를
   완료 재기동하지 않는다. 생성 결과가 불명이면 조회부터 하고 중복 기동하지 않는다.
8. 주입과 실패 게이트는 6절이다. 범위 변경·재설계는 보내기 전에 승인을 받는다. 호스트가
   실행 중 메시지를 막으면 보내지 않고 보고한다.

### 재개

`list_agents`로 자식 에이전트를 조회하고(`labels`의 `paseo.parent-agent-id`), `GRAPH.md`가
있으면 읽는다. 기록된 `agentId`와 결과 파일·실패 보고 파일을 대조한다. `완료`이거나 실행
중인 노드는 다시 띄우지 않는다. `실패` 노드는 재시도 조건과 잔여 횟수를 충족할 때만
재기동한다. `대기`는 기동한다. 그래프 형태가 그대로면 이미 받은 계획 승인을 재사용한다.
대조 절차는 참조의 「재개」다.

### 완료 보고
