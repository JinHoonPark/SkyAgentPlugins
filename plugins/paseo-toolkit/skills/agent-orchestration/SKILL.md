# Agent Orchestration

## 적용 판정과 Step 0

팀장을 주어로 한 직접 지시는 아래 트리보다 먼저 처리한다. 단 아래 Step 0의 되돌리기 어려운 행동과 10절 브레인스토밍은 별도 트리거로 우선한다. 직접 지시와 워커 지시가 함께 있으면 사용자에게 확인한다. 작성자와 다른 수행자의 독립 검토를 요구한 지시는 1로 분류한다.

직접 처리 여부와 무관하게 git 커밋·스테이징·푸시·태그·브랜치 삭제, 외부 전송, 파일·디렉터리 삭제, 저장소 밖 설정 변경을 수행하기 전에 Step 0을 적용한다. 같은 범위의 명시적 지시는 승인으로 재사용한다. 승인 점검만 해당하면 전제 조회·위임·실행 기록 절차로 진입하지 않는다.

Step 0 경량 경로는 워커·`GRAPH.md` 없이 승인만 받고 팀장이 수행한다. `list_profiles`·`list_workspaces`도 조회하지 않는다. 그 수행으로 파일을 만들거나 고쳤으면 작업 뒤 5절의 직접 수정 검토를 붙인다. 레벨 1 경로나 워커 한 명 요청에서도 Step 0을 건너뛰지 않는다.
위임 경로에서는 되돌리기 어려운 단위의 기동 직전에 승인받고, 해당하지 않는 단위는 기다리지 않고 기동한다. git 커밋·스테이징·푸시·태그·브랜치 삭제는 사용자 명시 승인 없이 워커에 맡기지 않는다.
팀장이 스스로 추가한 행동은 언제나 승인 대상이다. 무응답·답변 누락·주제 전환·다른 작업 지시는 승인이 아니다.

```text
스킬 적용 판정 — 요청 문장만 보고 위에서부터, 처음 걸리는 곳에서 멈춘다
1. 사용자가 워커에 맡기라고 지시했다                         → 적용
2. 요청에 이름이 나오지 않은 파일을 찾아 읽어야 한다           → 적용
3. 로그 파일이나 전체 빌드·테스트 출력을 읽고 해석해야 한다     → 적용
4. 요청에 이름이 나온 대상 파일이 5개를 넘는다                 → 적용
5. 요청이 설계·구현·검토처럼 단계마다 따로 산출물을 내며
   이어지는 여러 단계를 거쳐야 한다                          → 적용
6. 그 밖                                                    → 팀장이 직접 처리
   직접 처리 중에 2·3·5에 해당하게 되면 그 시점에 적용으로 바꾼다.
검색식 한 번으로 위치만 확인하는 것은 2의 "찾아 읽기"가 아니다.
명령의 종료 코드·통과 여부만 확인하는 것은 3이 아니다.
팀장이 직접 고친 뒤 붙이는 독립 검토는 5의 단계로 세지 않는다.
```

적용이면 1절부터 7절까지 따르고, 레벨 2면 9절로 간다. 8절은 상시 라우팅 요청에만, 10절은 브레인스토밍 요청에 1절보다 먼저 읽는다. 위임 여부는 다시 묻지 않으며 라우팅은 팀장만 수행하고 워커는 재위임하지 않는다.
현재 컨텍스트에 그 절의 내용이 남아 있으면 다시 읽지 않는다. 압축·재개·부분 읽기로 없으면 필요한 절만 읽는다. 실행 중 바뀌는 결과 파일·실패 보고 파일·`GRAPH.md` 상태는 예외다.
이 스킬과 참조의 `GRAPH.md` 생성·행 추가·열 변경은 스킬 디렉터리에서 `python scripts/graph_update.py`의 `create`·`add-row`·`set`으로 수행한다. 스크립트 오류가 나면 [references/failure-handling.md](references/failure-handling.md)의 「그래프 갱신 오류」를 읽는다.

## 리더가 직접 하는 일

직접 처리로 판정된 작업은 팀장이 수행한다. 위임 경로에서 팀장이 직접 맡는 일은 세션 대화 맥락 자체를 근거로 삼는 일, 사용자 확인 문답, 워커 결과 취합과 보고, 사용자 브레인스토밍과 `BRAINSTORMING.md` 작성(10절)이다.
직접 처리한 작업 자체에는 `GRAPH.md`·결과 파일·노드 실패 파일 의무가 없다. 되돌리기 어려운 행동 전 승인(도입부 Step 0)·검증·실패 보고는 유지한다. 실패하면 원인·미완료 범위·미검증을 응답으로 보고하고 노드 실패 파일은 만들지 않는다. 스킬이 발동한 위임 경로와 직접 수정 뒤 검토 노드에는 기존 결과·실패 파일 규칙을 적용한다.
팀장이 직접 파일을 만들거나 고쳤으면 삭제만 한 경우를 제외하고 작업을 마친 뒤 5절의 리뷰 워커 독립 검토를 붙인다. 파일을 만들거나 고치지 않은 직접 처리에는 이 본문을 읽지 않는다.
`Agent` 도구·`Workflow`·deep-research는 쓰지 않는다. 단 스킬이 그 도구들을 쓰라고 지시하면 그 스킬을 따른다.

## 팀장 발화

팀장이 사용자에게 **먼저** 꺼내는 출력이 **자발 발화**다. 사용자 질문·지시에 답하는 출력은 자발 발화가 아니며, 아래 네 조건 중 **하나라도** 걸리는 사건에서만 자발 발화를 낸다. 넷 중 어디에도 걸리지 않으면 **침묵**한다. 어느 조건에 걸리는지 판정이 갈리면 즉시 발화로 본다.

1. **사용자 입력이 있어야 다음 동작이 정해진다** — 승인·확정·선택·답변을 받기 전에는 다음 동작을 고를 수 없다. 출력하고 턴을 마쳐 답을 기다린다.
2. **말하지 않고 진행하면 되돌릴 수 없는 결과가 남는다** — git 커밋·스테이징·푸시·태그·브랜치 삭제, 외부 전송, 파일·디렉터리 삭제, 저장소 밖 설정 변경, 권한 상향.
3. **정해진 절차로는 더 진행할 수 없다** — 재시도·분기·폴백 중 어느 것으로도 재개 경로가 없다.
4. **기록과 실제 상태가 어긋나 지금의 기록을 믿고 판단하면 틀린다.**

침묵은 확인·검증·기록 의무를 줄이지 않는다. 위임 경로와 직접 수정 뒤 검토 노드의 침묵 구간에는 모델·모드·thinking 확인값 대조, 실패 보고 경로를 결과 파일보다 앞세우는 확인, 결과 파일과 합격 기준의 대조, `python scripts/graph_update.py` 호출로 `GRAPH.md` 갱신을 그대로 수행하고, 그 확인 결과는 완료 보고로 보낸다. 직접 처리한 작업 자체의 승인·검증·실패 보고는 「리더가 직접 하는 일」을 따른다. **기동 시점 출력(7절)만 이 규칙의 예외다.** 사건별 즉시·침묵 배정은 [references/FORM.md](references/FORM.md)의 「발화 지점 배정」에 있고, 문서가 지시하는 출력은 전부 그 표에 배정돼 있다.

## 1. 전제 점검

### 도구를 부를 수 있는 상태로 만든다

claude에서 Paseo 도구는 deferred이므로 호출 전에 스키마를 로드한다.

```text
ToolSearch select:mcp__paseo__list_profiles,mcp__paseo__create_agent,mcp__paseo__list_workspaces,mcp__paseo__send_agent_prompt,mcp__paseo__get_agent_status,mcp__paseo__list_agents,mcp__paseo__cancel_agent
```

필요한 도구가 늘면 같은 형식으로 이어 붙인다. 이 호스트에 `ToolSearch`가 있으면 먼저 쓰고, 없으면 노출된 도구와 현재 검색 수단으로 확인한다. Codex에서 `ToolSearch` 부재를 단정하거나 특정 모드를 강제하지 않는다. 이후 도구 이름은 접두어 없이 쓴다.

Paseo 도구가 세션에 없으면 연결 불충족을 보고하고 사용자 전역 config를 스스로 고치지 않는다. 프로필 조회는 CLI 대응 명령이 없는 `list_profiles`로만 한다. provider를 추측하지 않는다. 새 세션에 도구를 주입하려면 `daemon.mcp.injectIntoAgents`가 활성이어야 하며 없으면 기본은 false다. 승인된 범위에서만 복구하고, 불가능하면 설정 변경을 제시해 사용자 판단을 받는다. 그 뒤에만 `paseo run`의 `--provider`·`--mode`·`--thinking`으로 기동하고, 응답·`inspect`의 `thinking`·`currentModeId`를 요청값과 대조해 확인 여부를 7절에 보고한다.

### 프로필 목록을 읽는다

`list_profiles`로 모든 프로필의 `notes`를 읽고 `notes`가 맞는 프로필을 고른다. 추측하지 않는다. 같은 세션에서 이미 읽었으면 다시 호출하지 않는다.
**예외 — 사용자가 그 세션에서 프로필을 바꿨거나 갱신이 확인되면 `list_profiles`를 다시
호출한다.** 매 기동마다 재조회하지는 않는다.

| 상태 | 판별 | 처리 |
| --- | --- | --- |
| **A. 목록이 비었다** | `list_profiles`가 빈 목록 | 프로필이 없다고 알리고 진행 여부를 묻는다. 진행하겠다고 답하면 `list_providers`·`list_models`로 고른 뒤 그 사실을 완료 보고에 남긴다 |
| **B. 맞는 것이 없다** | 어느 `notes`도 이 작업 유형을 포함하지 않는다 | 어느 프로필도 억지로 고르지 않는다. 어떤 유형을 찾았고 어느 `notes`도 걸리지 않았는지 한 줄로 알리지 않고, 4절의 역할↔프로필 해석 4단계로 이번 실행용 값을 구성해 그 사실을 완료 보고에 남긴다 |
| **C. 부분적으로만 맞는다** | `notes`가 인접하지만 경계 문구가 이 작업을 배제한다 | 허용되는 부분만 분리해 배정하고, 나머지는 적합 프로필 없음으로 처리한다(B). 통지로 경계를 넓히지 않는다. 벗어나는 부분이 작업의 본체이면 B로 취급한다. 분리 배정한 사실은 완료 보고에 남긴다 |

### 워크스페이스를 고른다

`list_workspaces`로 조회해 `cwd`가 대상 저장소인 워크스페이스를 고르고, 그 `workspaceId`를
`create_agent`에 **명시한다.** 생략하면 새 워크스페이스가 만들어진다. 워크스페이스 ID를
하드코딩하지 않고 매번 조회한다.

결과 파일을 서로 읽어야 하는 작업들은 같은 워크스페이스에 둔다. 같은 파일을 여럿이 써야 하는 요청은 2절 Step 3에서 레벨 2로
떨어지므로 격리로 우회하지 않는다. worktree 격리는 사용자가
명시할 때만 쓰고, 그때는 각 worktree 경로를 받아 그 경로를 읽어야 하는 워커의 브리핑에 넣는다.

이 호스트에서 쓸 수 있는 완료 알림·대기 수단을 확인하고, 없으면 종료 확인에
`get_agent_status`·`list_agents`의 제한된 상태 조회를 허용한다.

## 2. 레벨 판정 게이트

대상·역할·공통 입력을 기준으로 작업을 서로 겹치지 않는 단위로 먼저 쪼갠다. 단위 하나 =
워커 노드 하나. 맥락이 다른 일은 나눈다 — 한 세션에 여러 맥락을 몰지 않는다. 워커를 하나라도
띄우기 전에, 그 단위들 사이의 의존을 이 절의 트리로 판정한다.

### 개발 워크플로우 단계

**레벨을 개발 성숙도로 해석하지 않는다.** 단순 조회와
명백한 소규모 수정에는 스펙·마일스톤을 강제하지 않는다.

개발은 스펙 작성·사용자 피드백 → 스펙 확정 → 스파이크 필요성 공동 판정 → 필요하면 스파이크 설계·확정·실험·확인 → 마일스톤 필요성 공동 판정 → 필요하면 마일스톤 작성·확정 → 태스크 분해·확정 → 구현·자체 테스트 → 기능 또는 마일스톤 단위 독립 리뷰 1회 순서다. 스펙·스파이크·마일스톤·태스크는 각각 사용자 확정 뒤 다음 단계를 기동한다. 스파이크·마일스톤은 공동 판정이 필요일 때만 돌고 생략이면 다음 단계로 간다. 상세한 단계 전이는 [references/level2.md](references/level2.md)의 「개발 워크플로우 단계」를 따른다.

독립 검토 노드를 여는 경우는 **넷뿐이다** — ① 동작하는 기능 또는 마일스톤 구현이 끝난 뒤 여는 1회(9번), ② 여러 후속 작업을 폐기할 수 있는데 실험이나 기존 코드로 확인되지 않은 결정에 대해 팀장이 대상을 지정한 중간 검토, ③ 사용자가 명시적으로 요청한 검토, ④ 팀장이 직접 처리하며 파일을 만들거나 고친 뒤 여는 검토(삭제만 한 경우 제외). 스펙·스파이크·마일스톤·태스크 분해 단계에는 검토를 자동으로 붙이지 않는다. 워커의 자체 검증과 팀장의 결과·실패 증빙 확인은 독립 검토가 아니다.

`SPEC.md` 확정 뒤 스파이크·마일스톤 필요성은 실제 `notes` 허용 범위에서 스펙 워커가 별도 판정안 노드로 이어 맡고, 허용하지 않으면 각 설계 역할이 맡는다. 스파이크가 필요하면 설계·확정·실험·확인 뒤 마일스톤을 판정한다. 판정안마다 고유 ID·행·결과/실패 파일을 두고 스펙이 바뀌면 작성 워커가 갱신한다. 상세는 [references/level2.md](references/level2.md)의 「공동 판정과 판정안」·「순차 후속 노드의 워커 재사용」을 따른다.
팀장은 각 판정안을 세션 맥락·사용자 확정 사항과 대조해 **공동 결론**을 낸다. **`팀장 단독` 판정은 금지한다.** 생략 판정도 정상 산출물이며 실패가 아니다.

스펙 작성 워커가 결정이 필요한 질문을 만들면 팀장은 결과·범위·수용 판정이 달라지는 지점만 묻고, 주어진 근거로 답할 수 있는 것은 묻지 않는다.
답이 서로 독립인 질문은 번호를 붙여 한 번에 묻고 질문↔답 원문 대응을 보존한다. 하나라도 종속이면 순차. 필수 답이 모두 오기 전 다음 단계를 기동하지 않는다. 미응답은 승인이 아니다.
팀장은 질문의 의미를 바꾸지 않고 중계하며, 사용자 답변은 질문 번호와 묶어 원문 그대로 같은 작성 워커에게 전달한다.

여러 작업에 같은 내용이 필요하면, 그것이 이미 확정된 공통 입력인지 먼저 확인한다.
확정됐으면 리더가 같은 내용을 각 워커에 넘겨 독립 노드로 둔다. 확정되지 않았으면 작성
노드 → 사용 노드의 다단이다. 리더가 독립성을 만들려고 그 내용을 직접 창작하면 「리더가
직접 하는 일」의 제한과 충돌한다. 그 경우는 다단으로 간다.

대상 파일이 다르다는 사실만으로 무조건 분리하지는 않되, 공통 입력이 있다는 이유로 한
워커에 합치지도 않는다.

### 같은 목적의 작업 묶음

동일한 목적·역할·확정 입력을 공유하는 정확 검색과 미리 지정된 명령은 **횟수와 무관하게 한 작업 단위로 묶는다.** 같은 조회를 여러 단위로 나눠 여러 워커에 맡기지 않는다.

묶기 전에 각 항목에 Step 1~5의 의존·역할 분리·공동 쓰기·판정 의존·불명확성이 없는지 확인하고, **하나라도 있으면 묶지 않는다.** 출력에 따라 다음 명령을 고르는 작업은 이 묶음에서 제외하고 `## 4. 프로필 선택과 값 이관`의 역할 해석으로 보낸다.

묶음 전체에도 Step 0과 6절의 실패·권한 규칙을 적용한다. 묶음으로 Step 0 승인, Step 1~5 레벨 판정, 작성자와 검토자 분리를 우회하지 않는다.

**순서가 있는 판정 트리다. 위에서부터 내려가 처음 걸리는 곳에서 멈춘다.** **워커 수는 어느
단계에도 나오지 않는다.**

```text
Step 0 (레벨과 직교, 항상 수행 — 도입부 「적용 판정과 Step 0」 참조)

Step 1  어떤 작업의 입력이 다른 작업의 출력인가?            예 → 레벨 2 (멈춤)
Step 2  같은 대상에 서로 다른 역할이 배정되는가?            예 → 레벨 2 (멈춤)
          (구현과 검토, 토론자와 사회자, 작성과 감수)
Step 3  둘 이상의 작업이 같은 파일을 쓰는가?                예 → 레벨 2 (멈춤)
Step 4  어떤 작업의 합격 기준 판정이 다른 작업의 결과에      예 → 레벨 2 (멈춤)
        걸려 있는가?
Step 5  Step 1~4 중 하나라도 "모르겠다"인가?                예 → 레벨 2 (멈춤)
Step 6  그 밖의 전부                                       → 레벨 1
```

쪼갠 결과 다른 작업이 없어도 트리를 건너뛰지 않는다. Step 6에서 레벨 1이 된다.

### 레벨 2로 떨어지면 9절로 간다

Step 1~5 중 하나에 걸리면 3절로 내려가지 않고 9절로 간다. 승인 화면의 mermaid가 해당 의존을 드러낸다. 순차로 돌린다는 이유만으로 레벨 1로 바꾸지 않는다.

### Step 0 — 되돌리기 어려운 작업

도입부 「적용 판정과 Step 0」을 따른다.

## 3. 레벨 1 — 팬아웃

2절에서 레벨 1로 판정된 요청과 팀장 직접 수정 뒤 5절의 검토 노드가 이 절로 온다. 단위마다 4절의 프로필을 고른다. 성격이 같으면 같은 프로필을 써도 된다. 되돌리기 어려운 노드는 기동 **직전** Step 0으로 따로 승인받는다. 그 밖은 계획 승인 없이 기동하며 작업 개수만으로 승인받지 않는다.

`create_agent` **전에** `python scripts/graph_update.py create` 또는 `add-row`로 `GRAPH.md`의 mermaid와 노드 행을 쓰고, 기동 결과를 받는 즉시 `set`으로 `agentId`를 채운다. 레벨 1로 판정한 뒤 기동 전에 필요한 내용이 현재 컨텍스트에 없으면 [references/level1.md](references/level1.md)의 「공통 `GRAPH.md` 기록」·「레벨 1의 `GRAPH.md` 기록」을 읽는다.

### 활성 큐와 대기 큐

활성 큐는 실행 중 워커 최대 10개다. 나머지는 상한 없는 대기 큐에 쪼갠 순서(FIFO)로 둔다. 작업별로 노드 ID(`N`·`G` 접두별 독립 번호, 재부여 금지)·상태(`대기`·`실행 중`·`완료`·`실패`·`생략`)·프로필·대상·결과 경로·`agentId`·되돌리기 여부·재시도 가능 여부를 추적한다. 생략 단계에는 워커를 만들지 않는다. 큐는 컨텍스트에만 두고 별도 파일을 만들지 않으며, 노드별 `상태`·`agentId`는 `GRAPH.md`에 남긴다.

1절에서 확인한 알림·대기 수단을 쓴다. 알림이 있으면 폴링하지 않는다. 종료 1건을 확인할 때마다 실패 보고를 먼저 보고 결과 파일을 합격 기준과 대조해 판정한다. 파일 부재만으로 성공으로 보지 않는다. 판정 즉시 `python scripts/graph_update.py set`으로 `상태`를 기록하고 mermaid는 건드리지 않는다. 빈 슬롯만큼 대기 큐 선두를 기동해 `실행 중`을 기록한다. 기동 실패는 슬롯을 차지하지 않으며 6절의 재시도 분류를 따른다. 대기·활성 큐가 모두 비면 최종 상태를 `set`으로 확정하고 7절로 보고한다.

재개 또는 실패한 앞 작업의 결과가 대기 작업에 필요함을 뒤늦게 발견하면 [references/level1.md](references/level1.md)의 「레벨 1 재개」·「의존을 뒤늦게 발견하면」 중 필요한 절을 읽는다(현재 컨텍스트에 없을 때만).

## 4. 프로필 선택과 값 이관

### 역할↔프로필 해석

워크플로우 단계와 그래프 패턴은 **역할 이름**으로 기술한다 — 스펙 작성, 스파이크 설계,
구현, 독립 검토처럼 일의 종류다. **프로필 id는 실제 선택 결과와 프리셋 예시에만 쓴다.**

역할 프로필은 앞 단계에서 확정되지 않을 때만 다음 단계로 해석한다.

1. **`notes`가 핵심 작업을 명시 허용하는 프로필을 쓴다.** 스펙 작성에는 요구사항 분석과 사용자 확인 질문 생성이 포함된다. 이름·id가 `spec`이어도 허용 근거가 되지 않는다.
2. **이름·id가 달라도 작업 범위를 허용하는 넓은 프로필을 쓴다.** 역할과 프로필 id를 일대일로 강제하지 않는다.
3. **담당 부분을 안전하게 분리할 수 있으면 분리 배정한다.** 나머지나 분리 불가능한 작업은 4단계로 간다.
4. **없으면 [../../references/presets.md](../../references/presets.md)의 역할 정의와 실조회 모델·thinking으로 이번 실행용 값을 구성한다.** 이때 필요한 「역할 정의」·「역할별 thinking 등급」·「등급 해석 — 표 밖 후보 만들기」 절이 현재 컨텍스트에 없으면 읽는다. 전역 `agentProfiles`는 자동으로 바꾸지 않고 값의 출처를 보고한다.

`notes`가 배제한 일은 인접 역할이라는 이유로 넘기지 않는다. 적합한 `notes`가 없으면 보고한다.

### 값 이관

`create_agent`에는 `profile` 인수가 없다. **프로필의 값은 자동으로 적용되지 않으므로 네가
옮겨 담는다.** 이름이 서로 다르니 아래 대응을 그대로 따른다.

| 프로필의 값 | `create_agent`의 자리 |
| --- | --- |
| `provider` + `model` | `provider` — 두 값을 `provider/model` 한 문자열로 합쳐 넣는다 |
| `modeId` | `settings.modeId` |
| `thinkingOptionId` | `settings.thinkingOptionId` |
| `featureValues` | `settings.features` — **프로필에 이 키가 있을 때만** 옮긴다. 없으면 `settings.features`를 넣지 않는다 |

- `workspaceId`를 명시한다(1절). `title`은 `프로필이름: 한 줄 요약`이며 60자 이내다. 프로필 이름 때문에 요약 여유가 10자 미만이면 요약만 쓰고 프로필은 `labels.profile`에 둔다. `labels`는 `{"profile": 프로필id, "task": 한 마디, "run": 실행 식별자, "node": 노드 ID}`이며 `run`은 `{YYYY-MM-DD}-{슬러그}` 실행 디렉터리 이름이다.
- 선택 필드인 `settings.modeId`도 기본으로 채우고 프로필 값을 그대로 옮긴다. 결과 파일을 쓸 단위에는 claude `plan` 모드를 고르지 않는다.
- 요청값이 아니라 기동 결과로 모드·모델·thinking을 확인한다. `currentModeId`와 `snapshot.model`·`snapshot.effectiveThinkingOptionId`를 대조하고 `runtimeInfo`는 쓰지 않는다. 노드 1~2개면 `create_agent` 직후 `get_agent_status` 1회, 팬아웃이면 전체 기동 후 `list_agents` 1회로 묶어 확인한다. 보고의 모드·모델에는 확인값과 요청값이 다를 때 출처를 적는다(7절).

### 자문 역할의 폴백

자문 역할에는 **다른 역할로의 대체를 두지 않는다.** 적합 프로필이 없으면 이번 실행용 값을 구성할 때 [../../references/presets.md](../../references/presets.md)의 「역할 정의」·「등급 해석 — 표 밖 후보 만들기」 중 자문에 필요한 절만 읽는다. 사용 목적의 **사용자 승인** 없이는 기동하지 않는다. 구성할 수도 없으면 자문 노드를 생략하고 보고한다. **자문을 탐색·검토 등 다른 역할의 폴백으로 쓰지 않는다.**

## 5. 워커 브리핑

브리핑은 이 작업의 수행·권한·판정에 필요한 정보만 한 번씩 싣고, 같은 내용을 반복하지 않는다.

`assets/worker-briefing.md`가 그 템플릿이다. 워커를 띄우기 직전에 필요한 내용이 현재 컨텍스트에 없으면 읽는다. 중괄호 자리를 채워 `initialPrompt`로 넘긴다.

반드시 싣는 것: 워커 신분과 세션 내 재위임 금지; 실제 프로필 이름과 `notes` 원문(첫 줄은 `너는 워커다. 프로필: {이름} — {notes 원문}`); 노드 목표·수정 가능 대상·사용자 확정 제약; **요약하지 않은 원본 합격 기준**; 필수 입력 경로; 지정한 결과·실패 보고 경로; 도구·권한 예외(셸은 기본 도구, 새 터미널 금지); 출력 크기 제한; 보고 형식.

싣지 않는 것: 프로필 선택 이유·모델 비교; 큐·계획 승인 절차; 다른 노드 작업·참고 배경; 같은 제약의 반복; 미승인 제안; 경로로 제공한 앞 산출물 본문; 검토 노드에 주는 작성자 보고·해결 방향.

사용자 대화에만 있는 제약은 브리핑에 싣는다. 스펙 질문과 그 사용자 답변은 제외 목록의 좁은 예외로서 조건과 예외까지 원문으로 전달한다. 미확정 요청과 질문 대안은 미확정 입력으로 표시하고 실행 지시나 확정 제약으로 취급하지 않는다.

전체 대화와 산출물 본문은 다시 보내지 않는다. 글자 수 때문에 포함 목록 항목을 빼지 않는다. 추가 맥락은 빠지면 실행이나 판정이 달라지는 경우에만 싣는다. 프로필 `notes`는 요약 없이 원문을 한 번만 싣는다. 새 브리핑 문서는 만들지 않는다.

### 검토는 만든 에이전트에게 맡기지 않는다

2절의 네 경우에 여는 독립 검토는 작성자와 다른 리뷰 워커에게 맡긴다. 검토 워커는 아래 세 조건을 **모두** 만족해야 한다.

1. **작성자와 다른 `agentId`다.** 작성자가 팀장이든 워커든 같은 에이전트에 재프롬프트해 검토를 시키지 않는다.
2. **작성자의 대화·보고를 입력으로 받지 않는다.** 위임 산출물 검토에는 원본 합격 기준과 대상 경로를 넘긴다. 팀장 직접 수정 검토의 변경 입력은 사용자 요청 원문·확정 제약·대상 경로로 한정하고 팀장의 보고·대화·해결 방향은 싣지 않는다. 합격 기준에는 사용자 요청 원문·확정 제약을 그대로 싣는다.
3. **선택한 프로필의 `notes`가 검토를 허용한다.** 검토를 금지하는 `notes`의 프로필은 쓰지 않는다.

검토 라운드는 같은 단계·같은 수용 기준에 대해 총 3회(최초 1회, 재검토 최대 2회)다. 상세한 예산·라운드별 결과/실패 경로는 검토를 열 때 [references/level2.md](references/level2.md)의 「두 예산 — 사용자 왕복과 검토 라운드」를 읽는다(현재 컨텍스트에 없으면 필요한 절만 읽는다).

**전용 검토 프로필이 있으면 우선한다.** 없으면 4절의 역할↔프로필 해석으로 고른다. 구현과 검토를 함께 요청받은 것은 2절 Step 2에 걸려 9절로 간다. 검토 노드 기동 직전에 필요한 내용이 현재 컨텍스트에 없으면 [assets/review-briefing.md](assets/review-briefing.md)를 읽어 `initialPrompt`로 넘긴다.
팀장 직접 수정 검토는 2절 Step 2의 역할 분리로 보지 않고 3절 레벨 1 절차로 기동한다. 작업을 마친 뒤 검토를 열 때 [references/level2.md](references/level2.md)의 「팀장 직접 수정 검토」를 읽는다(현재 컨텍스트에 없으면 필요한 절만 읽는다).

### 결과 파일로 받는다

결과는 완료 알림 본문이 아니라 파일로 받는다. 알림은 결론·수행 범위·핵심 실행 증빙·근거·제약·결과 경로를 짧게 적고 해당하지 않는 항목은 생략하되 **출력 제한 때문에 사용자 요구 데이터나 합격 근거를 빼지 않는다.** 긴 텍스트는 결과 파일에 부분과 위치를 보존한다. 파일 수정 자체가 결과면 별도 성공 보고 파일은 만들지 않는다.

실행 디렉터리는 `.skywork/paseo-orchestration/{날짜}-{슬러그}/`다. 날짜는 실행일의 `YYYY-MM-DD`, 슬러그는 실행 전용이며 경로가 이미 있으면 바꾼다. 조사·분석·판정·검토 결과는 노드별 `nodes/{노드 ID}.md`, 실패 보고는 **서로 다른** `nodes/{노드 ID}.failure.md`다. 앞 라운드 파일은 보존하고, 2라운드 이후 경로는 [references/level2.md](references/level2.md)의 「두 예산 — 사용자 왕복과 검토 라운드」를 따른다. 단계 산출물 `SPEC.md`·`SPIKE.md`·`MILESTONES.md`·`MILESTONE{NN}-Tasks.md`는 실행 디렉터리 바로 아래에 두며 `{NN}`은 마일스톤 번호다. 단계의 실패 보고도 노드 실패 경로에 둔다. 상세는 레벨 2 참조의 「설계」를 따른다.

경로는 네가 정해 브리핑에 명시하고 스킬 소스에 사용자 고정 경로를 넣지 않는다. 실행 중에는 선택한 workspace 기준 상대 경로를 쓰고 worktree 간 전달이나 호스트가 요구할 때는 조회로 확인한 실제 절대 경로를 전달한다. 이 디렉터리의 `GRAPH.md`가 레벨 1·2 공용 실행 기록이다.

파일 수정 작업에도 **실패 보고 경로를 지정한다.** 성공하면 실패 파일이 생기지 않고, 파일이 있으면 그것이 실패다. 실패 보고를 결과 파일보다 앞세운다. **수정 대상 파일에 실패 사유를 쓰게 하지 않는다.** 기록 불가·쓰기 금지면 워커의 짧은 실패·미검증 응답을 실패 보고로 본다. **결과 파일 본문을 네 컨텍스트로 옮기지 않는다.** 필요하면 알림 요약 뒤 해당 범위만 읽는다.

## 6. 실행 중 개입과 실패 처리

실패 분류·재시도·셸 실패·프로바이더 장애·재개가 발생하면 [references/failure-handling.md](references/failure-handling.md)의 필요한 절을 읽는다(현재 컨텍스트에 없을 때만).

### 주입 — 승인이 필요한 것과 아닌 것

실행 중 지시는 `send_agent_prompt`, 워커 폐기는 `cancel_agent`를 쓴다. 호스트가 메시지·모드 변경을 막으면 우회하지 않고 보고한다.

| 종류 | 예 | 승인 |
| --- | --- | --- |
| **조회형** | 진행 질의, 결과 파일 경로 확인 | 불필요 |
| **범위 내 명확화** | 결과 경로·출력 형식 재지시, 기존 결과 파일 덮어쓰기/이어 쓰기/버리기 | 불필요 |
| **범위 변경** | 합격 기준 변경·추가, 대상 파일 추가, 역할 변경, 되돌리기 어려운 행동 추가, 권한을 올리는 모드 변경 | **보내기 전에 필수** |

애매하면 범위 변경으로 본다. 사후 통지는 승인이 아니다. 이미 받은 계획·되돌리기·권한 승인은 같은 범위에서 재사용한다. 범위 변경 승인 뒤 지시를 보냈으면 `python scripts/graph_update.py set`으로 해당 `GRAPH.md` 행을 갱신한다.

### 실패

워커 실패는 참조의 재시도 분류를 따른다. 브리핑 결함·명시 거부는 재시도하지 않고 원인을 보고하며 모드를 올려 우회하지 않는다. 권한 대기는 승인 범위 안이면 재사용하고, 아니면 요청 원문을 보여주고 사용자 판단을 받는다. 사용자 중단이면 실행 중 전원을 중단하고 상태·남은 경로를 보고한다. 부분 실패는 작업별 완료/실패/미기동, 완료 결과 경로와 미완료 범위를 보고한다.

자동 재시도는 부수효과 없음·멱등 두 조건을 모두 만족할 때 1회만 한다. 재기동 **전에** 사용 횟수를 기록하고 생성 결과가 불명이면 조회부터 한다. 실패 보고 경로에 내용이 있으면 완료보다 앞세운다. 재시도 셀에는 한도·사용 횟수를 적는다. 셸 실패를 `full-access`로 자동 승격하지 않는다. 호스트가 허용하고 기존 또는 새 승인이 있을 때만 모드를 바꾸며, 프로바이더 장애도 자동 대체하지 않는다.

## 7. 취합과 보고

새 워커를 기동하면 크기와 무관하게 반드시 보고한다. 워커당 코드블록 하나를 연달아 내고 표나 구분자는 쓰지 않는다. 출력 직전에 필요한 내용이 현재 컨텍스트에 없으면 [references/FORM.md](references/FORM.md)의 `## 기동 보고`를 읽어 라벨·모델·모드 확인값 형식을 따른다.

레벨 1 첫 기동 때만 목적 머리말과 `GRAPH.md` 경로를 블록 앞에 내고, 레벨 2는 승인 화면에서 이미 냈으므로 블록만 낸다. mermaid는 내지 않으며 경로는 실행당 한 번이다. 기동 보고는 승인이 아니다. 요청값과 다르면 출처를, `paseo run` CLI면 `thinkingOptionId` 유실 가능성을 적는다. 쪼개기·프로필 선택 과정은 출력하지 않는다.

전원 판정 뒤 팀장이 최종 취합한다. 여러 결과 파일의 새 비교·분석 파일은 워커에 맡길 수 있다. 완료 보고 직전에 필요한 내용이 현재 컨텍스트에 없으면 [references/FORM.md](references/FORM.md)의 `## 완료 보고`를 읽는다.

### 결과 인수

팀장은 종료 요약의 수행 범위·핵심 근거·종료 코드·누락·미검증을 **원본 합격 기준과 대조**해 인수한다. 근거 없이 완료로 인정하지 않는다. 원문 전체 재독·검색·명령 전면 재수행을 기본으로 하지 않고, 근거 불일치·필수 데이터 누락·중요 결함 의심 때만 범위를 특정해 확인한다. **이미 낸 증빙의 필요한 부분을 확인하는 것은 결과 인수다.**

후속은 팀장의 결과 인수(새 워커 없음), 원래 역할 워커의 범위 내 보완(같은 노드 재작업과 순차 후속 노드 구분), 역할 변경(4절 프로필 해석, 실제 `notes`가 허용하는 스펙 판정은 같은 워커), 별도 워커의 독립 검토(원본 요구·개발 워크플로우·승인 그래프·팀장 직접 수정이 요구할 때)를 구분한다. 순차 후속 재사용은 [references/level2.md](references/level2.md)의 「순차 후속 노드의 워커 재사용」을 따르고 서로 다른 검토 노드에는 적용하지 않는다. 재사용은 기동 보고 없이 완료 보고에 노드와 `agentId`를 남긴다. **결과 인수는 독립 검토를 대신하지 않는다.** 5절의 세 조건을 지킨다.

## 8. 세션이 이 스킬을 참조하지 않고 지나갈 때

사용자가 상시 프롬프트 추가를 요청한 경우에만 `scripts/append_system_prompt.py`를 실행한다.
요청이 없으면 이 절을 실행하지 않는다. **이 절차를 실행할 때 스크립트를 읽는다.**

기본 dry-run의 고칠 파일 경로·추가할 한 줄 원문·바뀌는 부분만의 diff·되돌리는 방법을 그대로 보여주고 명시 승인을 받는다. 저장소 밖 설정 변경이므로 승인 전에는 적용하지 않는다. 무응답·주제 전환은 승인이 아니다. 승인 뒤에만 적용하고 무엇을 고쳤는지 보고한다. 시스템 프롬프트는 세션 시작 시 고정되므로 **새 세션부터** 적용된다고 알린다.

상시 프롬프트 추가 요청을 받아 점검하기 직전에 [references/system-prompt.md](references/system-prompt.md)의 옵션·실행·복구 상세를 읽는다(현재 컨텍스트에 없으면 필요한 절만 읽는다).

## 9. 레벨 2 — 그래프 실행

2절 Step 1~5에 걸린 요청은 워커 기동 전 계획 승인을 1회 받는다. 현재 대화에서 같은 범위·역할·실행 순서를 명시 승인했다면 재사용한다. 상세는 [references/level2.md](references/level2.md)에 있다. 노드 설계 전에 필요한 내용이 현재 컨텍스트에 없으면 그 문서의 「설계」·「계획 승인」부터 필요한 절만 읽는다. 그래프 형태를 고를 때는 [references/graph-patterns.md](references/graph-patterns.md)의 필요한 절을 읽는다(현재 컨텍스트에 없을 때만). 실행 때는 레벨 2 문서의 「GRAPH.md」·「실행」을, 재개·완료 보고 때는 각각 해당 절을 필요할 때만 읽는다.
레벨 2에서 그래프를 쓰기 직전에 필요한 내용이 현재 컨텍스트에 없으면 [references/level1.md](references/level1.md)의 「공통 `GRAPH.md` 기록」을 읽는다.

## 10. 브레인스토밍 진입

무엇을 만들지·어떻게 풀지가 정해지지 않은 채 아이디어를 요구하는 요청이면 — "브레인스토밍하자",
"아이디어 좀 내보자", "뭘 만들면 좋을까", "방향 좀 잡아줘" — 워커를 고르기 전에 **먼저
"브레인스토밍을 진행해볼까요?"를 묻는다.** 애매할 때만이 아니라 **매번** 낸다 — 지금부터가
아이디어 회의라는 것을 양쪽이 같이 알아야 어디서 끊고 다음 게이트를 물을지 정해진다.

할 일이 특정된 요청("고쳐줘", "조회해줘", "추가해줘")은 여기 들지 않고 1절로 간다. 판정이
갈리면 물어본다. 요청이 단순해 보인다는 이유로 이 물음을 건너뛰지 않는다. 사용자가 동의하면
[references/brainstorming.md](references/brainstorming.md)의 절차를 따른다(필요한 내용이 현재 컨텍스트에 없으면 필요한 절만 읽는다). 거절하면
1절로 간다.
