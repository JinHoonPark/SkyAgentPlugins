# 심판 브리핑과 채점 규격

축3(작업 품질)을 채점할 때 읽는다. 축1·축2는 `scripts/check_routing.py`가 결정론으로
판정하므로 심판이 필요 없다.

## 왜 심판을 따로 두는가

산출물을 만든 에이전트에게 그 산출물의 수용 판정을 맡기면, 심판이 구현자의 전제를
그대로 물려받아 같은 오류를 통과시킨다. "나는 탐색 작업을 잘 수행했다"는 테스트 워커의
자기 보고는 채점 근거가 아니라 **채점 대상**이다.

그래서 채점 재료는 테스트 워커가 쓴 요약이 아니라 Paseo가 기록한 활동
(`get_agent_activity`)이다. 이것도 도구 설명상 "curated summary"라 원시 로그 그대로는
아니지만, **테스트 워커가 자기 평가를 위해 작성한 글이 아니라 플랫폼이 남긴 행동 기록**이라는
점이 핵심이다. 무엇을 했는지가 남고, 스스로 잘했다고 주장한 말은 섞이지 않는다.

## 심판에게 주는 것과 주지 않는 것

| 준다 | 주지 않는다 |
| --- | --- |
| 프로필의 `notes` 원문 | 테스트 워커의 결과 보고·요약 |
| 프로브에 준 지시 원문 | 축1·축2 판정 결과 |
| `get_agent_activity`로 회수한 활동 기록 | 다른 프로필의 채점 결과 |
| 아래 루브릭과 출력 규격 | "이 프로필은 통과여야 한다" 같은 기대 |

축1·축2 결과를 주지 않는 이유는, 라우팅이 어긋난 것을 알면 심판이 품질 점수를 그쪽으로
끌어다 맞추기 때문이다. 세 축은 끝까지 따로 판정하고 보고에서만 나란히 놓는다.

## 루브릭

`notes`가 라우팅의 유일한 근거이므로 채점 기준도 `notes`다. 두 축으로 나눈다.
프로필이 실패하는 방식이 둘이기 때문이다 — 약속한 일을 못 하거나, 배제한 일을 한다.

**이행 (fulfillment)** — `notes`가 약속한 일을 실제로 해냈는가.

| 점수 | 기준 |
| --- | --- |
| 5 | 약속한 결과를 냈고 근거도 확인 가능하다 |
| 4 | 결과는 맞으나 근거 제시나 마무리가 부족하다 |
| 3 | 절반쯤 했다. 사람이 이어서 마무리해야 한다 |
| 2 | 시도는 했으나 쓸 수 있는 결과가 없다 |
| 1 | 약속한 일을 하지 않았다 |

**경계 (boundary)** — `notes`가 배제한 일을 하지 않았는가.

| 점수 | 기준 |
| --- | --- |
| 5 | 범위 안에 머물렀다 |
| 4 | 살짝 넘었으나 해가 없다 |
| 3 | 인접 프로필의 일을 일부 했다 |
| 2 | 범위를 벗어난 변경이나 판단을 했다 |
| 1 | 다른 프로필이 맡아야 할 일을 대신 했다 |

경계는 `notes`에 배제 문구가 있을 때 특히 분명하다. 예를 들어 리뷰 프로필의
`notes`에 「수정은 하지 않음」이 있으면, 파일을 고친 기록이 남는 순간 경계는 2점 이하다.
배제 문구가 없으면 인접 프로필과의 구분선을 기준으로 본다.

점수는 근거가 있을 때만 준다. 활동 기록으로 확인할 수 없으면 그 항목은 FAIL이고,
`evidence`에 "활동 기록에서 확인되지 않음"이라고 적는다. 입증 책임은 통과 쪽에 있다.

## 출력 규격

심판은 이 JSON 하나만 파일로 남긴다. `scripts/testrun_ledger.py record --quality-file`이
그대로 읽는 형식이다.

```json
{
  "fulfillment": 4,
  "boundary": 5,
  "items": [
    {
      "text": "notes가 약속한 대로 코드 위치를 파일:줄로 제시했다",
      "passed": true,
      "evidence": "활동 기록에 manage_profiles.py의 config 해석 지점을 지목한 응답이 있다"
    },
    {
      "text": "찾기를 넘어 파일을 고치지 않았다",
      "passed": false,
      "evidence": "활동 기록에 편집 도구 호출이 두 번 있다"
    }
  ],
  "summary": "찾는 일은 해냈으나 notes가 배제한 수정까지 했다."
}
```

이 규격은 `scripts/testrun_ledger.py record`가 그대로 검사한다. 어긋나면 기록되지 않는다.

- `fulfillment`, `boundary` — 위 루브릭의 1~5 **정수**. 필수. 실수는 받지 않는다.
- `items` — 개별 판정. **비어 있을 수 없다.** `text`/`passed`/`evidence` 세 필드를 쓰고
  이름을 바꾸면 ledger가 읽지 못한다. `passed`는 true/false, `text`와 `evidence`는
  비어 있지 않은 문자열이다. 항목은 `notes`의 약속과 배제에서 뽑아 2~5개로 둔다.
- `summary` — 한 줄 총평. 필수.
- `score`는 선택이다. 넣으면 ledger가 그 값(0~5)을 쓰고, 없으면 두 축의 평균을 낸다.

## 브리핑 생성

브리핑은 손으로 조립하지 말고 `scripts/testrun_ledger.py brief`가 만들게 한다. 문구를
직접 짤수록 테스트 워커의 자기 보고가 섞일 자리가 생긴다. `brief`는 활동 원문의 출처를
필수로 요구해서, `--agent-id`가 없거나 ledger에 `launched`로 기록된 id와 다르면 브리핑을
만들지 않는다. 활동이 비어 있어도 거부하고, 지나치게 짧으면 요약을 넘긴 것으로 보고 경고한다.

다만 **활동 파일에 무엇을 담느냐는 스크립트가 검사하지 못한다.** `get_agent_activity`
결과 대신 워커의 요약을 넣어도 구별되지 않는다. 그 한 걸음은 절차 신뢰로 남으므로
회수한 원문을 그대로 저장하고 손대지 않는다.

아래는 `brief`가 채우는 템플릿이다. 스크립트를 쓸 수 없을 때만 이 형태로 직접 만든다.

```text
너는 심판이다. Paseo 프로필 하나가 자기 notes가 약속한 일을 해냈는지 채점한다.

채점 대상 프로필: [id] ([name])
이 프로필의 notes 원문:
[notes 원문 그대로]

이 프로필로 띄운 에이전트에게 준 지시:
[프로브 지시 원문 그대로]

그 에이전트의 활동 기록:
[get_agent_activity 결과]

이 기록은 에이전트가 실제로 한 일이지, 스스로 잘했다고 주장한 보고가 아니다.
기록에 없는 것은 일어나지 않은 것으로 본다.

채점 기준과 출력 형식은 [이 파일의 경로]의 루브릭과 출력 규격을 따른다.
결과 JSON을 [경로]에 저장하고, 본문에는 두 점수와 한 줄 총평만 적는다.
```

심판은 라우팅용 프로필이 아니라 검토용 `notes`를 가진 프로필로 띄운다. 구현·탐색용
프로필로 띄우면 채점 대신 문제를 고치려 든다.
