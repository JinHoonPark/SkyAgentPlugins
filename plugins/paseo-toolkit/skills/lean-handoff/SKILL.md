# 담백한 핸드오프

받는 에이전트가 원 대화를 읽었다고 가정하지 않고, 현재 작업을 이어가는 데 필요한 브리핑을 초기 프롬프트로 전달한다.

## 받는 에이전트와 작업 위치 선택

1. `paseo` 스킬을 읽어 도구 사용법을 확인한다. `list_profiles`를 호출하고 각 프로필의 `notes`를 읽은 뒤에만 받는 에이전트를 선택한다.
2. 사용자가 지정한 프로필을 우선하고, 지정이 없으면 작업에 맞는 `notes`의 프로필을 선택한다. 맞는 프로필이 없거나 목록이 비어 있으면 `paseo`의 provider 탐색 절차를 쓰고 사용자에게 대체 선택 사실을 알린다. 모델·모드·기능을 추측하지 않는다.
3. 선택한 프로필의 `provider`와 `model`을 `provider/model`로 합쳐 `create_agent.provider`에 넣는다. 프로필에 있는 값만 `modeId` → `settings.modeId`, `thinkingOptionId` → `settings.thinkingOptionId`, `featureValues` → `settings.features`로 옮긴다. 없는 값은 생략한다.
4. 기본 작업 위치는 현재 워크스페이스다. 사용자가 worktree를 요청하면 `create_workspace`에 `isolation: "worktree"`와 작업에서 따온 짧은 브랜치 이름을 전달해 격리 워크스페이스를 만든다.

## 브리핑 작성

작성 직전에 [references/FORM.md의 「브리핑」 절](references/FORM.md#브리핑)을 읽고 그 양식을 쓴다. 내용이 없는 절은 제목까지 생략한다.

- 사용자 의도의 작업 종류와 범위를 보존한다. 조사만 요청한 작업을 수정·구현으로 바꾸지 않는다. 현재 유효한 완료 조건에서 사용자가 명시한 문구와 조건·예외는 원문을 유지한다.
- 선별 질문: "이 줄이 빠지면 받는 쪽이 무엇을 틀리거나 다시 하는가?" 답이 없으면 지운다.
- 금지 1: 추천·폐기된 요구·과거 실패를 현재 지시나 제약으로 올리지 않는다. 실패는 "조건 → 관측"으로 쓴다.
- 금지 2: 같은 사실은 한 곳에만 쓴다.
- 금지 3: 빈 절, 작업 일지, 채택 경위, 근거 없는 "절대로"·"이미 합의됨"을 쓰지 않는다.
- 글자 수 상한은 두지 않는다.

## 발송 전 확인

완료 주장의 검증 근거와 받는 위치에서 필수 입력의 접근 가능성을 확인하고, 확인 못 한 것은 미확인으로 표시한다.

받는 쪽 재확인은 구체적 불확실성(다른 작업이 같은 파일 수정 중 / 검증 후 파일이 바뀜 / 받는 위치에서 입력 접근 미확인)이 있을 때만, 그 대상에 한정해 브리핑에 "[사유]. [의존 행동] 전에 [대상]을 확인한다." 한 줄로 쓴다. 고정 문구로 매번 넣지 않는다.

## 기동과 사용자 안내

1. `create_agent`에 `[Handoff] <작업>` 제목, 선택한 프로필의 실행 설정, 브리핑 전체를 `initialPrompt`로 전달한다. 작업 위치를 명시해야 하면 선택한 워크스페이스의 `workspaceId`를 전달한다.
2. 반환된 에이전트와 워크스페이스를 사용자에게 알린다. 다른 워크스페이스에 있어도 받는 에이전트는 사용자가 직접 분리하기 전까지 하위 에이전트 트랙에 남는다고 설명한다.
3. 완료를 기다리거나 폴링하지 않는다. 독립 실행을 생성 모드로 지정하거나 CLI·프로토콜 호출로 분리하지 않는다. 분리(detach)는 사용자가 하위 에이전트 트랙에서 직접 한다.
