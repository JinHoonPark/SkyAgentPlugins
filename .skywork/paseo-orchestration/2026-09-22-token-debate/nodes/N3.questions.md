## Q1. 병렬 조건과 직접 처리 대상의 경계 (SPEC R1-1, A6 트리거 평가 세트)

**해결됨 — 팀장이 제시하고 사용자가 확정한 판정 트리로 대체.** 사용자 답변 요지: A안의 "그보다 큰 단위"가 판단 가능한 문장인지 물은 뒤 판정 트리를 "문제가 없다면 확정". 병렬 조건은 트리로 대체하고, Step 0·브레인스토밍은 트리 밖 트리거로 유지한다. SPEC R1-1~4·R2-4·A1·A6·A8에 반영했다.

"서로 독립인 작업 단위가 둘 이상이면 스킬 적용"과 "한두 파일 수정·짧은 조회는 직접 처리"가 겹친다. 예를 들어 "a.md와 b.md 오타 고쳐줘"는 독립 단위 둘이면서 두 파일 수정이다.

- **A. 작은 단위는 합쳐 직접 처리한다 (추천)** — 짧은 조회·한두 파일 수정·간단한 질문 크기의 단위만 여럿이면 합쳐서 팀장이 직접 처리한다. 병렬 조건은 그보다 큰 단위가 둘 이상일 때만 적용한다. 합친 양이 대량 탐색 조건에 걸리면 위임한다. 비발동 범주를 지키면서 조건 하나로 경계가 정해진다.
- **B. 독립 단위가 둘 이상이면 크기와 무관하게 적용한다** — 기준은 단순하지만, 위 예시처럼 작은 요청도 워커를 띄운다. 트리거 평가의 비발동 범주 "한두 파일 수정"과 일부 충돌한다.

## Q2. `presets.md`의 team-lead·spec notes 원문도 이번에 고칠지 (SPEC R6, C6)

**해결됨 — A.** 사용자 답변 원문: "응 고쳐야지". SPEC R1-7·R6-9·C6·A9에 반영했다.

실제 프로필 notes는 profile-setup으로 바꾸기로 했다(저장소 밖 작업). 그런데 저장소의 `plugins/paseo-toolkit/references/presets.md`에도 두 역할의 추천 notes 원문이 있다. 이 파일은 profile-setup이 프로필을 다시 구성할 때의 기준이고, 적합한 프로필이 없을 때 agent-orchestration이 이번 실행용 값을 만드는 기준이기도 하다.

- **A. 이번 변경에 포함한다 (추천)** — `presets.md`의 `team-lead`·`spec` notes를 profile-setup으로 등록한 실제 notes와 같은 문구로 맞춘다(프리셋의 notes 160자 경고 규칙 준수). 프로필을 다시 구성해도 되돌아가지 않고, 프리셋으로 구성하는 경로에서도 판정 통합이 적용된다.
- **B. 고치지 않는다** — 실제 프로필만 바뀐다. 이후 프리셋으로 프로필을 다시 구성하면 옛 notes로 돌아가고, 프리셋으로 구성한 spec 역할은 판정 통합을 쓰지 못한다.

## Q3. `graph_update.py` 테스트를 어디에 둘지 (SPEC A5)

**해결됨 — A.** 사용자 답변 원문: "A". SPEC R5-8·A5에 반영했다.

저장소에는 스크립트 테스트 파일 관례가 없다. 실행 디렉터리 `.skywork/`는 git 추적 대상이 아니다.

- **A. 스크립트 안의 `--self-test` 옵션 (추천)** — 새 파일 없이 G1~G11을 언제든 다시 돌릴 수 있다. 팀장은 스크립트를 읽지 않고 호출만 하므로 스킬 로드량은 늘지 않는다.
- **B. 스킬 `scripts/`에 별도 테스트 파일** — 역할이 분명하게 나뉘지만 파일이 하나 늘고 플러그인과 함께 배포된다.
- **C. 저장소에 남기지 않는다** — 실행 디렉터리에서 한 번 돌리고 결과만 보고한다. 이후 회귀 확인 수단은 남지 않는다.
