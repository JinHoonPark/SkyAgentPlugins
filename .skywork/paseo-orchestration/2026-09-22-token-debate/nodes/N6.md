# N6 — 스파이크 필요성 판정안

## 판정: 필요

구현 자체(문서 재배치, 규칙 문구, 표준 라이브러리 `graph_update.py`, `send_agent_prompt` 재사용)는 기존 방식으로 성립하며 기술 불확실성이 없다. 성립을 막을 수 있는 것은 대체 경로가 없는 수용 기준 A6(트리거 평가, "WSL이나 Claude CLI 인증이 없으면 미검증 실패")과, 설계 (A)의 전제인 description 사건 트리거다. 둘 다 구현 순서상 5단계(설치본 갱신 전후)에야 처음 실행되므로, 거기서 막히면 description이나 수용 기준을 되돌려야 한다.

## 불확실성 목록 (검증 설계는 spike-plan 몫)

**U1. 트리거 평가 하네스가 A6 명령대로 이 환경에서 동작하는가**
- 플러그인 스킬 경로를 `--skill-path`로 준 실제 실행은 한 번도 없다(`--help`만 확인).
- `run_eval.py`는 cwd에서 위로 올라가며 처음 만나는 `.claude/`를 프로젝트 루트로 삼고, 그 아래 `.claude/commands/`에 임시 파일을 쓴 뒤 그 위치에서 `claude -p`를 실행한다(`run_eval.py:22-35`, `:53`, `:89`). A6대로 skill-creator 디렉터리에서 실행하면 루트가 Windows 사용자 홈이 될 수 있다. 그러면 사용자 전역 `.claude/`에 임시 파일이 쓰이고, 그 설정과 설치된 기존 agent-orchestration이 평가에 섞일 수 있다.
- WSL의 Claude CLI 인증 여부는 확인되지 않았다.

**U2. 첫 도구 호출 판정과 SPEC 규칙이 양립하는가**
- `run_eval.py`는 첫 도구 호출이 이 스킬의 Skill·Read가 아니면 즉시 미발동으로 판정한다(`run_eval.py:130-141`).
- 트리 2·3과 되돌리기 어려운 행동 질의는 규칙상 첫 동작으로 위치 검색이나 `ls` 같은 제한된 확인이 올 수 있다("직접 처리 중에 2·3에 해당하게 되면 그 시점에 적용"). 이 경우 올바른 동작도 실패로 기록돼 `summary.failed = 0`을 구조적으로 달성하지 못할 수 있다.
- skill-creator 문서에 따르면 짧은 1단계 질의는 description이 맞아도 발동하지 않는 경향이 있다. "이 빌드 로그 분석해줘" 같은 필수 발동 질의의 발동률이 불확실하다.

**U3. description만으로 세션 중간의 사건 트리거가 일어나는가**
- 수행 중 새로 계획한 되돌리기 어려운 행동(R2-1)과 직접 수정 뒤 검토(R1-7)는 첫 요청이 아니라 작업 도중에 스킬을 불러야 한다. A6으로는 잴 수 없고 A8-3에서만 확인되는데, A8은 버전 승인과 설치본 갱신 뒤에 실행된다.
- 발동하지 않으면 Step 0 승인 보장(설계 A)과 직접 수정 검토가 성립하지 않는다.

## 스파이크 대상 아님 (참고)

- A8의 세션 누적 사용량: 지금까지 확인된 값은 `lastUsage`(마지막 턴)뿐이라 누적 합을 얻는 방법이 미확인이다. 다만 SPEC이 실측하지 못하면 "정적 개선, 실제 효율 미검증"으로 보고하는 대체 경로를 두므로 성립을 막지 않는다.
- description 1,024자 한도: 필수 문구를 담은 초안이 약 760자로 추정돼 여유가 있다(추정치, 미측정).

스파이크가 필요이므로 이 파일에서 내지 않는다. SPEC R6-5대로 스파이크 뒤 마일스톤 역할이 판정한다.
