# N5 — SPEC 토큰 효율 자문

## 결론과 판단 범위

**조건부 진행을 권고한다.** 워커 생략·재독 제거·후속 판정·질문 묶기는 반복 운영비를 줄일 수 있다. 다만 상시 description·후속 대화·검증비가 빠져 있어 SPEC 통과가 전체 토큰 절감을 입증하지는 않는다. 아래 비용 효과는 실측이 아닌 추정이다.

SPEC.md·DECISIONS.md는 이번 실행 디렉터리 기준이다. SKILL.md·assets/는 `plugins/paseo-toolkit/skills/agent-orchestration/` 기준, AGENTS.md는 저장소 루트다. 작성자 보고는 읽지 않았다. 최신 사용자 확정 Q1(적용 트리), Q2(두 프리셋 notes 수정), Q3(스크립트 내부 자가 테스트)가 이전 토론 제안보다 우선한다.

## 1. 적용 트리의 대표 사례와 비용

‘과위임·과소위임’은 **비용 목적상 한계**이며 승인 트리를 임의 수정할 근거가 아니다.

| 요청 예시 | 승인 트리의 결과 | 비용상 판단 |
| --- | --- | --- |
| `a.md` 오타 수정 / `parseConfig` 위치만 검색 | 직접 | 워커 초기 입력·브리핑·GRAPH·기동 보고가 없어지는 주된 절감 사례다. |
| “버전 설정이 있는 파일을 찾아 값 하나 바꿔줘” | 2번 적용 | 검색 뒤 몇 줄만 읽으면 끝나도 위임한다. 발견·편집 자체보다 기동과 인수 비용이 커질 수 있다. **최소 한 워커이지 파일별 여러 워커라는 뜻은 아니다.** |
| 이름을 모두 제시한 6개 문서의 같은 오타 수정 | 4번 적용 | 정형 변경인데 5개/6개 경계에서 운영비가 불연속적으로 증가한다. 기존 동일 목적 묶기를 유지해야 추가 분할까지 발생하지 않는다. |
| “`trace.log`의 두 줄을 해석해줘” | 3번 적용 | 작은 로그도 위임한다. 로그 분량에 상관없는 과위임 비용은 Q1의 의도된 절충이다. |
| “이름을 제시한 1개 대형 파일의 복잡한 알고리즘을 설명해줘” | 추가 파일 탐색·로그 해석이 없다면 직접 | 자료가 커도 분리가 안 된다. 팀장 컨텍스트가 길어져 이후 호출 비용이 늘 가능성이 있다. 다만 위임이 반드시 더 싸다고 단정할 수는 없다. |
| “`a.py` 수정 후 테스트 통과 여부 알려줘” | 직접, 실패 원인 해석에 전체 출력이 필요해지면 전환 | 실패 시 팀장이 한 탐색과 워커의 재탐색이 겹칠 수 있다. 이미 확인한 사실·경로·검증 결과만 인계하고 다시 전면 탐색하지 않아야 한다. |
| “`a.py` 구현 후 독립 검토해줘” | ‘독립 검토’가 1번 위임 지시에 해당하는지 불명확 | 직접 경로로 해석하면 작성자와 검토자 분리가 사라질 수 있다. 불필요한 재작업뿐 아니라 품질 규칙 충돌이 생기므로 아래 F1에서 해결한다. |

근거는 `SPEC.md:20`, `SPEC.md:26`, `SPEC.md:30`이다. 이름이 없다는 이유만으로 적용하지 않고 **찾아서 읽어야 한다**까지 판정해야 한다. 위치 검색·종료 코드 예외도 해당 분기에서 평가해야 한다.

## 2. 결함과 보완 제안

심각도: 높음=품질 규칙 충돌, 중간=비용 왜곡·반복 낭비, 낮음=일회성 검증비 보완.

### F1 [높음] 적용 트리와 독립 검토의 경계가 정의되지 않았다

위치: `SPEC.md:21`, `SPEC.md:30`, `SPEC.md:139`.

적용한 뒤에는 기존 레벨 판정을 유지하지만, 적용하지 않는 요청은 그 판정에 도달하지 않는다. 따라서 지정 파일 5개 이하의 구현+독립 검토 요청에서 트리 1의 ‘워커에 맡기라는 지시’를 좁게 해석하면 직접 처리가 된다. 기존 SKILL은 사용자 요청 검토에 작성자 분리를 요구한다(`SKILL.md:330`). R9의 독립성 불변과 R1을 어떤 우선순위로 적용할지 불명확하다.

수정 제안: “‘다른 에이전트에게 검토’, ‘독립 검토’처럼 작성자와 다른 수행자를 요구하는 지시는 트리 1로 분류한다”는 해석을 사용자에게 확인하고 양쪽 경계 사례를 A6에 넣는다. **새 6번째 트리거를 조용히 추가하거나 기존 Step 5를 트리 앞에 복원하지 않는다.** 명시적 독립 검토 요구가 없는 직접 기능 수정의 기본 리뷰 의무까지 유지할지도 별도로 명시한다. 기존 기본 독립 리뷰(`SKILL.md:111`)가 직접 경로에서 제외된다면 R1의 의도 변경 범위에 그 사실을 드러낸다.

### F2 [중간] ‘직접 처리 로드 0’은 총 토큰 비용 0이 아니다

위치: `SPEC.md:18`, `SPEC.md:35`, `SPEC.md:168`, `SPEC.md:174`, `SPEC.md:233`.

트리 원문과 예외·권한 조건을 description과 본문에 반복하는데 A1은 발동 후 SKILL 본문부터 센다. 적용 판단에 노출되는 description 증가분이 제외된다. 또한 A8은 변경 후 2건만 측정하므로 캐시·모델·작업 구성 차이를 통제한 전후 절감률을 얻을 수 없다. 정적 Read 감소도 실제 팀장 모델 호출 감소와 같지 않다.

수정 제안: Q1 원문 보존은 유지하고, A1에 **description 전후 문자 차이**를 별도 열로 추가한다. 직접 경로의 0은 ‘본문·참조 로드 0’이라고 명명한다. A8은 세션 전체의 누적 사용량인지 명시하고 팀장+모든 워커 합계·전체 모델 호출 수를 함께 기록한다. 최초/마지막 한 턴 수치로 세션 비용을 대표하지 않는다. 추가 반복 실험은 요구하지 않는다. 보고 문구는 ‘워커 생략·재독 감소 확인, 전체 토큰/비용 절감률 미입증’으로 한정한다(`DECISIONS.md:34`).

### F3 [중간] 후속 브리핑의 신분·notes 생략이 현재 문맥을 확인하지 않는다

위치: `SPEC.md:123`, `SPEC.md:80`, `SPEC.md:150`.

참조 문서는 압축 뒤 재독을 허용하면서 후속 브리핑은 신분·notes를 다시 싣지 않는다. 재위임 방지가 문맥의 지시에 의존하므로 압축에서 유실되면 범위 밖 수행·재위임 비용이 생길 수 있다. 영구 워커 규칙은 `assets/worker-briefing.md:24`에 있다. 실제 유실을 관측한 것은 아니다.

수정 제안: 현재 문맥에 역할·notes가 유효하게 남아 있을 때만 생략하고, 압축·재개로 없으면 그 두 항목만 다시 준다. 매 후속마다 전체 브리핑을 복제하거나 새 워커를 띄우지는 않는다. 실제 프로필 변경이 있으면 이전 notes를 계속 쓰지 않는다.

### F4 [중간] 스크립트 오류의 반복 호출에 중단 기준이 없다

위치: `SPEC.md:97`, `SPEC.md:94`.

“인수 오류면 진단대로 고쳐 다시 부른다”만 있어, 중복 노드·깨진 상태처럼 인수 교정으로 해결되지 않는 오류도 재호출 루프로 흐를 수 있다. 워커 기동 재시도 한도를 이 기록 도구에 잘못 적용하는 것도 피해야 한다.

수정 제안: 교정 근거가 있을 때만 재호출하고 같은 진단의 반복·기록 불일치는 기존 실패 게이트로 처리한다. 필요한 기록 없이 다음 워커를 기동하지 않는다. 직접 편집 폴백은 명시된 실행 불가 환경에 한정한다. 별도 복구 규칙을 늘리지 않는다.

### F5 [낮음] 검증이 자체적으로 큰 토큰 작업이 될 수 있다

위치: `SPEC.md:200`, `SPEC.md:222`.

A6은 발동 6범주×2건=12건, 비발동 최소 9건, 각각 3회이므로 **최소 63회 질의 평가 실행**이다. 이는 SPEC에서 산출한 하한이며 실제 모델 호출 수·토큰량은 미측정이다. A4도 기존 규칙 전부와 새 인용을 생성하므로 대조표 작성·검토 비용이 크다. 다만 트리거 평가 자체는 오늘 바뀐 AGENTS.md가 요구하므로 없애면 안 된다(`AGENTS.md:69`).

수정 제안: 정적 문구·링크·길이 검사를 먼저 통과시키고 description을 고정한 뒤 최종 평가를 한 번 수행한다. 이후에는 변경으로 무효화된 경우만 재평가한다. 대조표의 원문·위치·인용 검사는 가능한 부분을 스크립트로 생성하고, 모델은 의미 대응을 확인한다. 보고에는 불일치·요약만 싣고 표 전체를 다시 컨텍스트에 복사하지 않는다. 3회 반복을 줄이는 방안은 별도 선택이며 현재 합격 조건을 임의 완화하지 않는다.

## 3. 합의 대비 변경·정합성

- **승인된 교체:** 작업 성격·의존 불명확성 중심의 옛 적용안(`DECISIONS.md:13`)은 Q1의 파일/로그 트리로 대체됐다(`SPEC.md:20`). 이것을 합의 위반으로 되돌리지 않는다. 다만 F1의 독립 검토 경계는 잔류 규칙과 조정해야 한다.
- **승인된 추가:** presets의 team-lead·spec notes 수정과 내부 `--self-test`는 Q2·Q3를 반영한다(`SPEC.md:36`, `SPEC.md:98`, `SPEC.md:112`). profile-setup 작업을 팀장 측 별도 전제로 둔 것도 DECISIONS.md:8과 일치한다.
- **현재 규칙에 맞춘 변경:** 구조 변경에 skill-creator 전체 실행을 요구하지 않는 C2는 오늘 변경된 AGENTS.md:71에 맞다. 과거 자문에서 요구했던 구조 변경 시 skill-creator 적용은 더 이상 판단 기준이 아니다. 발동 조건 평가는 여전히 필요하다.
- **합의 유지:** 판정안은 스펙 확정 뒤 별도 결과 파일, 팀장 공동 판정, 스파이크 뒤 마일스톤 순서를 지킨다(`SPEC.md:104`, `DECISIONS.md:25`). 다른 판정 노드를 같은 에이전트에 맡기는 R6-8 예외는 그 통합을 실현하는 데 필요하며 일반 재사용 경계 확대와 구별된다.
- **줄지 않는 비용:** 판정 통합은 새 세션 수를 줄이지만 확정 후 판정 요청·공동 판정·마일스톤 후속 요청은 남는다(`SPEC.md:104`, `SPEC.md:109`). 단계 승인이나 판정 횟수까지 사라졌다고 보고하면 안 된다. R7의 새 노드 기록과 완료 보고도 추가된다(`SPEC.md:120`, `SPEC.md:125`).
- **측정 범위 유지:** 대표 2건 각 1회는 비용 때문에 선택한 합의다. 대규모 전후 실험을 다시 요구하지 않는다. L1 3워커 시나리오는 ‘서로 독립’뿐 아니라 같은 목적 묶음 대상이 아님을 고정해야 한다. 그렇지 않으면 기동 3회라는 A8 조건이 기존 묶음 규칙을 거슬러 쓸데없는 워커를 보상한다(`SPEC.md:232`, `SKILL.md:133`).

## 4. 권장 구현 순서

1. **진입 경계 확정 후 R1·R2·두 notes 정합성:** F1을 해결하고 description 정적 검사를 먼저 한다. 명시 대상의 작은 작업에서 가장 큰 반복 절감이 예상된다. 실제 notes 반영 여부는 별도 전제로 확인한다.
2. **R4 재독 제거·R8 질문 묶기:** 현재 문맥 재사용과 질문 왕복 감축을 적용한다. 파일 구조 변경보다 작고 실패 비용이 낮다. 필수 답·사용자 확정 게이트는 유지한다.
3. **R5 기록 스크립트와 자가 테스트:** 기존 형식·순서를 고정한 채 기계적 편집 호출을 줄인다. 출력은 요약만 반환해 GRAPH 전체 재주입을 막는다. 표준 라이브러리 구현·자가 테스트는 모델 재호출 없이 끝내는 방향으로 구성한다.
4. **R6·R7 판정/워커 재사용:** agentId 공유 시 행·실패 경로·재개를 함께 검증한다. 기동 수 감소와 누적 대화 비용의 교환이므로 무제한 재사용으로 넓히지 않는다.
5. **R3 최종 재배치·최종 트리거 평가·A8 2건:** 앞선 변경으로 사라진 중복을 마지막에 정리해 문서 이동을 두 번 하지 않는다. 최종 평가 전 description은 고정한다. 기존 버전 승인·설치본 갱신 시점은 유지한다.

승인 범위는 유지하고 구현 순서만 나눈다. 반복 1건의 절감량 E와 일회성 개발·검증비 M을 분리해 보고한다. 비용 회수 조건은 `실행 횟수 × E > M`이며 현재 E·M은 미측정이다.

## 검증

Get-Content·rg로 입력과 원본 규칙을 대조하고, 6,000자 제한·인용 파일/줄 존재·BOM 없는 UTF-8을 확인했다. 구현·트리거 평가·사용량 실험은 하지 않았다.
