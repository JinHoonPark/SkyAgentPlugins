# N2 — 2라운드 교차 반박

## T1. 필요성 판정 통합

**최종 판정: 중재안 조건부 수용.** 단계 역전은 피할 수 있지만 현 상태 그대로는 프로필 경계를 바꾼다.

- 수용: 스펙 피드백을 같은 작성 워커가 반영하므로, **사용자가 SPEC.md를 명시 확정한 뒤** 그 워커가 스파이크 필요성 판정안을 갱신하면 기존 순서(스펙 확정 → 필요성 공동 판정)를 지킬 수 있다(`SKILL.md:101-108`, `ROUND2.md:17-20`). 판정 결과는 `필요·생략·정보 부족`이어야 하고 팀장 공동 판정도 유지한다(`level2.md:123-134`).
- 반박: 현 규칙은 “스파이크 설계 역할”이 판정안을 내도록 하고, spec notes는 검증 설계를 `spike-plan`으로 넘긴다(`level2.md:125-134`, `presets.md:238-246`). “설계만 배제하므로 필요성은 자동 허용”은 `notes`가 핵심 작업을 **명시적으로 허용**해야 한다는 기준을 충족하지 못한다(`SKILL.md:237-250`). 마일스톤 판정도 현재 milestone 역할 소관이며 스파이크 뒤다(`SKILL.md:105-120`, `presets.md:254-256`).
- 합의 문구: “사용자가 SPEC.md를 확정한 뒤, spec notes에 필요성 판정을 명시적으로 허용한 경우 같은 스펙 워커가 **별도 노드 결과 파일**에 스파이크 필요성 판정안을 낸다. 실험 설계는 하지 않으며 팀장이 공동 판정한다. 스파이크가 필요하면 이후 기존 절차를 따른다. 마일스톤 필요성은 milestone 역할이 판정한다.” 마일스톤까지 재사용하려면 spec notes와 역할 규칙을 별도 승인으로 넓혀야 하며, SPEC.md에 판정안을 섞으면 결과 경로 규칙도 바뀐다(`level2.md:102`).

## T2. Step 0의 상시성

**최종 판정: 별도 스니펫 파일은 폐기. 짧은 상시 정책이 최선이고, 불가능하면 destructive 트리거가 안전한 차선이다.**

- 수용: 연결되지 않은 파일은 상시 규칙이 아니며 문서만 늘린다는 자문·리뷰 결론에 동의한다(`N1.md:20`, `N2.md:31`).
- 반박/비용: destructive 문구를 description 트리거에만 넣으면 단일 삭제에도 19,243자 스킬이 로드된다. 다만 워커 1회 실측 입력 31,965토큰 중 31,232가 캐시였다는 한 사례는 비용 일반화 근거가 아니며, 최소한 새 워커 기동도 함께 피해야 한다(`ROUND2.md:6-7`).
- 합의 기준: 우선순위는 (1) 호스트가 항상 읽는 AGENTS/CLAUDE/system 영역에 Step 0 네 범위를 3~5줄로 두되 사용자 승인 후 설치, (2) 그것이 없으면 description이 destructive 요청을 트리거하고 스킬은 **승인만 받은 뒤 단순 작업을 팀장이 직접 수행**하는 경량 분기를 둔다, (3) 승인 없는 삭제·외부 전송·저장소 밖 설정 변경은 비용과 무관하게 진행하지 않는다. 현재 `appendSystemPrompt`가 비어 있어 충돌은 없지만 전역 설정 변경은 이번 구현 범위가 아니다(`ROUND2.md:14`, `SKILL.md:165-177`).

## T3. 조건부 적용 기준

**최종 판정: 정량 문턱을 보조 기준으로 쓰고, Step 5 불명확성과 분리한다.**

- 수용: “애매하면 직접”은 탐색량 추정에만 적용해야 한다는 자문 지적이 정확하다(`N1.md:48`). 파일 10개·수천 줄은 예측 가능한 운영 기준으로 쓸 수 있다(`LEAD.md:16-18`).
- 합의 문구: “명시적 위임, 독립 작업 단위 2개 이상, 또는 분해된 단위 사이 Step 1~4가 예이거나 불명확하면 이 스킬을 적용한다. 그 밖에 착수 전에 읽을 대상이 10개 이상이거나 처리할 단일/합산 출력이 2,000줄 또는 100,000자 이상으로 예상되면 적용한다. **오직 탐색량 문턱이 애매한 경우에만 직접 처리**한다. 적용 후 Step 1~4 판단이 불명확하면 Step 5에 따라 레벨 2다.”
- 설정: 저장소 밖 `team-lead` notes는 새 직접 처리 정책과 충돌하므로 사실과 영향만 보고하고 자동 수정하지 않는다(`ROUND2.md:23-25`, `LEAD.md:19-21`). 동의한다.

## T4. 검증 가능한 합격 기준

**최종 판정: 파일 크기가 아니라 동일 수용 조건을 통과한 요청의 경로별 총비용으로 판정한다.** 캐시 비중이 크므로 raw·cached·non-cached 입력을 분리한다(`ROUND2.md:6-7`, `N1.md:24-35`).

합격 기준 세트:

1. 고정 시나리오: 짧은 조회, 한 파일 수정, 레벨 1 팬아웃, 레벨 2 순차+검토, 실패 재개를 변경 전후 같은 모델·mode·thinking·입력으로 각 3회 실행한다.
2. 기능 게이트: 승인, 검토 독립성 3조건, 결과/실패 경로 분리와 실패 우선 판정이 전부 통과해야 한다. 하나라도 실패하면 비용과 무관하게 불합격이다.
3. 경로별 필수 고유 문자 합과 반복 Read 문자 합을 모두 기록한다. 직접 처리 경로는 orchestration 본문 Read 0회, 짧은 두 시나리오는 워커 생성 0회여야 한다.
4. 각 에이전트의 `inputTokens`, `cachedInputTokens`, `inputTokens-cachedInputTokens`, 출력·추론 토큰, 워커 수, 모델 호출 수, Read 수, 완료 시간을 합산한다. 변경 후 3회 중앙값 기준 최적화 대상 각 경로의 총 입력 토큰과 Read 문자가 감소하고, 전체 시나리오의 가격 가중 입력비가 20% 이상 감소해야 한다. 가격을 검증하지 못하면 raw/cached 수치만 보고하고 비용 합격은 보류한다.
5. 비대상 레벨 2 경로는 총 입력·호출 수가 5% 넘게 악화되면 불합격이다.

측정 명령 예시:

```powershell
$files=@('경로1','경로2'); ($files|%{[IO.File]::ReadAllText((Resolve-Path $_)).Length}|Measure-Object -Sum).Sum
$rows=Get-ChildItem usage/*.json|%{$j=Get-Content $_ -Raw|ConvertFrom-Json; [pscustomobject]@{input=$j.lastUsage.inputTokens;cached=$j.lastUsage.cachedInputTokens;uncached=$j.lastUsage.inputTokens-$j.lastUsage.cachedInputTokens}}; $rows|Measure-Object input,cached,uncached -Sum
rg -n 'toolName.*(Read|exec_command)|Get-Content|ReadAllText' activity/*.json
```

SKILL에 남길 것: 적용/직접처리 경계, Step 0, 레벨 트리, 사용자 확정 게이트, 검토 독립성 3조건, 값 이관 표, 브리핑 필수 항목, 결과/실패 경로 분리·실패 우선, 주입 승인 표, 재시도 핵심. 옮길 것: 8절 상세, 브레인스토밍 상세, 자문 폴백, 프로필 B·C 세부, 라운드 파일명·재개, 레벨별 큐/GRAPH 세부. 레벨 1 세부는 이미 필수인 `level1.md`, 레벨 2 세부는 `level2.md`에 두고 중복을 제거한다. `FORM.md`의 매 시점 재독은 “현재 컨텍스트에 해당 절이 남아 있지 않을 때만”으로 바꾼다(`LEAD.md:26-33`, `N2.md:51-59`).

## T5. 자문 추가안

**최종 판정: 독립 질문 묶기만 이번 범위에 조건부 포함, patch 단순화와 thinking 조정은 후속 분리.**

- 질문 묶기: 현재 한 번에 하나만 묻는 규칙은 모델 왕복을 늘린다(`level2.md:136-141`, `N1.md:42`). “서로 답에 의존하지 않는 질문은 번호를 붙여 한 번에 묻고 질문↔답 원문 대응을 보존한다. 하나라도 종속이면 순차로 묻고, 필수 답이 모두 오기 전 다음 단계를 기동하지 않는다”로 합의 가능하다.
- patch: 생성·적용 실패 예산과 라운드 증빙을 바꾸므로 별도 설계·승인이 필요하다(`level2.md:350-363`, `N1.md:43`). 이번 범위에서 제외한다.
- thinking: 실제 품질/비용 벤치마크와 프로필 변경 승인이 필요하며 임의 하향 금지와 맞물린다(`N1.md:44`, `presets.md:94-104`). profile-test-run 성격의 후속 작업으로 뺀다.

## T6. 버전·구조 변경

**최종 판정: 이의 없음.** 개발 중 버전을 올리지 않고 main 머지 직전에 규모·추천 버전을 제시해 사용자 승인 후 두 매니페스트에 함께 반영한다(`AGENTS.md:52-57`). `graph_update.py` 추가와 본문 분리는 파일 구조 변경이므로 구현 전에 `skill-creator`를 적용한다(`AGENTS.md:64-78`). 새 스크립트는 상태 변경 시 mermaid 불변, 원자적 실패, UTF-8, 버전 읽기 실패를 테스트해야 한다(`N2.md:34`).
