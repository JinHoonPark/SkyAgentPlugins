# N4 — SPEC 1라운드 검토

## 판정

**수정 후 진행. 결함 7건(높음 3, 중간 4).**

DECISIONS.md의 합의 1~12와 후속 확정 Q1~Q3는 대체로 빠짐없이 반영됐다. 승인 게이트, 검토 독립성 3조건, 결과/실패 파일 분리·실패 우선, 실패 처리도 의도 변경 다섯 항목 밖에서는 보존 대상으로 명시돼 있다(`SPEC.md:136-140`). 다만 아래 결함 때문에 현재 문서만으로는 트리거 우선순위와 안전 회귀를 단정할 수 없고 A6을 이 Windows 호스트에서 그대로 실행할 수 없다.

## 결함 목록

### D1. 높음 — “팀장이 직접” 예외의 우선순위가 트리와 모순

- 위치: `SPEC.md:18-35`, `SPEC.md:220`
- 근거: Q1 트리는 “위에서부터 처음 걸리는 곳”에서 멈추지만 직접 처리 지시는 트리 안에 없다. 동시에 R1-6과 A6은 기존 “네가 직접 해” 예외를 유지한다. 예를 들어 “네가 직접 이 에러 원인 찾아줘”는 직접 지시와 트리 2가 함께 성립해 적용 여부가 둘이다.
- 수정: 정확한 Q1 트리는 바꾸지 말고 그 앞에 “팀장을 주어로 한 직접 지시는 적용 판정 트리보다 먼저 처리한다. 단 Step 0·브레인스토밍 별도 트리거는 우선한다. 직접 지시와 워커 지시가 함께 있으면 모순을 사용자에게 확인한다”를 둔다. A6에 이 세 경우를 발동/비발동 질의로 추가한다.

### D2. 높음 — 수행 중 새로 계획한 Step 0의 안전 동작을 검증하지 않음

- 위치: `SPEC.md:42-47`, `SPEC.md:218-223`, `SPEC.md:229-234`
- 근거: R2는 처음에는 스킬이 발동하지 않은 직접 처리 중 새로 계획한 삭제·외부 전송·저장소 밖 설정 변경도 행동 전에 발동하라고 한다. 그러나 A6은 사용자 요청 문장의 정적 트리거만 평가하고, A8도 처음부터 삭제가 명시된 S0나 직접 조회만 다룬다. description 문구가 존재하는지는 실제로 행동 전 정지·승인이 되는지 입증하지 못한다. 이 경로는 기존 Step 0 승인 의미를 지키는 핵심이다(`SKILL.md:165-177`).
- 수정: 임시 fixture에서 “이름이 나온 파일 하나를 고치되 수행 중 별도 파일 삭제가 필요해지는” 시나리오를 추가한다. 삭제 전 스킬을 읽고, 사용자 명시 승인 전 파일 해시가 그대로이며, `list_profiles`·`create_agent`·`GRAPH.md` 없이 승인 요청에서 멈추는 것을 통과 조건으로 둔다. 실제 삭제 대신 mock 명령/임시 파일로 검사한다.

### D3. 높음 — A6 `run_eval.py` 명령은 현재 호스트에서 명세대로 실행 불가

- 위치: `SPEC.md:146`, `SPEC.md:218-223`
- 근거: 실제 Claude 공식 스크립트는 `--eval-set`이 필수인데 명세의 호출 인수에서 빠졌다(`claude skill-creator/scripts/run_eval.py:260-268`). 파일 경로로 직접 실행하면 `from scripts.utils`에서 `ModuleNotFoundError`가 났고(`run_eval.py:19`), 올바른 형태는 스킬 디렉터리에서 `python -m scripts.run_eval`이다. 또한 native Windows Python은 스크립트의 `select.select([process.stdout])`에서 `WinError 10093`이 재현됐다(`run_eval.py:85-108`). WSL의 `python3 -m scripts.run_eval --help`는 동작했다. `--model`에 “실행 세션 모델 ID”를 넣는 규칙도 Codex가 구현하면 Claude CLI가 받지 못하는 모델 ID가 된다.
- 수정: 실행 환경과 완전한 명령을 고정한다. 예: Claude 공식 skill-creator 디렉터리에서 WSL `python3 -m scripts.run_eval --eval-set <실행 디렉터리/eval.json> --skill-path <WSL 경로> --runs-per-query 3 --trigger-threshold 0.5 [--model <유효한 Claude 모델 ID>] > <결과.json>`. Codex 세션이면 `--model`을 생략해 Claude 설정 모델을 쓰고 결과에 실제 모델을 기록한다. WSL·Claude CLI 인증이 없으면 A6 미검증으로 실패 처리한다. `summary.failed = 0` 검사는 그대로 유효하다(`run_eval.py:247-255`).

### D4. 중간 — 직접 처리의 “실패 보고” 형태가 결정되지 않음

- 위치: `SPEC.md:32`, `SPEC.md:220`
- 근거: 직접 처리에는 결과·실패 보고 **파일** 의무가 없지만 실패 보고는 면제하지 않는다고만 한다. 구현자는 사용자 응답, 임시 파일, 기존 노드 경로 중 무엇인지 결정해야 하며, 잘못 해석하면 R1-4와 결과/실패 파일 규칙이 충돌한다.
- 수정: “직접 처리 실패는 사용자에게 원인·미완료 범위·미검증을 응답으로 보고하며 노드 실패 파일은 만들지 않는다. 스킬이 발동한 위임 경로만 기존 결과/실패 파일 규칙을 쓴다”를 R1과 A6에 넣는다.

### D5. 중간 — R7의 검토 재사용 금지가 기존 재검토 라운드와 혼동됨

- 위치: `SPEC.md:118-126`
- 근거: “검토 노드는 재사용하지 않는다”는 서로 다른 후속 노드 간 재사용 금지인지, 기존 동일 검토 노드의 2·3라운드 재사용까지 금지하는지 불명확하다. 기존 규칙은 여러 라운드에도 검토 노드 하나와 라운드별 파일을 쓴다(`level2.md:321-326`). 후자로 구현하면 검토 흐름 의미가 바뀐다.
- 수정: “R7의 **서로 다른 노드 간** 워커 재사용은 검토 노드에 적용하지 않는다. 기존 동일 검토 노드의 재검토 라운드·결과 파일 규칙은 바꾸지 않는다”로 한정한다. R6의 역할이 달라지는 재사용에는 R7-3~6의 기록·후속 브리핑 규칙이 모두 적용된다고 명시한다(`SPEC.md:104-112`, `SPEC.md:120-123`).

### D6. 중간 — A3가 최초 필수 Read까지 금지하는 문구

- 위치: `SPEC.md:78-82`, `SPEC.md:187-197`
- 근거: R4는 컨텍스트에 없는 절의 최초 Read를 허용한다. 반면 A3은 `직전에`·`읽는다` 검색 결과 “전부”가 조건형이어야 한다고 해 레벨 판정 뒤 최초로 `level2.md`를 읽는 정상 지시까지 금지하는 해석이 가능하다.
- 수정: A3-6을 “같은 정적 참조의 **재독**을 무조건 요구하는 지시 0건. 최초 Read와 컨텍스트에 내용이 없는 경우의 Read는 허용”으로 바꾸고, 검색 결과는 최초 Read/조건부 재독/변하는 파일 Read 세 부류로 판정한다.

### D7. 중간 — `--self-test` 뒤 `git status` 조건이 기존 변경을 오판

- 위치: `SPEC.md:203-216`
- 근거: 현재 작업 트리에는 이미 `AGENTS.md` 변경이 있다. “실행 뒤 저장소 작업 트리에 변화가 없다(`git status`)”를 깨끗한 상태 요구로 구현하면 self-test와 무관한 사용자 변경 때문에 실패하고, 반대로 사후 상태만 보면 self-test가 기존 파일을 바꿨는지 구분하지 못한다.
- 수정: 실행 전후 `git status --porcelain=v1 --untracked-files=all` 출력을 저장해 문자 단위로 같음을 확인하고, 추적 파일은 필요하면 `git diff --no-ext-diff` 전후 해시도 비교한다. self-test 임시 디렉터리는 저장소 밖 또는 무시 경로에 만들고 종료 시 제거한다.
