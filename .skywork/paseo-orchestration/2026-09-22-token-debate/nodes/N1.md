# N1 — 자문 1라운드 독립 판단

결론: 문서 길이보다 불필요한 워커 기동과 팀장 왕복을 먼저 줄인다. 조건부 위임은 효과가 크지만 역할·승인 적용 경로까지 바꾸는 제품 정책 변경이다. 다른 참가자 의견은 읽지 않았다. 아래 내용은 제안이며 구현 승인이 아니다.

근거 경로: `SKILL.md`, `references/`, `assets/`, `scripts/`는 모두 `plugins/paseo-toolkit/skills/agent-orchestration/` 기준이다. `presets.md`는 `plugins/paseo-toolkit/references/presets.md`, `AGENTS.md`는 저장소 루트다. `FEEDBACK.md`는 이 실행 디렉터리의 입력 파일이다.

## 1. 8개 항목 판정과 절감 우선순위

실행별 사용량 자료가 없어 **실측 순위는 산출할 수 없다**. 다음은 작은 요청과 연속 개발 작업이 반복되는 사용을 가정한 예상 순위다. 순위와 효과 크기는 모두 추정이며 작업 구성·캐시 적중률에 따라 달라진다. 기동 절감 효과들은 서로 겹치므로 합산하지 않는다.

| 예상 순위 | 피드백 항목 | 판정 | 비용 효과와 근거·조건 |
| --- | --- | --- | --- |
| 1 | 1. 조건부 사용 | 조건부 찬성 | 작은 작업에서 워커 초기 입력뿐 아니라 브리핑·그래프·기동 확인·인수 비용을 함께 없앨 가능성이 가장 크다. 현재 전면 위임은 `SKILL.md:8`, 기동 전 기록은 `SKILL.md:188`, 워커별 보고는 `SKILL.md:421`이다. 그러나 팀장 직접 처리는 `SKILL.md:23`, 팀장의 위임 전용 notes와 읽기·확인 권한(`presets.md:188`, `presets.md:214`)을 함께 재설계해야 한다. 단순히 description만 바꾸면 불완전하다. |
| 2 | 7. 후속 워커 재사용 | 조건부 찬성 | 새 세션의 초기 입력과 동일 파일 재탐색을 줄일 수 있다. 다만 같은 노드의 재작업은 이미 기존 워커 재사용이 기본이다(`references/level2.md:367`). 추가 이익은 **서로 다른 후속 노드**에 한정된다. 같은 파일이라는 이유만으로 재사용하지 말고 역할·프로필·권한·입력 전제의 일치를 요구한다. 검토 독립성 세 조건(`SKILL.md:332`)은 유지한다. |

| 4 | 4. 재독 금지 | 조건부 찬성 | 같은 내용을 도구 응답으로 반복 삽입하는 비용을 줄인다. 직전 Read 요구가 브리핑·기동 보고·기록에 있다(`SKILL.md:299`, `SKILL.md:425`, `references/level2.md:266`). 다만 “같은 세션이면 변경 전까지 금지”는 과하다. **현재 컨텍스트에 해당 절의 유효한 내용이 남아 있으면 재사용**으로 고친다. 압축·재개·부분 읽기로 내용이 없으면 필요한 절만 읽는다(`references/level1.md:48`). |

| 6 | 3. 핵심본 50% 축소 | 조건부 찬성 | 중복 제거와 사용 경로별 선택 읽기에는 찬성, 50%를 합격 조건으로 삼는 데는 반대한다. 값 이관·결과 경로·큐 운영은 대부분의 위임에 필요해 이동해도 다시 읽는다(`SKILL.md:257`, `SKILL.md:301`, `SKILL.md:216`). 브레인스토밍 상세는 이미 별도 문서이고(`SKILL.md:498`), 8절 실행도 요청 시에만 한다(`SKILL.md:457`). 줄 수보다 실제 경로의 총 입력·출력을 줄여야 한다. |
| 7 | 8. 도구 주입 조사 | 찬성 | 조사만으로 직접 절감은 없지만 초기 입력의 원인을 확인하는 가치가 있다. 소스는 설정이 새 세션에 도구를 주입한다고만 설명한다(`SKILL.md:58`). 워커별 주입 여부·도구 정의 크기·지연 로딩·캐시 사용량은 이 대상 파일만으로 확인할 수 없다. 전역 비활성화는 팀장 도구까지 끊을 수 있으므로 조사 결과 없이 대안으로 확정하면 안 된다. |

## 2. 지배 비용과 올바른 측정 지표

비용은 모델별로 `비캐시 입력 × 단가 + 캐시 입력 × 단가 + 출력 × 단가`를 합산해 비교한다. 추론 토큰이 별도 계측·과금되면 그 항도 포함한다. **원시 토큰량, 청구 비용, 지연 시간은 다른 지표**다. 현재 제공된 자료에는 실제 요청별 입력·출력·캐시 수치나 청구 정보가 없으므로 어느 항이 지배적인지 확정할 수 없다. 가격·캐시 정책도 이번 파일 조사로 검증하지 않았다.

구조상 예상은 다음과 같다.

- **짧은 요청:** 워커 하나의 고정비와 그 워커를 운영하는 팀장 호출이 작업 자체보다 커질 가능성이 높다. 두 비용은 함께 발생하므로 SKILL 길이만 줄여서는 해결되지 않는다. 프로필·워크스페이스 조회, 생성, 모델 확인, 기록, 결과 인수가 남는다(`SKILL.md:67`, `SKILL.md:79`, `SKILL.md:275`, `SKILL.md:445`).
- **여러 단계의 긴 실행:** 팀장 호출 수와 매 호출의 누적 컨텍스트, 여러 워커의 중복 탐색·출력·추론이 유력하다. 캐시가 잘 적중하면 고정 문서보다 매번 새로 만드는 브리핑·그래프·판정 출력과 추론의 비중이 커질 수 있다. 캐시가 부실하면 누적 입력과 새 워커 초기 입력이 더 무겁다. 어느 쪽도 실제 사용량 없이 단정하지 않는다.
- **프롬프트 캐시:** 비용을 줄이는 변수이지 낭비를 없애는 장치가 아니다. 새 워커라고 초기 입력이 모두 비캐시인 것도, 같은 세션이라고 전부 캐시인 것도 가정하지 않는다. 반복되는 접두부와 변경되는 입력을 나눠 계측해야 한다. 문서를 다시 Read하면 같은 내용이 새 도구 응답으로 추가되므로 기존 문맥의 캐시 재사용과 구분한다.
- **Read 횟수:** 독립된 원인보다 입력 증가와 모델 재호출을 만드는 수단이다. 한 번에 문서 전체를 읽는 방식이 필요한 절을 두 번 읽는 방식보다 비쌀 수 있다. Read 건수만 최소화하지 않는다. 팀장 “턴”도 사용자 왕복 수와 실제 모델 호출 수를 분리해 센다.

현 파일의 `.NET String.Length` 실측은 SKILL 19,243자, references 전체 41,793자, 합계 61,036자다(개행 포함, 토큰 수 아님). SKILL + level2 + graph-patterns + FORM은 48,058자다. 실패 문서는 사건 발생 시 읽으므로 61,036자를 매 레벨 2 실행의 필수 입력으로 잡을 수 없다(`references/level2.md:7`, `references/level2.md:9`). “매 요청 로드”와 “매 요청 동일한 비캐시 비용”도 동일하지 않다(`FEEDBACK.md:13`).

권장 비교 단위는 **동일 수용 조건을 통과한 요청 1건의 팀장+전체 워커 총비용**이다. 작은 조회, 정형 수정, 구현+검토, 실패 재개를 동일 입력으로 비교하고, 첫 실행과 캐시가 유지된 반복 실행을 구분한다. 워커 신규 생성 수·팀장 모델 호출 수·비캐시/캐시 입력·출력/추론·완료 시간·재작업 수를 함께 기록한다. 정확성·승인 준수·검토 독립성·실패 차단이 후퇴하면 비용 절감으로 합격시키지 않는다. 50%는 편집 참고치일 뿐 수용 조건을 대체하지 못한다.

## 3. 놓친 큰 낭비 후보와 대안

아래 비용 크기 역시 구조에서 추정한 것이며 발생 빈도는 확인하지 않았다.

1. **역할 경계를 과하게 나눠 생기는 탐색·실행 왕복.** 묶음 명시 규칙은 정확 검색과 지정 명령에 치우쳐 있다(`SKILL.md:133`). 구현과 디버깅 notes는 이미 검증·최소 수정을 포함한다(`presets.md:266`, `presets.md:276`). 같은 역할이 수행 가능한 재현→수정→자체 테스트를 불필요하게 다른 워커로 쪼개지 않는 예시를 둔다. 독립 리뷰는 별도 유지한다. 기존 역할 안이면 승인·독립성·결과·실패 의미를 바꾸지 않는다.
2. **독립 질문을 한 개씩 중계하는 사용자 왕복.** 현재 서로 독립된 결정도 한 번에 하나만 묻는다(`references/level2.md:138`). 의존 없는 질문만 묶고 질문-답변 원문 대응은 보존하면 팀장·작성자 재호출을 줄일 수 있다. 확정 전 다음 단계 금지는 그대로 유지한다. 단, 현재 문답 절차의 의미 변경이므로 합의가 필요하다. 사용자 응답을 생략하거나 승인으로 추정하는 제안이 아니다.
3. **patch 생성→팀장 적용→검토자의 역적용·복원.** 2라운드부터 추가 생성·적용과 실패 경로가 생긴다(`references/level2.md:350`, `assets/review-briefing.md:8`). 범위가 확정된 수정은 원래 작성자가 직접 수정하고 독립 검토자가 현재 파일과 필요한 차이를 검토하는 대안이 있다. **현재 patch 산출 규칙과 적용 실패의 예산 처리 의미를 바꾸는 제안**이다. 승인된 내용의 해시·수정 범위·라운드별 검토 증빙을 보존하는 설계 없이 적용하면 안 된다.
4. **역할별 고정 추론 등급과 실제 작업 크기의 불일치.** 경량 구현도 기본 high이고 팀장도 high 고정이다(`presets.md:188`, `presets.md:199`, `presets.md:216`). 운영 문장만 줄여도 라우팅·형식 준수 판단을 매번 높은 등급으로 하면 절감이 제한될 수 있다. 현재 모델별 성능·비용은 검증하지 않았으므로 자동 하향 대신 대표 과제의 품질/비용 비교 후 프로필 변경안을 승인받는다. 등급 임의 하향 금지(`presets.md:99`)를 깨는 자동 최적화는 제안하지 않는다.

## 4. 부작용·충돌과 채택 조건

- **1·2:** “애매하면 직접”은 크기 판정에만 적용해야 한다. 의존을 모르면 레벨 2인 `SKILL.md:152`까지 덮어쓰면 안 된다. 직접 경로에도 승인·실패 처리·필요한 텍스트 결과 보존을 명시해야 한다. 위임을 없애며 기존 결과 파일 의무까지 없애면 의미 변경이다. 이미 상시 프롬프트를 추가한 환경은 description 수정만으로 새 정책이 적용된다고 보장할 수 없다(`SKILL.md:457`, `SKILL.md:474`). 전역 설정은 이번 제안으로 자동 수정하지 않는다.
- **3·4:** 실행 경로·권한·승인·성공 여부 지시는 본문에 남기라는 저장소 규칙이 있다(`AGENTS.md:82`). 결과·실패 경로 분리와 실패 우선 같은 핵심까지 참조로 숨기지 않는다. 재독 금지는 현재 결과 파일·실패 파일·GRAPH 상태 조회에 적용하지 않는다. 이들은 정적 참조가 아니다(`references/failure-handling.md:224`).
- **5:** 행 추가는 mermaid에도 승인된 구조를 반영해야 한다(`references/level2.md:245`). 상태만 바꿀 때와 구분한다. 여러 전이를 일괄 기록하더라도 기동 전 행 작성·재시도/검토 횟수 증가·재지시 전 상태 전환 순서를 지켜야 한다(`references/level2.md:270`). 표 전체를 도구 출력으로 되돌려주면 절감이 사라진다. 원자적 쓰기 같은 기존 구현은 참고할 수 있지만 설정 백업·daemon reload까지 복제할 이유는 없다(`scripts/append_system_prompt.py:324`).
- **6:** 마일스톤 판정은 실험 뒤에 있다(`SKILL.md:105`). 스펙 때 낸 안은 잠정안으로 두고 실험 결과가 바뀌면 재판정해야 한다. 스파이크 생략 시 SPIKE.md를 만들지 않는 규칙과 판정안의 노드 결과 경로도 지켜야 한다(`references/level2.md:102`). SPEC.md에 합쳐 저장하면 **결과 파일 규칙 변경**이다. 공동 판정 상대를 바꾸는 것은 전문 역할 책임 변경이며 `presets.md:240`과의 정합성을 확인해야 한다.
- **7:** 단위 하나=워커 하나(`SKILL.md:92`)를 바꾸며, 노드별 labels(`SKILL.md:268`)와 중단·재개에서 한 agentId가 여러 노드를 가리키는 의미를 정해야 한다. 노드별 결과·실패 경로와 판정은 계속 분리한다. 완료된 이전 노드까지 실행 중으로 오판하거나 이전 실패를 새 노드에 적용하면 안 된다. 긴 세션의 오래된 전제와 누적 컨텍스트 때문에 무제한 재사용이 항상 저렴한 것도 아니다.
- **8:** 도구 주입 차단은 조사와 별도 결정이다. 팀장 연결·워커의 실제 필요 도구·호스트별 로딩 차이를 확인하고, 실패 시 권한 상승이나 다른 경로로 우회하지 않는다.
- **공통:** 피드백의 즉시 마이너 버전 증가(`FEEDBACK.md:81`)는 머지 직전 추천값을 승인받는 규칙(`AGENTS.md:53`)과 충돌한다. 자문 목적 승인은 버전·전역 설정·구현 승인으로 확대하지 않는다. 구조 변경 시 skill-creator 적용도 필요하다(`AGENTS.md:65`).

## 검증

`Get-Content`와 `rg -n`으로 입력 피드백, 스킬 본문·참조·브리핑·관련 스크립트 구간·프리셋·저장소 규칙을 대조했다. `ReadAllText(...).Length`와 정규식 검사로 결과 파일 8,000자 이하·판정 8개·인용 57개의 파일과 줄 존재·UTF-8 BOM 없음을 확인했다. 실제 워커 실험, 캐시/청구 계측, Paseo daemon 주입 구현 확인은 수행하지 않았으며 비용 효과를 실측 사실로 보고하지 않는다.
