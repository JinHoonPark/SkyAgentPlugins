# SPEC — agent-orchestration 토큰 효율화

대상은 `plugins/paseo-toolkit/skills/agent-orchestration/`(이하 스킬 디렉터리)다. `SKILL.md`·`references/`·`assets/`·`scripts/`는 스킬 디렉터리 기준, `presets.md`는 `plugins/paseo-toolkit/references/presets.md`다. "변경 전"은 커밋 `5e833be`의 파일이다.

## 1. 용어

- **직접 처리** — 팀장이 작업 자체를 워커 없이 수행한다. 파일을 만들거나 고치지 않았으면 스킬이 발동하지 않고, 고쳤으면 R1-7의 검토를 위해 발동한다.
- **Step 0 경량 경로** — 되돌리기 어려운 행동으로만 스킬이 발동해 승인만 받고 팀장이 수행하는 경로.
- **되돌리기 어려운 행동** — git 커밋·스테이징·푸시·태그·브랜치 삭제, 외부 전송, 파일·디렉터리 삭제, 저장소 밖 설정 변경.

## 2. 요구사항

### R1. 조건부 적용

대상: frontmatter `description`, SKILL.md 도입부·「리더가 직접 하는 일」·2절 독립 검토 개설 조건·5절 「검토는 만든 워커에게 맡기지 않는다」, `assets/review-briefing.md` 「고정 검토 가이드」의 적용 범위 문장, `presets.md`의 `team-lead` notes.

1. 팀장을 주어로 한 직접 지시("네가 직접 해")는 적용 판정 트리보다 먼저 처리한다. 단 Step 0·브레인스토밍 별도 트리거가 우선한다. 직접 지시와 워커 지시가 함께 있으면 사용자에게 확인한다.
2. 적용 판정은 아래 트리로 한다. SKILL.md 도입부에는 코드블록 원문 그대로 둔다. `description`에는 트리의 문구·번호를 그대로 옮기지 않아도 되고, 아래 의미를 짧은 동등 표현으로 빠짐없이 담는다.
   - 우선순위: 위에서부터 보고 처음 걸리는 곳에서 멈춘다.
   - 경계: 적용 조건 1~5(4의 "5개를 넘는다" 수치 포함), 그 밖은 팀장이 직접 처리, 아래 세 예외 문장(검색식 한 번의 위치 확인, 종료 코드·통과 여부만 확인, 팀장 직접 수정 뒤의 독립 검토).
   - 전환: 직접 처리 중에 2·3·5에 해당하게 되면 그 시점에 적용으로 바꾼다. 사용자가 전환을 지시하면("이제 워커한테 맡겨", "오케스트레이션으로 전환해") 그 시점에 트리 1로 적용하고 전환 전 수정은 되돌리지 않는다. 수행 중 자동 전환은 보장하지 않으며, 실측(A8-5)은 사용자 지시 전환으로 판정한다.
   - 파일을 고치지 않는 직접 처리는 SKILL.md를 읽지 않으므로(R1-10) 그 경로에 필요한 승인·검증·실패 보고 의무와 수행 중 전환 조건(위 전환, 되돌리기 어려운 행동 전의 Step 0 발동, 파일을 고친 뒤의 R1-7 발동)은 본문으로만 옮기지 않고 `description`에 둔다.
   ```text
   스킬 적용 판정 — 요청 문장만 보고 위에서부터, 처음 걸리는 곳에서 멈춘다
   1. 사용자가 워커에 맡기라고 지시했다                         → 적용
   2. 요청에 이름이 나오지 않은 파일을 찾아 읽어야 한다           → 적용
   3. 로그 파일이나 전체 빌드·테스트 출력을 읽고 해석해야 한다     → 적용
   4. 요청에 이름이 나온 대상 파일이 5개를 넘는다                 → 적용
   5. 요청이 설계·구현·검토처럼 단계마다 따로 산출물을 내며
      이어지는 여러 단계를 거쳐야 한다                          → 적용
   6. 그 밖                                                    → 팀장이 직접 처리
      직접 처리 중에 2·3·5에 해당하게 되면 그 시점에 적용으로 바꾼다.
   검색식 한 번으로 위치만 확인하는 것은 2의 "찾아 읽기"가 아니다.
   명령의 종료 코드·통과 여부만 확인하는 것은 3이 아니다.
   팀장이 직접 고친 뒤 붙이는 독립 검토는 5의 단계로 세지 않는다.
   ```
3. 이 트리가 "서로 독립인 작업 단위가 둘 이상이면 적용"(병렬 조건)을 대체한다. 적용 뒤 레벨 1·2 판정은 어느 트리 항목으로 적용됐든 2절 Step 1~5가 그대로 맡는다.
4. "독립 검토"·"다른 에이전트에게 검토"처럼 작성자와 다른 수행자의 검토를 요구하는 지시는 트리 1(워커에 맡기라는 지시)로 분류한다.
5. 되돌리기 어려운 행동(R2)과 브레인스토밍 진입(10절)은 트리 밖의 별도 트리거로 유지한다.
6. 직접 처리한 작업 자체에는 `GRAPH.md`·결과 파일·실패 보고 파일 의무가 없다. 승인(R2)·검증·실패 보고는 면제하지 않는다. 직접 처리 실패는 사용자에게 원인·미완료 범위·미검증을 응답으로 보고하며 노드 실패 파일은 만들지 않는다. 스킬이 발동한 위임 경로와 R1-7의 검토 노드만 기존 결과/실패 파일 규칙을 쓴다.
7. 팀장이 직접 처리하며 파일을 만들거나 고쳤으면(삭제만 한 경우와 경미한 수정 제외, 직접 지시로 처리한 경우 포함) 작업을 마친 뒤 이 스킬로 리뷰 역할 워커의 독립 검토를 붙인다.
   - 경미한 수정 — 한 파일의 기존 상수·설정값 한 줄 변경을 실행·테스트로 확인한 경우. 리뷰 워커 검토 대신 완료 보고에 생략 사실과 확인 명령·종료 코드를 적는다.
   - 검토 독립성 3조건을 그대로 적용한다 — 작성자인 팀장과 다른 `agentId`, 작성자의 대화·보고를 입력으로 주지 않음, `notes`가 검토를 허용하는 프로필. 변경 내용에 관한 입력은 사용자 요청 원문·확정 제약·대상 경로로 한정하고 팀장의 보고·대화·해결 방향은 싣지 않는다. review-briefing의 프로필 notes, 결과/실패 경로, 도구·권한, 출력 제한·보고 형식은 그대로 싣는다.
   - 합격 기준 자리에는 사용자 요청 원문과 확정 제약을 그대로 싣고, 고정 검토 가이드 다섯 항목을 모두 적용한다.
   - 검토 노드 하나를 레벨 1 절차(프로필 선택·`assets/review-briefing.md`·결과/실패 파일·`GRAPH.md`·기동 보고)로 기동한다. 2절 Step 2의 역할 분리로 보지 않으며 계획 승인 화면을 두지 않는다.
   - 지적 반영은 작성자인 팀장이 대상 파일을 직접 고친다(patch 왕복은 작성 워커에만 적용). 재검토는 기존 검토 라운드 상한과 라운드별 결과 파일 규칙을 따른다.
   - 직접 처리 중에 트리 2·3·5로 적용으로 바뀌면, 그때까지 팀장이 만들거나 고친 파일은 되돌리지 않고 현재 상태 그대로 적용 경로 작업의 입력으로 넘긴다. 이 파일들의 검토는 적용 경로의 실행·테스트 결과까지 모두 나온 뒤(재검토도 재실행 결과 뒤) 한 번 붙이고, 적용 경로가 만든 `GRAPH.md`가 있으면 그 파일에 검토 노드 행을 더한다. 레벨 2의 구현 뒤 독립 검토가 이 파일들을 대상에 넣었으면 따로 붙이지 않는다.
   - SKILL.md 2절의 독립 검토 개설 조건(현재 "셋뿐이다")에 이 경우를 넷째로 더하고, 5절 검토 적용 범위 문단과 「고정 검토 가이드」의 적용 범위 문장을 맞춘다.
8. 무조건 위임 문구를 없앤다: "작업 크기로 예외를 두지 않는다", "할 일만 적힌 요청은 전부 위임 대상", "파일과 설정은 대상이 이 세션 것이어도 워커에 맡긴다".
9. 유지: 위임 여부를 다시 묻지 않음, 라우팅은 팀장만·워커 재위임 금지, 적용 뒤의 1~10절 절차.
10. 적용 여부는 `description`만으로 정한다. 파일을 고치지 않는 직접 처리 경로는 SKILL.md를 읽지 않는다.
11. `presets.md`의 `team-lead` notes 원문을 profile-setup으로 등록한 실제 notes와 같은 문구로 고친다(C6).

### R2. Step 0 경량 경로

대상: `description`, SKILL.md 도입부와 2절 「Step 0」, `references/FORM.md` 「발화 지점 배정」.

1. `description` 트리거에 되돌리기 어려운 행동을 넣는다. 사용자 요청뿐 아니라 수행 중 새로 계획한 행동도 행동 전에 발동하게 쓴다.
2. 본문에 아래 문구를 둔다.
   > 직접 처리 여부와 무관하게 git 커밋·스테이징·푸시·태그·브랜치 삭제, 외부 전송, 파일·디렉터리 삭제, 저장소 밖 설정 변경을 수행하기 전에 Step 0을 적용한다. 같은 범위의 명시적 지시는 승인으로 재사용한다. 승인 점검만 해당하면 전제 조회·위임·실행 기록 절차로 진입하지 않는다.
3. 경량 경로는 워커·`GRAPH.md`·`list_profiles`·`list_workspaces` 없이 승인만 받고 팀장이 수행한다. 승인 강도는 기존과 같다 — 무응답·답변 누락·주제 전환·다른 작업 지시는 승인이 아니고, 팀장이 추가한 행동은 언제나 승인 대상이다. 경량 경로로 파일을 고쳤으면 수행 뒤 R1-7을 따른다.
4. R1 트리와 Step 0은 SKILL.md 도입부(본문 첫 절)에 두고, 2절 트리의 Step 0은 그 절을 가리킨다.
5. 경량 경로의 승인 요청을 「발화 지점 배정」에 즉시 (1, 2)로 넣는다.
6. Step 0용 별도 스니펫 파일을 만들지 않는다.

### R3. SKILL.md 재배치

대상: SKILL.md 전 절, `references/level1.md`, `references/level2.md`, 새 `references/system-prompt.md`.

1. SKILL.md 크기 비율 목표를 두지 않는다. 판정은 A1로 한다.
2. 값 이관 표, 결과/실패 경로 분리, 실패 보고 우선, 검토 독립성 3조건은 SKILL.md에 남긴다.
3. FORM.md 견본을 SKILL.md에 옮겨 적지 않는다.
4. 절별 배치:

| 절 | SKILL.md에 남긴다 | 옮기거나 합친다 |
| --- | --- | --- |
| 도입·리더·발화 | 적용/직접 경로, 재위임 금지, 승인, 침묵 원칙 | 화면은 FORM |
| 1 전제 점검 | 도구 로드, notes 경계, 재조회 조건, 워크스페이스, 대기 수단, 프로필 상태 A·B·C | "provider를 추측하지 않는다" 반복을 한 번으로 |
| 2 레벨 판정 | Step 0~6, 단계 순서·확정 게이트·공동 판정, 독립 검토 개설 조건, 묶음 경계 | 상세 그래프·단계 전이 중복은 level2로 |
| 3 레벨 1 | 큐 상한, 기동·판정 순서, 기록 시점, 상태 핵심 | 재개·뒤늦은 의존 발견은 level1 |
| 4 프로필 | 역할↔프로필 해석, notes 명시 허용, 값 이관 표, 실제값 확인, 자문 승인 조건·대체 금지 | 등급·폴백 상세는 `presets.md` 참조 |
| 5 브리핑 | 포함·제외 목록, 검토 독립성 3조건, 기본 결과/실패 경로, 분리·보존, 실패 우선, 본문 제한 | 템플릿은 assets, 라운드 경로는 level2 |
| 6 개입/실패 | 범위 변경 승인, 기존 승인 재사용, 실패 우선, 재시도 조건·한도, 권한 우회 금지 | 세부는 failure-handling 유지 |
| 7 취합 | 기동 보고 의무, 증빙 대조, 결과 인수와 독립 검토 구분, 후속 보완 경계 | 출력 형식은 FORM 유지 |
| 8 상시 프롬프트 | 사용자 요청 한정, dry-run 제시, 명시 승인, 새 세션 적용, 읽는 시점 | 옵션·실행·복구 상세는 `references/system-prompt.md` |
| 9 레벨 2 | 진입 조건, 계획 승인 핵심, level2 읽는 시점 | 공통 기록·실패 반복은 정본 참조로 |
| 10 브레인스토밍 | 진입 질문, 승인/거절 분기 | 추가 분리 없음 |

5. 같은 규칙은 한 곳(정본)에 두고 나머지는 참조로 바꾼다. level1·level2에 중복된 `GRAPH.md` 공통 규칙도 정본 하나로 모으되, 위치는 A1의 L1·L2 조건을 함께 만족하는 곳이다.
6. 새 참조 문서는 `references/system-prompt.md` 하나로 한정한다.

### R4. 재독 금지

대상: SKILL.md(규칙 1회)와 읽기 시점 지시가 있는 곳 전부(SKILL.md 5·7절, level1.md, level2.md, `references/brainstorming.md`).

1. 규칙 문구: "현재 컨텍스트에 그 절의 내용이 남아 있으면 다시 읽지 않는다. 압축·재개·부분 읽기로 없으면 필요한 절만 읽는다."
2. 결과 파일·실패 보고 파일·`GRAPH.md` 상태처럼 실행 중 바뀌는 파일에는 적용하지 않는다.
3. "직전에 읽는다" 지시를 이 규칙과 충돌하지 않는 조건형으로 고치고, 적용하는 양식·규칙은 그대로 둔다.

### R5. `scripts/graph_update.py`

대상: 새 `scripts/graph_update.py`, `GRAPH.md` 갱신을 지시하는 SKILL.md 3절·level1.md·level2.md·failure-handling.md.

1. 명령은 셋이다.
   - **생성** — 경로, 팀장이 넘기는 mermaid 블록(표준 입력 또는 파일), 노드 행들로 버전 줄·mermaid·노드 표를 쓴다. 이미 있는 경로에는 쓰지 않는다.
   - **행 추가** — 노드 행 1개와 그 노드의 mermaid 줄(노드 정의 줄과 관계선)을 받아 표 끝과 mermaid 닫는 펜스 앞에 한 번에 쓴다. 노드 정의 줄이 없으면 쓰지 않는다("노드 추가는 mermaid와 표에 함께 반영" 규칙 유지).
   - **열 변경** — 노드 ID와 `열=값` 하나 이상(예: `상태=완료 agentId=…`)으로 그 행의 지정 셀만 바꾼다. mermaid는 어떤 경우에도 바꾸지 않는다.
2. 형식은 FORM 「실행 기록」 견본과 같다 — 맨 위 `버전 : {값}`, 14열 헤더의 이름·순서, 셀 구분.
3. 버전은 스크립트 위치 기준 플러그인 루트의 `.claude-plugin/plugin.json`, 실패하면 `.codex-plugin/plugin.json`의 `version`이다. 둘 다 실패하면 `버전 : 읽지 못함`으로 쓰고 생성을 계속한다. 추측하지 않는다.
4. 대상 노드 없음·노드 ID 행 중복·이미 있는 ID로 행 추가·모르는 열·`|`나 줄바꿈이 든 값·다섯 상태(`대기`·`실행 중`·`완료`·`실패`·`생략`) 밖의 상태는 파일을 바꾸지 않고 실패한다. 부분 기록은 없다.
5. UTF-8로 읽고(BOM 허용) BOM 없는 UTF-8로 쓰며 기존 개행 방식을 유지한다.
6. 표준 라이브러리만 쓴다. stdout에는 요약만 내고 `GRAPH.md` 전체를 출력하지 않는다. 진단은 stderr다. 모든 예외를 잡아 트레이스백 없이 0이 아닌 종료 코드로 끝내며, 입력을 기다리거나 세션을 멈추지 않는다.
7. 문서의 `GRAPH.md` 생성·행 추가·열 변경 지시를 스킬 디렉터리 기준 `python scripts/graph_update.py …` 호출로 바꾼다. 형식·기록 시점·기록 내용 규칙은 바꾸지 않는다.
8. 오류 처리: 진단에 교정 근거가 있을 때만 인수를 고쳐 다시 부른다. 같은 진단이 반복되거나 기록이 실제와 어긋나면 기존 실패 게이트(「팀장 발화」 조건 3·4)로 처리한다. 필요한 기록 없이 다음 워커를 기동하지 않는다. 직접 편집은 스크립트를 실행할 수 없는 환경에만 같은 형식으로 한다.
9. 테스트는 스크립트 안의 `--self-test` 옵션이다. 저장소 밖 임시 디렉터리에서 A5의 G1~G11을 실행해 항목별 결과를 보고하고, 끝나면 임시 디렉터리를 지운다. 별도 테스트 파일은 만들지 않는다.

### R6. 판정 통합

대상: SKILL.md 2절 공동 판정 문단, level2.md 「공동 판정과 판정안」·노드 표 「결과 파일」 행, `presets.md`의 `spec` notes.

1. 사용자가 SPEC.md를 명시적으로 확정한 뒤, spec notes가 스파이크 필요성 판정을 명시적으로 허용하면 같은 스펙 워커가 판정안을 별도 노드 결과 파일 `nodes/{판정 노드 ID}.md`(실패 보고는 같은 ID의 `.failure.md`)에 낸다. SPEC.md에 섞지 않고 실험 설계는 하지 않는다.
2. 판정안은 기존 항목(실패 시 성립하지 않는 것, 현재 근거, 확인할 질문)과 필요·생략·정보 부족을 담는다.
3. 팀장 공동 판정을 유지하고 팀장 단독 판정은 금지다.
4. 스펙이 바뀌면 같은 워커가 판정안을 갱신한다.
5. 스파이크가 필요하면 기존 절차(스파이크 설계·실행 역할, 사용자 확인, 그 뒤 마일스톤 역할의 필요성 판정)를 따른다. 마일스톤 판정은 스파이크 뒤다.
6. 스파이크가 생략이고 spec notes가 마일스톤 필요성 판정까지 명시적으로 허용하면 같은 워커에 이어 묻는다(별도 노드 결과 파일, 기존 마일스톤 판정안 항목).
7. notes가 허용하지 않으면 기존 전문 역할 경로다.
8. 이 역할이 달라지는 재사용에도 R7-3~6의 기록·재개·후속 브리핑 규칙이 모두 적용된다. R7-1의 "같은 역할·같은 대상 파일" 조건은 요구하지 않는다.
9. `presets.md`의 `spec` notes 원문을 profile-setup으로 등록한 실제 notes와 같은 문구로 고친다(C6).

### R7. 워커 재사용

대상: SKILL.md 7절 「결과 인수」, level2.md 「기동과 판정」·「재개」, failure-handling.md 「재개」, FORM 「발화 지점 배정」·「완료 보고」.

1. 조건(모두): 앞 노드와 같은 역할·같은 대상 파일, 순차(앞 노드 → 후속 노드 엣지, 앞 노드 완료 뒤 기동), 승인된 범위(승인 그래프의 노드, 범위 변경 없음), 앞 에이전트가 프롬프트를 받을 수 있음.
2. R7의 서로 다른 노드 간 워커 재사용은 검토 노드에 적용하지 않는다. 기존 동일 검토 노드의 재검토 라운드·결과 파일 규칙은 바꾸지 않는다. 검토 독립성 3조건은 그대로다.
3. 후속 노드는 자기 노드 ID·`GRAPH.md` 행·결과 파일·실패 보고 경로를 따로 가지며, 그 행의 `agentId`에 재사용한 ID를 쓴다. 한 `agentId`가 여러 행에 있을 수 있고 그중 `실행 중` 행은 동시에 하나뿐이다.
4. `labels.node`는 생성 때의 노드 ID로 두고 바꾸지 않는다. 한 에이전트의 노드들은 `GRAPH.md` 행으로만 구분한다.
5. 재개 때 에이전트가 실행 중이면 그 `agentId`의 `실행 중` 행이 진행 중 노드다. 나머지 행은 각자의 결과·실패 보고 파일로만 판정한다.
6. 후속 지시는 `send_agent_prompt`로 보내고 5절 포함 목록의 노드별 항목(목표·수정 가능 대상·합격 기준·입력 경로·결과/실패 경로·도구·출력 제한·보고 형식)을 싣는다. 신분 줄과 프로필 notes는 현재 문맥에 유효하게 남아 있을 때만 생략하고, 압축·재개·프로필 변경 시에는 그 두 항목만 다시 싣는다.
7. 앞 에이전트가 `closed`·`error`면 기존 절차대로 새로 기동한다.
8. 재사용에는 기동 보고를 내지 않는다. 「발화 지점 배정」에 "침묵 → 완료 보고"로 넣고, 「완료 보고」 필수 항목에 재사용한 노드와 `agentId`를 더한다.
9. 「재작업」(같은 노드 산출물 재수정) 규칙은 바꾸지 않는다.

### R8. 질문 묶기

대상: level2.md 「스펙 문답」, SKILL.md 2절 스펙 질문 문단.

1. 규칙 문구: "답이 서로 독립인 질문은 번호를 붙여 한 번에 묻고 질문↔답 원문 대응을 보존한다. 하나라도 종속이면 순차. 필수 답이 모두 오기 전 다음 단계를 기동하지 않는다. 미응답은 승인이 아니다."
2. "한 번에 서로 독립된 결정 하나만 묻는다"를 대체한다. 결과·범위·수용 판정이 달라지는 지점만 묻고 근거로 답할 수 있는 것은 묻지 않는 규칙은 유지한다.
3. 사용자 답변은 질문 번호와 묶어 원문 그대로 같은 작성 워커에게 전달한다. 사용자 확정 게이트는 그대로다.

### R9. 의미 불변과 의도 변경

1. 의도적으로 바꾸는 동작은 여섯뿐이다 — 조건부 적용(R1), 직접 수정 뒤 독립 검토(R1-7), Step 0 경량 경로(R2), 판정 통합(R6), 워커 재사용(R7), 질문 묶기(R8).
2. 그 밖의 규칙은 위치·문장이 바뀌어도 의미를 바꾸지 않는다. 승인 게이트, 검토 독립성, 결과 파일 규칙, 실패 처리, `GRAPH.md` 형식·기록 시점, 발화 규칙이 여기 든다.
3. R4(읽기 조건)·R5(`GRAPH.md` 편집 수단)는 적용 양식·기록 결과가 같아 의미 불변이다.

## 3. 제약

- **C1 버전** — 개발 중 두 `plugin.json`의 `version`을 바꾸지 않는다. main 머지 직전에 major·minor·patch와 추천 버전을 사용자에게 제시하고, 승인받아 두 파일에 함께 반영한다.
- **C2 구조 변경** — 파일 추가·분리는 `skill-creator` 없이 AGENTS.md §6 골자를 따른다(SKILL.md 500줄 미만, 분리 파일은 SKILL.md에서 읽는 시점과 함께 링크, 참조 깊이 한 단계, frontmatter는 `name`·`description`만, 부가 문서 금지, 견본은 FORM.md `##` 절).
- **C3 트리거 평가** — `description` 발동 조건 변경은 A6의 트리거 평가(발동해야 할 질의와 발동하면 안 될 질의 세트)로 확인한다.
- **C4 공용 스킬** — 핵심 동작은 스킬 본문·스크립트에 둔다. `${CLAUDE_PLUGIN_ROOT}`·사용자 홈·드라이브 문자·절대 경로 금지, 파일 참조는 스킬 디렉터리 기준 상대 경로.
- **C5 문체** — 한국어 단정형 문체와 1~10절 번호 체계를 유지한다.
- **C6 저장소 밖 전제** — 이 변경은 profile-setup으로 바꾸는 두 notes와 맞물린다: team-lead notes(현재 "작업 자체는 담당 워커에게 맡긴다")는 조건부 적용에 맞게, spec notes는 스파이크(생략 시 마일스톤) 필요성 판정 허용으로. 이 notes가 적용되기 전에는 R1·R6이 실제 라우팅에 반영됐다고 보고하지 않는다. `presets.md`의 두 notes는 그 실제 문구를 따른다(R1-11, R6-9).
- **C7 실행 환경 전제** — `daemon.mcp.injectIntoAgents=true`(전역)라 워커 세션에도 Paseo 도구가 주입된다. 에이전트 단위 차단은 없고 provider 단위 `paseoTools {enabled, disabledTools}`만 있다. 재위임 금지는 도구 차단이 아니라 스킬·브리핑 규칙으로 유지한다.
- **C8 실측 시점** — A8은 C1 버전 승인·설치본 갱신 뒤, 머지 전에 한다.

## 5. 수용 기준

### A1. 경로별 정적 측정

- 문자 수: UTF-8로 읽어 CRLF를 LF로 바꾼 뒤 Python `len`. 바이트·UTF-16 길이를 쓰지 않는다.
- 본문·참조 로드 = 스킬 발동 시 SKILL.md 전체 + 그 경로에서 읽으라고 지시된 파일·절(절은 그 헤딩부터 같은 단계 이상의 다음 헤딩 전까지). 재독 포함 합과 고유 합을 함께 적는다.
- Read 횟수 = SKILL.md 로드를 뺀, 스킬 파일(references·assets·scripts·`presets.md`)을 읽는 호출 수.
- `description`의 전후 문자 수와 차이를 별도 열로 적는다.
- 읽기 목록은 변경 전·후 각각의 규칙으로 만든다.

| 시나리오 | 통과 조건(변경 후) |
| --- | --- |

### A2. `GRAPH.md` 갱신

- 변경 후 문서의 `GRAPH.md` 생성·행 추가·열 변경 지시가 전부 `graph_update.py` 호출이고, 실행 불가 환경 외에 `GRAPH.md`를 읽고 고치라는 지시가 0건이다(검색).
- L1·L2에서 `GRAPH.md` 갱신 1회가 도구 호출 1회다.

### A3. 링크·절 참조·구조

스크립트로 확인해 전부 통과한다.
1. SKILL.md·`references/*.md`·`assets/*.md`의 마크다운 링크 대상이 그 파일 기준으로 존재한다.
2. 백틱 경로(`references/…`, `assets/…`, `scripts/…`)가 스킬 디렉터리 기준으로 존재한다.
3. 「…」나 `## …`로 지목한 절이 지목한 파일에 헤딩으로 존재하고, "N절" 참조가 SKILL.md의 `## N.` 헤딩으로 존재한다.
4. `references/system-prompt.md`와 `scripts/graph_update.py`가 SKILL.md에서 직접 참조되고 같은 문단에 읽거나 실행하는 시점이 있다.

- 트리거 평가 방법: 질의의 한 회 실행마다 아래를 따른다.
  1. 저장소 밖에 격리 임시 폴더를 새로 만들고 평가 대상 스킬 디렉터리를 그 폴더의 `.claude/skills/agent-orchestration/`에 실제 스킬로 복사한다.
  2. 그 폴더에서 `claude -p <질의> --output-format stream-json --setting-sources project,local --strict-mcp-config --model <모델>`을 실행한다. `<모델>`은 유효한 Claude 모델 ID이고 결과에 기록한다. 출력·실행 제어 옵션(`--verbose` 등)은 더할 수 있으나 설정·스킬·MCP 로드를 바꾸는 옵션은 더하지 않는다.

  4. 출력 초기 정보에 대상 스킬이 없거나 설치본 paseo-toolkit이 보이거나 실행이 오류로 끝나면 그 회는 질의 실패다. stderr 로그에 질의를 특정한 `Warning: query failed` 줄을 남긴다.
  5. 끝나면 임시 폴더를 지운다.
  - 질의별 발동 비율이 발동 기대 질의는 0.5 이상, 비발동 기대 질의는 0.5 미만이면 `pass` = true다. 결과 JSON에는 질의별 `pass`와 `summary.failed`(`pass` = false 질의 수)를 담는다.
  - Claude CLI나 그 인증이 없으면 A6은 미검증 실패다.
- 평가 세트(실제 한국어 표현의 구체적 질의): 발동 8범주(트리 1~5, 독립 검토 요구, 되돌리기 어려운 행동, 브레인스토밍) 각 2개 이상, 비발동 4범주(검색식 한 번의 위치 확인, 이름 나온 5개 이하 파일 읽기·설명, 종료 코드·통과 여부만 확인, 간단한 질문) 각 2개 이상·합계 9개 이상, 비발동의 절반 이상은 발동 범주와 단어를 공유하는 근접 사례. 이 평가는 첫 도구 호출로만 발동을 판정하므로, 파일을 고치는 직접 처리 요청(R1-7로 수정 뒤 발동)은 평가 세트에 넣지 않고 A8-3으로 확인한다. 직접 지시·워커 지시가 함께 있는 질의도 넣지 않고 A8-4로 확인한다. 반드시 넣는 질의 — 비발동: "`parseConfig` 어디 있어?", "네가 직접 이 에러 원인 찾아줘", "`cache.py`의 캐시 설계 설명해줘" / 발동: "테스트 돌리면 `KeyError: 'timeout'`이 나는데 이 에러 원인 찾아줘", "docs/ 아래 30개 파일 링크 통일해줘", "이 빌드 로그 분석해줘", "`cache.py`에 만료 정책을 설계하고 구현해줘", "네가 직접 build 폴더 지워줘", "네가 직접 브레인스토밍하자", "`a.py` 고치고 리뷰 에이전트한테 독립 검토 받아줘", "`a.py` 수정은 이제 워커한테 맡겨", "`cache.py` 작업을 오케스트레이션으로 전환해".
- 재실행 대상: 1차 실행에서 (1) 결과가 기대값과 다른 질의(`pass` = false), (2) stderr에 `Warning: query failed`가 난 질의, (3) 애매한 질의. 애매한 질의는 평가 세트를 만들 때 `"boundary": true`로 미리 표시한 질의이며, 비발동 근접 사례 전부, R1-1의 직접 지시가 걸린 질의 전부, 트리 예외 문장(검색식 한 번의 위치 확인, 종료 코드·통과 여부 확인)이나 트리 4의 5개/6개 경계나 트리 5의 한 단계/여러 단계 경계를 겨냥한 질의가 여기 든다. 경고 줄에서 질의를 특정할 수 없으면 1차 평가 세트 전체를 재실행 대상으로 삼는다. 대상만 모은 평가 세트를 같은 방법으로 질의당 3회 실행하고 재실행 결과 JSON과 재실행 stderr 로그로 저장한다.
- 통과: 재실행 대상이 아닌 질의는 1차 실행에서 기대값과 같다. 재실행 대상은 3회 중 과반(2회 이상)이 기대값과 같다 — 재실행 결과 `summary.failed` = 0과 같다. 재실행 대상이 없으면 1차 결과 `summary.failed` = 0으로 끝난다. 1차 평가 세트·결과 JSON·stderr 로그를 실행 디렉터리에 남기고, 재실행 대상이 있을 때는 재실행 평가 세트·결과 JSON·stderr 로그도 남긴다.
